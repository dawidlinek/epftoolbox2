# Sync documentation with the code

The code is the source of truth. It is documented in four places, all hand-written:

| Surface | Role |
|---|---|
| `docs/src/content/docs/<category>/*.md(x)` | Starlight site; one page per component, plus pipeline, workflow and reference pages |
| `llms.txt` | Entry point for LLM agents (llmstxt.org format). An H1, a `>` summary, a short list of essential rules, then one `- [Title](docs/src/content/docs/<path>): one-line description` bullet per docs page under H2 sections that mirror the docs sidebar, and an `## Optional` section. It is an index, not a reference: parameters, defaults and examples live only in the docs pages |
| `README.md` | Key Features list and quick start |
| `examples/*.py` | Runnable end-to-end scripts, each with a `main(...)` that `tests/test_examples.py` calls on a short window (need an ENTSO-E key; not run in CI) |

## 1. Find the drift

**Mechanical drift** — run the checker; it imports the package and compares it with every surface:

```bash
uv run python .claude/skills/docs-sync/scripts/check_docs.py              # findings, exit 1 on errors
uv run python .claude/skills/docs-sync/scripts/check_docs.py --inventory  # every component: params, defaults, docs page
```

It covers registry/TUI gaps, components without a docs page, parameters missing from a docs page, llms.txt index drift (a docs page that llms.txt doesn't link, or a link to a file that doesn't exist), broken `from epftoolbox2 … import` lines, documented calls with keyword arguments the constructor doesn't accept, and `report.<method>()` calls that don't exist.

**Semantic drift** — the checker can't see changed *behaviour*. Look at what changed in the code (default scope: `git diff main...HEAD -- epftoolbox2/`, plus uncommitted changes) and read the changed public code in full. Watch for:
- changed output columns of a source or transformer
- changed meaning of a parameter, even when its name and default stay the same
- new or changed `EvaluationReport` methods → `model-pipeline/results.md`
- a change to one of the essential rules at the top of `llms.txt` (time zones, DST, column naming, transformer order, information set, leak-free inputs, Open-Meteo limits, caches, YAML) → that bullet, together with the docs page that owns the fact
- `cli.py` flags → `getting-started/cli.mdx`; `Workflow` YAML keys → `workflow/overview.mdx`; caching → the two `caching.mdx` pages

## 2. Update every surface the change touches

| Change | Update |
|---|---|
| New or changed constructor parameter | docs page parameter table and example. Serialization YAML examples if the component appears there |
| New component | new page `docs/src/content/docs/<category>/<kebab-name>.md` modelled on a sibling page (frontmatter `title`/`description`, example, parameter table, output, notes), its bullet in `llms.txt`, README Key Features |
| New, renamed, moved or removed docs page | its bullet in `llms.txt` under the H2 that matches the sidebar section (`- [Title](docs/src/content/docs/<path>): one-line description`), the sidebar entry in `docs/astro.config.mjs` when the section isn't autogenerated, and links from other pages |
| Removed or renamed parameter / class | remove it everywhere, including examples and YAML snippets |
| Output columns | the page's output section |

Rules:
- Every statement must be traceable to code you read. Don't document behaviour from memory or from other docs.
- Match the style of the surrounding page. `.mdx` pages import Starlight components at the top (`import { Aside, Tabs, TabItem } from '@astrojs/starlight/components';`).
- Categories under `docs/src/content/docs/` with `autogenerate` in `docs/astro.config.mjs` (data-sources, transformers, validators, models, evaluators, exporters) pick up new pages automatically in the sidebar. `llms.txt` never does: every page needs its bullet there.
- Keep `llms.txt` short (well under 200 lines). Link to a page instead of copying its content, and keep a one-line description per bullet. A fact belongs in the essential rules only if every user must know it before using the library, and it must also be stated on a docs page.
- Links in `llms.txt` are repo-relative paths, so a local agent can open them. The published site URL appears once, as a base URL in the intro paragraph.
- Don't touch `docs/.astro/` (generated).
- Findings in the `registry` group that point at `epftoolbox2/tui.py` or `COMPONENT_REGISTRY` are code gaps, not doc gaps: report them, don't fix them as part of a docs sync.

## 3. Verify and report

1. Re-run `check_docs.py` until it reports no errors. Resolve warnings or say why they stay (e.g. a TUI default that proposes a display name on purpose).
2. Run `uv run pytest tests/test_docs_code.py -q`. It compiles every python block and checks its imports and its call arguments against the real signatures, and compares the `reference/api.md` stubs with them. It is part of the fast suite in CI. Fix a failing block rather than opting it out with ```` ```python nocheck ````.
3. If `docs/node_modules` exists and pages changed structurally, build the site: `cd docs && npm run build`. Otherwise say the build wasn't run.
4. Report: each file changed and what changed in it, drift fixed, anything left and why.
