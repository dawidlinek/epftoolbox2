# Models: how a run works and what must not change by accident

## Run structure (`BaseModel.run` → `_worker.py`)
- `_preprocess` adds `{target}_d+{h}` targets by shifting **calendar days in local time** (not 24h), then `day` ids from local dates and a `hour` period id (0–23, or 0–95 for `freq="15min"`).
- One fit per task `(period, horizon, run_day)`, or with `refit` one per unit (see the `refit=` bullet under Dates). Task identity for the worker is `(hour, horizon, day_in_test)`, but `ResultStore` resumes on `(hour, horizon, run_date)` — the absolute calendar date each record already carries — so a `test_start` change between runs into the same directory can't make an unrelated date look already done. `BaseModel.run(save_to=...)` also writes/checks a manifest (`epftoolbox2.results.manifest`) recording the rest of what defines a forecast (predictors and their per-`(period, horizon)` order, target, freq, training window, model params, the data used up to `test_end` and its time zone, how its training rows are chosen); resuming into results made with a different one of those raises `ManifestMismatchError` unless overridden. The information-set settings and the `availability` level are recorded but not compared (they gate predictors, not what a fitted model predicts), so changing only the level resumes. Don't rename the JSONL record keys without updating `ResultStore`, which resumes from them.
- Workers are a `ProcessPoolExecutor` (fork on Linux, spawn on Windows) initialised once with numpy arrays. The model is **rebuilt in each worker** as `model_cls(predictors=[], **self._model_kwargs)`. A new hyperparameter that is not returned from `_model_kwargs` silently falls back to its default inside workers — see `LassoCVModel` for the pattern. `newest_target` is deliberately not one: the cut travels in `config["newest"]` (period -> k per issue day, by the task's position), so a worker's own copy keeps `"d-1"` and nothing reads it there.
- `_fit_predict(train_x, train_y, test_x)` receives standardised data and returns `(prediction_in_scaled_space, coefficients)`; the worker inverse-transforms the prediction.
- **Phases and worker inputs** (step 5g, `refactor/run-phases`; bitwise, records, manifests, tables, captured warnings and progress totals, `epftoolbox2-research/library_check_step5/run_phases/`): `run` is `_prepare_run` → `_RunState` (windows, the plan or its check, the inputs' check, the period frames, masks, store and manifest, pending tasks, and the skips decided before any fit, whose records go to the store at once), `_execute(state, sink)` (one pool of `_run_tasks`: `_build_hour_arrays`, `_worker_inputs`, every option a fit reads passed explicitly, `_jobs`; each job's records go through the sink in `_collect`: the store, or `_MemorySink` of the in-memory list) and `_finish_run(state)` (skip counts into the manifest, the shortfall warning, the ref); `run` closes the store (`_RunState.close`), `_prepare_run` closes it if it raises. `_prepare_run(periods=)` takes frames another model read (`_load_periods` returns them as `_Periods`): of the same frame object, target, largest horizon and freq, holding its columns (a fit reads its own by name). `ModelPipeline.run` checks each model once (`_checked_inputs` → `_Checked`) and passes it as `run(checked=)`; a check is of one model object in one state (`_Checked.run_of`: the model, frame, information sets and plan by identity, the model's `_check_settings` and the run's arguments by value), so a run whose arguments or settings differ from the check's, or another model's, checks itself, as before (a plain run into results made with windows runs the test window alone; a window widened after the check). So a pipeline no longer raises a check's warnings and logs twice per model (a midnight stamp, an unknown column at "raise", accepted assumptions). The phases are one frame under `run`, so each stacklevel that reached past `run` counts it: the store's cut-tail and lock warnings and the manifest's kernels and rows-unverified ones take 5, `_check_inputs` and `_plan_predictors` take `stacklevel=` for the midnight-stamp and never-published-in-a-window warnings, and a warning is attributed to the line it was before (`tests/models/test_run_phases.py`). Worker: every task function (`_fit_one_numpy`, `_row_value`, `_run_task`, `_run_day`, `_fit_unit`, `_run_unit`, `_run_block`) takes a `TaskInputs(hour_arrays, expanded, config, model)`, None meaning the pool's, all four of what `_worker_init` loaded into the module globals, never a mix (`_inputs_of`: inputs without a model raise `ValueError`), and `_fit_member` the model, required; a task's place, newest target, list, mask and rows are `task_place`, `task_newest`, `task_list`, `task_mask`, `member_rows` (a unit's `unit_rows`) and `finite_rows`, its record `forecast_record` (the key order of every path: a unit's `refit_anchor` after `freq`), `_combined` for a list of windows and `skip_record` for a skip. A test's stand-in for `_fit_member` or `_fit_unit` passes the arguments after the ones it reads through.
- **Estimator options** (step 3i): `LassoCVModel(fit_intercept=True)`, `OLSModel(fit_intercept=False)`, `StandardScaler(scale_binary=False)`, keyword-only, defaults today's. `_model_kwargs` returns an option only when not default, `StandardScaler.get_params` leaves out its default and `scaler_spec` gives the name when `get_params()` is empty, and YAML writes a model parameter only when not at its value in `_WRITTEN_WHEN_SET` (a class dict, which also holds `newest_target` and `refit`; a subclass adds its own): so no old manifest, `scaler_spec` or file moves. `scale_binary=True` ignores the mask (every column scaled), including a refit unit's. `tests/models/test_estimator_options.py` holds them to hand fits, with and without `refit`.
- **`RidgeModel`** (`models/ridge.py`, step 4c): `RidgeCV(alphas, fit_intercept, cv=None)`, i.e. efficient leave-one-out, on the standardised rows; one class defines `_fit_predict` (the composition of the other two), `_fit_model` and `_predict_fitted`, so `refit=` works. `alphas=None` is `DEFAULT_ALPHAS`, `np.logspace(-3, 4, 36)` written out as 36 literals (bit-identical to numpy 2.4.0's, the quality study's grid; literals so that a last-bit difference between numpy builds can't make a resume on another node refuse); `_model_kwargs` always returns the **resolved** grid and `fit_intercept`, so a manifest names what was searched (changing the default grid refuses resumes, deliberately), while `_WRITTEN_WHEN_SET` keeps YAML free of `alphas` unless set. `alphas` is checked and stored as a list of floats in `__setattr__` (a worker rebuilds the model from `_model_kwargs`). Fewer than 3 training rows raise `ValueError` (counted `fit_error`): with one or two, every leave-one-out error is 0/0 and scikit-learn quietly keeps its first penalty. The record keeps no chosen penalty (seam is `(prediction, coefficients)`). scikit-learn's LOO route loses digits as 1/alpha (largest coefficient error vs an exact SVD ridge, n 364, p 247: 1.7e-10 at 1e-3, 1.7e-7 at 1e-6, 1.8e-4 at 1e-9, 0.17 at 1e-12), so `_check_alphas` refuses penalties below `MIN_ALPHA` = 1e-6 (pointing to OLSModel); hand fits compare with `RidgeCV` itself (1e-12; bit-equal in practice) and a one-element grid with `Ridge` (1e-10 above alpha 1). `tests/models/test_ridge.py`; the golden is `tests/golden/lear_ridge_metrics.json` (its own file, so `synthetic_metrics.json` doesn't move); mutants in `epftoolbox2-research/library_check_step4/ridge/mutants/`.
- **`NaiveModel`** (`models/naive.py`, `_fits_nothing = True`): a forecast is its one predictor's value on the issue row (`issue_row`, so the second occurrence of a repeated hour), read by `_worker._row_value` (`config["fits"]` False) with no training rows, scaler or fit, coefficients `[]`; `training_window` is 0, so `read_days` reaches no history. Masks are still computed (over no rows, never read), which keeps a plan's resume checks as they are. One name per list: `_precompute_expanded_predictors` and `_plan_predictors` raise otherwise, and on a matching list; `newest_target`/`refit` aren't parameters and `__setattr__` refuses them. **`known_only=True`** (`_known_only`): with an information set (or `cut_rules`, which is how the probes give it, `_issue_day_forecasts`) a task whose cell is late is skipped as `not_published` in the parent before any task runs (`BaseModel._unpublished`, through `_Cells(..., "warn").known`, the path of `ctx.published`), at every level; the check neither refuses nor lists such cells (`_issue_time_checks` for fixed lists, `PredictorPlan.known_only` for functions), while a column without a rule follows `unknown` and the level. Which keys exist depends on the rules, so `training_cut["known_only"]` records the issue time and each input's resolved rule and a change refuses a resume. A model that fits nothing has no training target to check (`PredictorPlan.trains`). `tests/models/test_naive.py`; the week-ahead reproduction is `tests/test_week_ahead.py`.
- **Zones and `PooledModel`** (step 7g, `models/pooled.py`, `models/_pooled.py`, `results/panel.py`): `ModelPipeline.run(data={zone: frame})` (`_run_zones`) runs each plain model per zone through its own `run`, checked per zone before any fit, into `save_dir/<zone>/`: records, manifests and tables are its run on the frame alone, bit for bit (`tests/models/test_pooled.py`); keep it so, nothing a plain model stores may know it ran beside other zones. `issue_timezone="data"` is resolved per frame (`InformationSet.in_data_zone`) before anything reads it. A `PooledModel` is no `BaseModel`: each zone has a **member** (`member_of`, a copy of the inner model under the pooled name, `_pooled` read by `build_manifest` as the compared `pooled` field: zones in stack order, `over`, `zone_feature`, `missing`, the other zones' data hashes), whose `_prepare_run`/`_finish_run` are its own run's; `run_pooled` runs one pool of jobs (issue day or anchor, period) over every zone. A unit (period, day or anchor[, horizon]) reads **every zone's rows whatever is pending** (`member_fit`: `member_rows`/`unit_rows`, the zone's own mask, `finite_rows`, a scaler fitted on that member's rows alone, the order of skip checks of `_fit_member`/`_fit_unit`), stacks zone-major then horizon then date with the zone one-hot (none with one zone or horizon), fits with `_fit_model` and forecasts each issue row with `_predict_fitted`, inverted by its own member's scaler: one zone is the model to the bit, a resume cut short equals a fresh run. Never a scaler over the stack, never a member's issue row through another member's scaler, never one zone's day ids for another's rows (the three mutants of `epftoolbox2-research/library_check_step7/pooled/mutants/`). The shared fit is made by the earliest issue of its day: `shared_fit_checks` judges every zone's training target (on anchors with `refit`) and over-time predictors on each earlier zone's clock (`earlier_issue_zones`), refused at "raise", merged into the zone's listing at "warn"; `verify_pooled` perturbs rows before D on that clock too, and gives each zone its own positive control (its frame alone perturbed by `perturb_recent`, its own forecasts must move; never another zone's control, which can't reach it). Refused: `NaiveModel`, ctx functions, window lists, `"published"`, validation windows, one frame. A run over zones is told by its zone index (`save_dir/zone_run.json`, `read_zone_index`) alone, never by folders, so every layout of runs of one frame reads as before; every zone's frame is checked (days included, `_check_days_in_frame`) before any zone's files, errors name the zone, and a pooled run prepares zones with a manifest first; `_run_zones` checks the pooled resumes of the zones on file (`check_resumes`) and runs their plain models before it writes the index or any file of a new zone, and refuses a zone differing from an indexed one only in case (`check_zone_case`). `PanelReport.log_gain` scores every model on the same keys and cells by default (`common=True`).

## Dates (`models/_calendar.py`)
- **Rows by date, never by count.** A forecast (period, h, D) trains on the rows of its period dated in `training_span(D, W, h)`, `[D-W-h, D-1-h]`, and forecasts from the last row dated D; `actual` is that row's `y` (`_worker.training_rows`, `issue_row`). A date can hold two rows of a period or none, so anything that counts rows is wrong around a switch. `training_row_days`, `_training_sample`, `_matching_day_counts` and `_stored_actual_lookup` go through these. `too_few_rows` is no row in the span. `read_days` and `_days_read_by` read more than the span and stay supersets.
- **Both rows of a doubled autumn hour train**, each with the same target, and the second is the one forecast from. Dropping one would move every switch-hour forecast for a window after each autumn.
- **A target on a repeated autumn hour stays NaN** (`ambiguous="NaT"`): which of two prices is "the" 02:00 is undefined, and a mean would be a synthetic actual. That row drops from training, and `aggregate()` drops that day, by rule.
- **A slot the clock doesn't have is not planned**, on the issue day or the target day: no record, no skip, not in `count`. `IssueCalendar(freq, zone, horizons)` is the one count of planned forecasts (`run`, `split_by_window`, `report`, the ensembles), and `report` builds it from the manifest's `data_timezone` (`read_zone`), needing no data. A plan still evaluates a predictor function on those keys (`PredictorPlan.planned`), and nothing it returns or reads there counts: `describe`, `_matching_day_counts`, `check`, `listing` and the probe's reads leave them out, and a late `ctx.value()` there doesn't raise (`_Cells.planned`). A real gap is planned: `missing_test_row` on D, NaN `actual` on D+h. A period is on the clock when any minute of it is (`_clock_gaps` reads only the dates whose midnights aren't 24 h apart, minute by minute): Lord Howe's hour 2 stays on its spring day at 1 h, with its row at 02:30.
- **`newest_target`** (`BaseModel` keyword, validated in `__setattr__`): `"d-1"` is today's path call for call (`training_rows(days, day, W, hz)` without `newest`, so tests that monkeypatch `training_span` with three parameters still bind) and reads no information set. `"published"` reads k per (period, issue day) from `InformationSet.newest_targets` (`NewestTargets` in `_calendar.py`, looked up by date ordinal) and trains on `training_span(D, W, h, k)`; the worker, `_training_sample` (masks), `_matching_day_counts` and `_matching_days_of` all go through `_newest_of`, and `read_days`, `_days_read_by` and a matching plan's `first_grid_day` reach back by `NewestTargets.reach` (k below -1). It raises without an information set (`cut_rules` is the probe's way in, nothing else is read from it) or a rule for the target, at every level, and its training target is never checked (`check_target=False` through `check`, `late_uses`, `violations`, `PredictorPlan._scan`). A cell the clock skips reads as known (-inf), so it doesn't stop the walk; on the day before a spring switch the skipped hour's k is one more and its window ends on the switch day, with one row fewer, as "d-1" has the day after. Tables are memoised by value in `information_set._NEWEST_TABLES` (16, read-only arrays). YAML writes the keyword only when `"published"` (`_serialize_component`). `tests/models/test_newest_target.py` holds it to a hand table and hand fits.
- **`horizons=`** (`resolve_horizons` in `_calendar.py`, the one place the arguments are read): `horizon=H` is 1…H, a list is sorted, a repeat, an empty list or both arguments raise, and `range(1, H + 1)` is `horizon=H` in everything, so every place that writes or compares something asks `every_horizon` and keeps today's form for it (no manifest key, `ModelResultRef.horizons` None, YAML `horizon: H`, `horizon_arguments` passing `horizon=` on). Internals take `horizon` (the largest) and `horizons` (what is planned; None means 1…horizon): tasks (`IssueCalendar`), plans (`PredictorPlan.horizons`; `build_plan` calls the function for these alone), masks, expanded predictors and the checks go by `horizons`; targets (`_preprocess`, `_build_hour_arrays`, so the worker's `hz - 1` column), `check_names`/`check_predictors` (`{target}_d+k` for k ≤ max refused), `read_days`, the newest-target cap and a plan's `first_grid_day` stay at the max. No worker line knows the list, which is what makes a record of `horizons=range(3, 10)` bitwise that of `horizon=9` (`tests/models/test_horizon_ranges.py`, which also holds the mutants of `epftoolbox2-research/library_check_step3/horizon_ranges/`).
- **`issue_days=`** (`resolve_issue_days` in `_calendar.py`: weekday names in any case, sorted to `date.weekday()` numbers; all seven are None, every day, which keeps today's form everywhere: no manifest key, no YAML key, `IssueCalendar` called with three arguments, no `config["run_days"]` in a plain run). Only the issue days change; **training is untouched**: rows by date as above, every date's row trains. Internally `weekdays` (the tuple) goes to `_plan_predictors`, `_check_inputs`, `_check_plan_is_for`, `_window_days`, `RunWindows.issue_days(weekdays)` and `IssueCalendar(freq, zone, horizons, weekdays)` (its `issue_days`, `tasks` and `count` skip other weekdays: their keys are neither planned, missing nor skipped). A plain run with weekdays gets `config["run_days"][d] = (None, d, position)`, so `day_in_test` stays calendar days and a task's plan list and newest target are found by its place among the listed days (`NewestTargets.by_position(listed days)`). Newest targets are read for **every calendar day** of the windows, as a run of every day reads them, so `reach`, `read_days` and the mask day keep a run of every day's. **Masks** (the rule is in the masks bullet below): a fixed list's is read on the window's first calendar day whatever its weekday, and a function's list of the window's first planned issue day reads there too (so a Friday-only function equals the fixed list); any other on the date of its first planned issue day, read from `plan.issue_days` (never `offset + position`: positions aren't consecutive days). Never "on every issue day": that made the mask of Friday 24 March depend on whether a later Friday used the list (`test_a_later_end_of_the_test_moves_no_earlier_forecast`, `test_a_later_friday_s_data_moves_no_earlier_forecast`). The re-read of a column with no value scans calendar days, so a Friday run reads it where a run of every day does. A Friday record of a function still differs from a run of every day's where the two read a mask on different days, both no later than D (`test_where_a_friday_record_and_a_run_of_every_day_s_differ`: a Fridays-only list, Wednesdays and Fridays from a Monday, a list from a Thursday, and a list from the second Friday at a (period, horizon) whose first Friday's key the clock skips: (2, 2) on 24 March 2023, aimed at the skipped 02:00 of 26 March, makes 31 March the Friday run's first planned issue day of that pair). A plan's window slices go through `PredictorPlan.days_between` (bisect), never `position_of`, since a window may start on an unlisted day. The information-set check and the `warn` listing get the listed days (`issue_days=` to `check`/`late_uses`, also per window), so a weekly column (`Availability.weekly`) at `_d+9` is known on a Friday and late on a Monday. `verify` samples listed days (`sample_issue_days(issue_days=)`) and plans a function on them (`verify_model(issue_days=)`); `explain`, `leakage_probe` and `positive_control` don't take it (they run single days). A window with no listed weekday raises (`check_issue_days_in`). `tests/models/test_issue_days.py` holds a Friday run to the Fridays of a run of every day key by key; mutants in `epftoolbox2-research/library_check_step3/issue_days/`.
- **`freq="1D"`** (`DAILY` in `_calendar.py`, in `FREQ_STEPS`, `periods_per_day` 1): one row per local date at one wall-clock time, read from the index (`_date_utils.daily_anchor`). `_contract._check_daily` holds it on the whole frame: at most one row a date, one time of day, a time the clock has once on every date from the first to the last (02:30 in Warsaw raises), gaps allowed; finer data raises and suggests `at_time("12:00")`. The elapsed spacing checks aren't used for it (23 h would read as off a 24 h grid). Period 0 is on the clock of every date (`_clock_gaps` keeps a period with any minute), so `IssueCalendar` plans every date and no switch reaches a daily key. Rows by date and targets by the wall-clock day shift, as at any freq. `_resolve_day` finds a date by its day id: `.loc[date]` of a daily frame stamped at midnight is the row itself, not a slice. Every count of periods goes through `periods_per_day(freq)` (`_FREQ_TO_PERIODS`, `_Cells.periods`, the plan's checks, `_newest_targets`, `_skipped_slots`), never `1440 // step`, since `_STEP_MINUTES["1D"]` is 60. A daily run of `df.at_time("12:00")` is period 12 of the hourly run of `df` to the bit (`tests/models/test_freq_daily.py`); mutants in `epftoolbox2-research/library_check_step3/freq_daily/`. No transformer builds daily frames (decision 13 of the step 3 spec).
- **`refit=`** (`BaseModel` keyword, `check_refit` in `__setattr__`: None, `"kD"` or `"kMS"` with k from 1, or `"auto"`; anything else raises; a model without its own `_fit_model` and `_predict_fitted` raises, `_can_refit`). `refit_anchor(day, refit)` (`_calendar.py`, `_EPOCH` Monday 1970-01-05, months from January 1970) is a function of the issue day alone, and the one place anchors are computed. A forecast (p, h, D) uses the unit `FitUnit(p, h, a, list_id)`: rows `training_rows(days, a, W, h)` (with k(a) under `"published"`), cut as for a forecast issued on a, so nothing after a - 1 - h trains. Pool jobs are blocks, the issue days of one anchor (`_worker._run_block`); `_fit_unit` fits once and predicts each task on its own row through `_predict_fitted`, never `predict` over several rows (that differs in the last bits in about half the cases even with 5 columns: a forecast would depend on which others share its fit, and a resume wouldn't be bitwise). The scaler is fitted on the unit's (filtered) rows and transforms the test rows of the unit's pending tasks value by value; the mask is `StandardScaler.get_scalable_mask` of the unit's unfiltered rows (decision 17), so such a model computes no first-day masks (`masks` empty), records no `binary_masks` (`_fixed_mask_digests` None) and depends on no `test_start`/`test_end` (`binary_mask="fit"` gives a model without refit the same, see its bullet). Under `"published"` `_newest_targets` reads k on the anchors (`refit_anchors`), so `NewestTargets.at` of an issue day raises; `_newest_of` and its callers take anchors (`_fit_days`), the worker gets the table in `config["refit"]["newest"]`, and `newest_target_day` is a + min(k(a), h-1). Reads go back from the anchor: `_fit_start` gives `read_days`/`read_ranges` each window's anchor as its start, and `_check_reaches_back` (from `_check_inputs`, both paths) raises when the frame's first local date is after the earliest first row of `training_span(a, W, h, k(p, a))` over the planned anchors, periods and horizons (exact: a frame from that day gives a long frame's records, the day after changes them; `tests/models/test_refit.py` and `recheck_probes/probe_frame_check.py`), since the first block would silently train on fewer days (a frame sized for refit=None is too short whenever the test doesn't start on an anchor); and a matching plan's `first_grid_day` and `_days_read_by` start at `anchor(D) - W - h - reach` (`PredictorPlan.refit`, `_back_to_anchor`); `_check_plan_is_for` compares `refit`. The training-target check reads the anchors (`_target_on_anchors` for fixed lists, `PredictorPlan._scan`), predictors the issue days. The probes (`information_set._issue_day_forecasts`, so `leakage_probe`, `positive_control`, `verify`) run a refit model from run_day to the end of its block (`refit_block_end`, capped at the frame's last date) and compare run_day's forecasts only, its reads from a plan of run_day alone: a run of one day has one forecast per unit and hides a fit that reads a later day of its block. `_can_refit` requires one class other than BaseModel to define all three of `_fit_predict`, `_fit_model` and `_predict_fitted` (`_owner_of`), so a subclass overriding `_fit_predict` alone raises instead of being refitted with its parent's estimator, and one overriding the seam alone raises instead of refitting another estimator than its refit=None run fits. Records add `refit_anchor` (ISO) only when set; `training_cut` adds `refit` and `refit_epoch`; `check_stored_lists` compares each stored `refit_anchor` (`PlannedForecast.refit_anchor`) and skips mask comparisons when the cut names a refit, and a plain fixed-list refit run passes `check_stored` to `check_and_write` too. A resume runs pending tasks only, so a unit with pending forecasts is fitted again and only those are written. With `refit=None` no line of today's path runs differently: no `config["refit"]`, `_fit_days`/`_fit_start` return their input, `_back_to_anchor` is zeros, YAML has no key. Pool processes are capped at the number of blocks (a calendar year of `"12MS"` is one). `tests/models/test_refit.py` holds it (mid-block starts, a day alone, 1-3 processes, reversed units, resume, after-D changes, perturbations after a - 1 - h with positive controls over both switches at 1h/15min/1D, hand fits, published k on the anchor); mutants in `epftoolbox2-research/library_check_step3/fixed_refit/`. **`refit="auto"`** (step 4e, decision 16): `member_rules(members, refit)` gives each training window its rule, `"1D"` for W <= 84 (`AUTO_DAILY_UP_TO`) and `"7D"` for longer and `"expanding"`, from the window alone; any other `refit` is every member's (`BaseModel._refit_rules`). A unit `FitUnit(p, h, a_m, list_id, m)` is anchored on its member's rule (`_unit_of` reads `config["refit"]["rules"][member]`), so member i is to the bit the single-window model with W_i and its rule written out, and a single window under "auto" is its rule in every record. Everything that asks for *one* rule takes the coarsest (`_refit_block`, `block_rule`, which raises for rules that don't nest; "auto" gives `{1D, 7D}`): pool jobs are its blocks (a week holds the long members' one fit and the short ones' daily fits), `refit_anchor` in records and in `_stored_forecast_lookup` is its anchor (the oldest fit; `_worker._across_members` sets it, and `newest_target_day` as the max over members), `_fit_start`/`_fit_days`, a plan's `refit_block` (`_back_to_anchor`, a matching grid; matching takes one int window anyway), and the probes' `_last_day_of_block` (via `model._refit_block`). Everything that asks *which days a fit is made on* takes the union of every member's anchors (`_anchor_days`, `anchors_of_rules`): `_newest_targets` under "published", `_target_on_anchors`, `PredictorPlan._scan` (the plan gets `refit_rules`; `_check_plan_is_for` compares them). `_check_reaches_back` runs per member on its own rule's anchors and names the member under "auto"; for every refit rule it also requires the predictors' deepest lag (`_days_back`: `_d-k` k days, an hour lag rounded up to a day) before the earliest training row, since in a frame built from that date the row's lag is empty and the row drops out silently (a frame cut after its lags were built is refused too; refit=None has no such check). ## Predictor functions of `ctx` (`models/context.py`)
- `BaseModel` takes a function with one parameter named `ctx` (`takes_ctx`, by the name) as `_ctx_fn`; `(horizon)` and `(horizon, hour)` callables and fixed lists keep their own path and records, without a `predictor_list` key.
- `build_plan` evaluates it for every planned forecast, once, before any fit, and returns a `PredictorPlan`: distinct lists (expanded, deduplicated) and `assignment[(period, horizon)]`, the list id of each issue day. `ModelPipeline.run` builds it (`model._plan_predictors`), checks it, and passes it to `model.run(plan=...)`, which refuses a plan made for another frame, window, horizon, freq or information set. Nothing about a plan lives on the model.
- `ctx.published` / `ctx.value` read one cell, of the row the model forecasts from (issue day D, the period; a repeated autumn hour's second occurrence), and go through `_IssueClock`, the same path as `InformationSet.violations`, so a profile, an aggregate and a built-from rule mean the same in both. Never add a second availability computation. A no-rule column raises there at `availability="raise"`, whatever `unknown` says, and counts as known at the other levels. `published` must answer alike at every level with an information set, or a level would change the plan and the forecasts; what differs is only whether `value` of a late column raises (`raise`) or returns it (`warn`, `none`) and what is listed.
- `PredictorPlan.check` computes availability once per distinct name and reports per list. Only cells a list reads count, unlike a fixed list, which is checked on every day: a Friday-only list may hold a Friday-only column. The training-target check goes through `violations` unchanged.
- Workers get `task_lists` (the assignment), `list_hashes`, `expanded_preds` keyed by list id and masks keyed `(list id, period, horizon)`, and the per-period arrays hold the union of the lists.
- Masks (`BaseModel._plan_scalable_masks`, `_precompute_scalable_masks`, both through `_scalable_mask`; the default `binary_mask=None` without `refit`, see the `binary_mask=` bullet under Dates) are computed over the whole plan, pending or not, so a resumed run equals a fresh one. Per list L, (period, horizon) and window: the **mask day** m is the window's first calendar day (`offset`) if L is the list of the window's first **planned** issue day of the pair, else the first planned issue day that uses L; a fixed list's is always the window's first day. Only planned keys count (`PredictorPlan.planned()`): what a function returns where the clock lacks the period on the issue day or the target day decides nothing, and a list returned only there gets no mask (the worker never asks for one). A column with no value in m's training rows is **read again on the first calendar day d after m** whose rows (`training_rows`, with `_newest_of`) have one, for every list, fixed lists included, with no "used on every day" condition, and the scan stops at d or at the window's last day (`last`: `self._last_day`, or a window's end in `_window_masks`). Leak-free because m <= D, d is decided by rows dated d-1-h or earlier (d-1 with `"published"`), a forecast of L with a finite row has a value of the column in its own unfiltered rows so d <= D (a matching filter only drops rows), and a forecast before d has no finite row and is skipped; so the window-end stop moves no forecast either and only keeps a window's mask off other windows' days and the end of the data. Never scan issue days (a Friday run would differ from a run of every day), never let the last issue day or an unplanned answer decide (the old rule: a later `test_end` moved forecasts of 5 April by up to 0.25). Resume guard: a plain run of fixed lists has no digests to compare, so it records `binary_masks` (test key) only where the re-read changed a mask (`_fixed_mask_digests`, against `_precompute_scalable_masks(h, offset, offset)`), and `manifest.unrecorded_masks` refuses results with such a run's config but no digests (scaled before the re-read); every other plain manifest stays byte for byte as before. `tests/models/test_masks.py` (everything after D changed, a Friday run, keys the clock skips, a hand fit, the resume guard) holds it; mutants in `epftoolbox2-research/library_check_step3/mask_reread/`.
- Resume (`results.manifest.check_stored_lists`): each stored forecast inside the test period must have the list hash and mask digest a fresh run would give it, else `ManifestMismatchError`. The function's path and fingerprint are recorded, not compared: a source change that moves nothing stored resumes with a note. `predictor_layout_hash` is the constant `PREDICTOR_FUNCTION_LAYOUT`, so fixed lists and functions never mix; `data_columns_hash` is over the union of the lists, so a new column raises even if only pending forecasts use it.
- YAML: `predictors: {function: "package.module:qualname"}` (`importable_path` on save, by a round trip through import; `load_function` on load). `leakage_probe` plans on each frame it tests, at the pipeline's level, and runs without the information set, so a late list shows as a moved forecast, and a late `value()` raises at `raise` and is a change at the other levels (`late_reads`, whatever the noise did); `verify_model` also plans the whole test period and reports what the function uses late there as a `leak` (`late_in_period`), sampled or not; a cell read through `ctx` that moved counts as a change too (`_moved_reads`: the noise is large and positive, so `value(x) > 0` needn't flip). `verify_model` counts the columns a function only reads as inputs, and plans the whole period to report inputs no sampled day reads as `inconclusive`.

### `Use(list, train_on="matching")`
- **What it is:** per (period, horizon) a forecast fits only on past days for which the function returned its list id, which is the expanded list and `train_on` (`list_hash`), so the same names with `train_on="all"` don't match. `_fit_one_numpy` filters the rows of `training_span`, so a set can't reach past it. The window is not extended.
- **As of whose issue time:** a training row on D' at horizon h has issue day D' and target day D' + h, and the function runs for it exactly as for a forecast issued on D'. `_plan_training_days` asks through a second `_Cells` over the grid's days that aren't issue days, whose clock gives each day its own issue time, never that of the forecast being made. Moving that time would change the list of a day with what wasn't known on it; `tests/models/test_train_on_matching.py` perturbs such cells. A day that is also an issue day takes its answer from `assignment`, so a plain run over a window and a run of both windows agree bit for bit.
- **The plan:** only if some forecast returned a matching list, and only for the (period, horizon) pairs that have one, and days with a row there in the window of one of them (`_days_read_by`, `[D - training_window - horizon, D - 1]`). `day_lists[(period, horizon)]` has one id per calendar day from `first_grid_day` on: `OTHER_LIST` for a list no forecast uses, which stays out of `plan.lists` because the manifest, masks and the check index them, and `NOT_PLANNED` for a day not asked about. A row on such a day raises in `matching_rows`: it would otherwise quietly match nothing. A plan with no matching list has none of this and its function is never called on a training day. `_check_plan_is_for` refuses a matching plan for another `training_window`.
- **Workers** get `config["matching"]` only with such a plan, and no column more: the function is never called there.
- **Mask:** stays the list's (`_plan_scalable_masks`, unfiltered window), not one per set, and the scaler is fitted on the filtered rows. So don't compute a mask from `train_x` there.
- **Calendar:** a doubled autumn row follows its date, on both occurrences. A day with no row at a period isn't asked.
- **Vintages:** `ctx` reads the frame as it is now, so "as of D'" is about the availability rules, not about what was out on D'. A revision made after D moves the set and the forecast, which no probe can see, and a live `published()` False against a backfilled archive gives a list with `no_matching_days`. Only vintage data can fix it. The docs say so, and must not claim "what was known then".
- **Records:** `matching_days` hashes the dates of the span the function matched, before dropping rows with a missing value (`matching_digest`). `training_days` counts the dates left after that drop, what the fit really uses. Other records don't change. The record's days are dates, not day ids, which depend on where the frame starts. So a resume can refuse though the fit's rows are the same, when only a day it would drop anyway moved, and its message says the matching days differ, not the training days.
- **A list's order is part of it** (`list_hash`). `build_plan` warns on two lists with the same names in another order, on training days too, for any `train_on`; `list(set(names))` changes with the hash seed.
- **Resume:** `check_stored_lists` compares `matching_days` for each stored forecast (`PlannedForecast.matching_days`), through the worker's own `training_row_days` and `matching_rows` in the parent (`_matching_days_of`). This is what catches a data change in a column the function only reads, which `data_columns_hash` doesn't cover.
- **Too few:** no matching day is `no_matching_days`, no fit. As many days as predictors or fewer is not refused: `warn_about_thin` (`results/matching.py`) warns before any fit from `_matching_day_counts`, which counts as the worker does without fitting, and `ModelPipeline.report` again from the records. `report.training_days()` reads the records of its window, and the terminal exporter prints what is thin.
- **Late reads on a training day** go through `PredictorPlan.late_reads`, `read_cells` (keys with a third part, `TRAINING_DAY`, since they are on other days) and `listing`, so `leakage_probe`, `verify` and the report see them as they do on an issue day. A window's listing holds what its forecasts read through a matching list on another window's days too (`_read_by_forecasts_of`), which a plain run over it would list. The check on list names stays on forecast days, as for fixed lists: a list returned for a training row, late on that day, is no look-ahead for a forecast issued later.

## Validation and test windows (`results/windows.py`, `BaseModel.run(windows=...)`)
- A plain run has `windows=None` and goes through the same code with no `window` field, none of the manifest keys of a run with windows and the same worker config. `tests/pipelines/test_validation_test.py` and the export comparison in the step's report hold it byte-identical. Keep it so: a plain record has no tag, and a record without one means "test".
- Tasks are still `(hour, hz, d)`, with `d` the calendar offset from the run's first day (so `ResultStore` and `run_date` work unchanged; days between the windows have no tasks). `config["run_days"][d]` is `(window, day_in_window, plan position)`: the record's `day_in_test` is `day_in_window`, and `plan.assignment` is indexed by position, because a plan has no days between the windows.
- **Masks are per window, read from the window's own first day** (`_window_masks`; a model with `refit` has none, each unit reads its own rows), and `config["scalable_masks"]` is keyed by window in a windowed run. This is what keeps test records bitwise those of `run(df, test=T)` and validation records those of `run(df, test=V)`. One mask per run would change test forecasts silently: never read a mask across a window boundary. Nothing else in a fit may look at the window; `day_in_test` only labels the record (no seed, mask or refit depends on it).
- Everything that looks at days takes the windows' days, once: `_plan_predictors`, `_check_frame` (`_contract.read_ranges`, the union of what each window reads, so a coarse stretch no window reads isn't refused), `InformationSet.check` / `late_uses` / `violations` (`issue_days`), `PredictorPlan.check` / `listing`. The function of `ctx` has no way to see the window. `listing` and `describe` take a `(start, stop)` slice of the plan's days for one window, and the rows of each window travel through `ModelResultRef.availability_listing` and the manifest's `availability["windows"]`.
- Resume (`results.manifest`): a run with windows compares the data on what the stored forecasts read (`_compare_data`: the columns and last day their manifest recorded, and `actuals`, the target up to that day + horizon, since a stored `actual` reads past the last issue day), which is what lets `run(validation=V)` be followed by `run(validation=V, test=T)`. The manifest then grows to cover both (`_cover_both`). Stored keys are compared one by one in `check_stored_lists`: another window or mask raises `ManifestMismatchError`, and a file keeps one mask per (window, list, period, horizon), also for records outside this run's days, since a digest says nothing about which records used it. A plain run into results with windows runs as `RunWindows.fixed(None, test)` if that is the test window on file, and raises otherwise (`_as_run_of_test_window`); a window a run doesn't name stays recorded (`RunWindows.keeping`), and one that can't stay next to what the run names raises (`RunWindows.would_drop`). Plain results of fixed lists have no digests: if the test start moved, `check_stored_lists` refuses rather than guesses. Plain results have no `actuals` hash either, so their stored `actual` is compared with the frame (`_stored_actual_lookup`, the worker's own row), and an issue day past the frame's last day is refused, as nothing would compare it later. Known gap, unchanged: plain runs with different `test_start` mix masks in one file, fixed lists without a word and functions when a run on other days overwrote a digest, as they always did. The fixed-list case is pinned by the strict xfail `test_a_plain_run_resumed_over_an_earlier_start_equals_the_fresh_run` in `tests/test_known_issues.py` (286 of 812 records differ on the spring frame; `binary_mask="fit"` gives 0).
- `ModelPipeline.report()` takes the same window arguments. Shards whose manifests differ raise (`_stored_windows`). Ensembles choose through `read_windows(path)` and `Segment.serves` (`.claude/rules/evaluation.md`).

## Array tasks (`Workflow`, `environment.model_index`, `models_per_task`)
Task `i` runs the slice `[i*k, (i+1)*k)` of `pipeline.models` and leaves ensembles, evaluators and exporters to `report()`. `k` only says which process runs a model: no record or manifest may hold `k`, `model_index` or what else shared the task, and nothing a model stores may depend on them, or a merge stops equalling one run and a resume at another block size stops equalling a fresh one. `tests/pipelines/test_models_per_task.py` compares them byte for byte, manifests apart from their timestamps.

## Information set (the leakage boundary)
In `_fit_one_numpy` (its `_fit_member`, once per training window), training rows are dated in `training_span(day, training_window, hz)` and the last row dated `day` is the forecast issued on it, so with the default `newest_target="d-1"` the newest training target is the price of `day - 1`. This is deliberately conservative (it does not assume the day-`day` auction result is known). A model with `newest_target="published"` trains on `training_span(day, W, hz, k)`, k read from the target's rule (see Dates), and never on a row dated `day` or later (the cap in `training_span`, decision 6 of the step 3 spec). Moving either boundary, or the default, changes every published number — only do it when asked, and say so explicitly.

`verify` and the probes see through `"published"`: `verify_model` passes `check_target_boundary` only for `"d-1"` (`leakage_probe` raises on it for a published model), the target copy of a model that reads its target as an input gets the target's resolved rule, not `static`, `_issue_day_forecasts` gives the run `cut_rules`, and `positive_control` changes only rows dated D or later for such a model (`perturb_recent(first_row_day=0)`); with `rebuild` the raw values of D-1 still change and `_with_training_data_of(first_row_day=0)` puts back every built row before D. Each of these is pinned by a test with a planted leak (k + 1) and a model the control can't reach (`TrainingRowsOnly`).

`verify_model` also reads what a plan's function read through `ctx` on training days of a matching list (`_revised_training_reads`, from `plan._training_cells.read_cells()`, before `_check_inputs` releases them, and from the whole-period plan): a column whose rule `is_revised` (`REVISED_VINTAGES`: `latest_revision`, `last_write_stamp`) read there makes the model `inconclusive` (`IssueDayCheck.revised_reads`, decision 19). A read counts whatever the function did with it; an undeclared class, an issue-day read and a `train_on="all"` list don't.

**Rerun and co-batch** (step 6c, `verification.rerun_check`, `information_set.co_batch_probe`): on by default only for a model with `_predicts_together = True`, a `_co_batch_items` hook or a `_card` (`checked_by_default`), so every core model's `VerifyReport.table()` is as before with `rerun` and `co_batch` empty (`<NA>`). The rerun runs the unperturbed issue day twice at atol 0, each run inside `seeded_global_generators(2*seed+1 / 2*seed+2)` (numpy legacy, `random`, torch's if imported; states put back), since both runs fork their pools from the parent and would otherwise draw alike; a model that first imports torch inside a worker starts from torch's fixed default seed in both runs, which the rerun can't see (6g's torch scope seeds it). A difference makes the model `inconclusive` (`nondeterministic`); on that day a probe or co-batch move is `leak` only above `NOISE_MARGIN` (100) times the day's `RerunResult.noise` (inf when a forecast is missing or NaN in one run), else `inconclusive`, while `moved_reads`, `late_reads` and `late_in_period` stay `leak`. The co-batch check is the probe and control again over runs widened (`span=`) to the dates `_co_batch_items(run_day)` names that the built frame has: the probe's perturbation (every cell unknown at `run_day`'s issue time, every row; a row after D read as of its own issue day, `perturb_unknown`'s `own_day = max(day, 0)`, which only `as_of` and `weather_cutoff` read, so a later row's value from its own run is unknown; the target from D on for `"d-1"`), never whole rows, so other items' targets and late inputs change and what the rules call known at D for that row (a forecast published days ahead, a block's earlier days, training rows) doesn't; only `run_day`'s forecasts are compared. For a model that predicts its refit blocks in one call (`cuts_at_issue_day`: `_predict_block` and `_predicts_together`) the check also runs `run_day` on the built frame cut after its local date, the rows a run on that day has, against the whole frame, each run in `seeded_global_generators(2*seed+1)`, at atol 0 (`issue_day_cut`, `CoBatchResult.cut`, review 6d): its call holds the block's later days the frame has, so a forecast that depends on which rows its call holds moves though no unknown value does; a move is `leak` beyond the noise margin, `co_batch` counts the forecasts that moved under either, once. Not for other co-batch models: a sequence model reads later rows' known-ahead values, which the cut would take away. A hook names the whole call as the model forms it from the issue day alone; a batch of contexts that share history needs nothing more, since only unknown cells change. `_predicts_together` without the hook is `inconclusive`. `verify(device=)` sets an attribute named `device` on each copy that has one (`VerifyReport.devices`, a warning when none has). The shared adapter checks are `tests/models/adapter_suite.py`.

## Scaling
`StandardScaler` is fitted per task (per unit with `refit`) on training rows only. Columns that are binary 0/1 are not scaled; the mask is computed once per `(period, horizon)` (with `refit` per unit and with `binary_mask="fit"` per fit, from its own unfiltered rows), and per window in a run with validation, from the **first** test day's window (`_precompute_scalable_masks`, a column with no value there from the first later day with one, see the masks bullet above) and reused for all days. The target is standardised, which is why `OLSModel` defaults to `fit_intercept=False` (centering plus one-hot dummies carry the level); an expert model whose dummies aren't a one-hot needs `fit_intercept=True`.

A column is constant when its standard deviation is at or below `CONSTANT_STD_RTOL` (1e-12) of its largest finite absolute value, and then its scale is 1.0, as for an exact 0. One rule in `scalers/base.py` (`mean_std`, `is_constant`) serves every scaler, for the columns and the target; an all-zero column and one with fewer than two values keep scale 1.0. Never test a standard deviation with `== 0`: numpy gives 5.6e-17 for 0.3 thirty times, and a column of rounding noise divided by that became a regressor (a forecast of 3.5e13 for a test row of 0.31). The four VSTs (`AsinhScaler`, `MirrorLogScaler`, `PolyScaler`, `NPITScaler`) decide on the raw column and fit the VST as for the exactly constant column it stands for (`_VSTScaler._standardise`), since a transformed noise is only as small as the noise was, not small beside its own maximum. A column that is not constant by this rule scales bitwise as before. A constant predictor's training values are set to exactly 0.0 after centring (`scale_training_column`, NaNs stay NaN), so no solver is left to ignore its centred noise of about 1e-15 and any gives it the coefficient 0; its test row is still `(x - mean) / 1.0`, and the target is not zeroed.

`MirrorLogScaler` (`"mlog"`, `c=1/3`) and `PolyScaler` (`"poly"`, `lam=0.125`, `c=0.05`; step 4g) are Uniejewski, Weron & Ziel's (2018) transformations on `AsinhScaler`'s normalisation (`vst._median_mad`: median, MAD / 0.6745, the std and 1.0 fallbacks), then standardised like every VST. They are computed as `sgn(u) log1p(c|u|)` and `sgn(u) b expm1(lam log1p(|u|/a))` with inverses `expm1`/`log1p`, the paper's functions written so values near the median keep their digits (paper's form within 4e-15, round trips within 1e-14; `tests/scalers/test_mlog_poly.py` holds both against a transcription of the regimes research's `rg.py`). `c` and `lam` are keyword-only and left out of `get_params` at their defaults, as `standardise=True` is. A list of scalers inside one model doesn't exist: D2's recommended LEAR is an `AverageEnsemble` of four `LEARModel`s, one per VST: Lago's Invariant asinh (`{"name": "asinh", "params": {"standardise": False}}`, the member the regimes research measured; the standardised `AsinhScaler` forecasts differently), `"mlog"`, `"poly"`, `"npit"` (`models/lear.mdx`, `examples/lear_lago.py`, `tests/models/test_lear_recommended.py`).

## LEAR kernels (`models/_lars.py`, `models/_lars_numba.py`)
- **`_lars.py` is the numpy reference and a transcription of scikit-learn 0.24.2** (what Lago et al. ran): `lars_path` is `_least_angle._lars_path_solver(method="lasso", Gram=G)` rule for rule, `cd_lasso` is `_cd_fast.enet_coordinate_descent_gram` with beta 0 (two axpy updates of `H` per coordinate, the gap checked against `tol * yy`), `ic_select` is old `LassoLarsIC`'s criterion (ddof 0, df = |w| > eps, first argmin). Its quirks are kept on purpose: a degenerate entrant (Cholesky pivot below 1e-7) has its correlation zeroed and swapped back while the Gram rows stay swapped, and a path can then end early with its last kink labelled α = 0 (`test_a_degenerate_entrant_can_end_the_path_early_as_in_0_24_2`). Don't fix them as a side effect. The two departures are in the module docstring. A fit reads `GramStats` alone (the step-5 seam). Stage 2 of `"lars"` is `lasso_at`: its path runs to α* - 2 float32 eps, because 0.24.2's early stop ends a path stopped at α* itself on a kink up to 1.19e-7 above it without interpolating (6 of 144 real W 1456 fits, up to 2.3e-4 EUR/MWh off the exact refit); never call `path_at(lars_path(G, q, n, α), α)` for the lasso at α.
- **Verified against today's scikit-learn**, whose solver differs from 0.24.2's by one line (`np.around(corr_eq_dir, 15)`); the tests run it with that line and without (`_without_rounding`). With exact or near duplicate columns which column enters at a tie depends on the last bit of a BLAS sum (even on buffer alignment), in 0.24.2 too: those designs are compared up to the tie, and the degenerate-entrant rule on Gram designs of dyadic numbers, whose ties are exact.
- **`LEARModel`** (`models/lear.py`, step 4d): stage 1 is α* by `ic_select` on the normalised path, stage 2 Lago's refit at α* on the centred, unnormalised Gram (`lear_fit`): `solver="lars"` the exact lasso (`lasso_at`), `"cd"` Lago's `Lasso(max_iter=2500, tol=1e-4)`, whose early stop makes it depend on the column order. One class defines `_fit_predict` (the composition), `_fit_model` (`_fit_stats(gram_stats(x, y))`) and `_predict_fitted` (`ybar + (row - xbar) @ w`, one row, `w.tolist()` as coefficients), so `refit` works; `_fit_stats(stats)` reads `GramStats` alone, the step-5 hook for shared statistics. `_model_kwargs` is `criterion` and `solver`, written to YAML always (no `_WRITTEN_WHEN_SET` entry). `lago()` is a plain model: `lear_predictors(..., order="lago")` (the original's slot-major `_build_and_split_XYs` order; the exogenous series in file order, FR/BE generation first), AIC, `"cd"`, `{"name": "asinh", "params": {"standardise": False}}` (Lago's Invariant scaler: `_VSTScaler(standardise=False)` sets mean 0, scale 1 after the VST, still zeroes a near-constant column's training values, and is left out of `get_params` when True), `newest_target="published"`, `[49, 77, 1085, 1449]` (cw - 7: the original drops the first week). `tests/fixtures/lago/` holds the original epftoolbox's forecasts (47d6e06, scikit-learn 0.24.2) for the first DE and BE test days, its test rows and data (`build.py`, not run in CI); `test_lear_lago.py` holds the design row to the bit and every forecast to 1e-6 (measured 1e-9). A run reads `_kernel_backend` in the parent before its pool (numba compiles there) and passes it to the manifest's `kernels` (provenance: never compared, absent for other models; a resume on the other backend warns). **Exact twins** (columns equal up to a factor on the training rows, |G_jk| >= (1 - 1e-12) sqrt(G_jj G_kk): copies, exact negatives such as a complementary dummy pair after centring, `price`/`price_day_last` at hour 23, a daily value on 24 slots) are dropped but one in both backends' `lear_fit` before stage 1 (`_lars.without_twins`: rows, columns and q set to 0, coefficient exactly 0; the first in column order unless a later one is longer, as the lasso puts the weight on the longest): LARS can't take a second twin (0.24.2's degenerate entrant on a last-bit tie, then cancelling coefficients of about 1e14; scikit-learn 1.8 too). A design without twins gets back the same arrays, bit for bit as before. A dependency of three or more columns (a full one-hot set with the intercept) can still decide a tie by a last bit, which is why the backend claim is "within 1e-9 where no tie decides an entry". The manifest's `kernels` is a name, or the list of backends in the order first used once a resume used the other; a resume warns while a file mixes them. Records differ across machines by up to about 3e-9 (BLAS rounding of `X'X`).
- **`criterion="cv"`** (step 4f, `_lars.lear_fit_cv`) is old `LassoLarsCV(cv=KFold(5), normalize=True, max_iter=2500)` of 0.24.2 (`LarsCV.fit`, `_lars_path_residues`), from `CvStats`: the centred sums of five contiguous blocks of the training rows in their (date) order, KFold's sizes (`cv_stats`; the step-5 seam for `"cv"`, as `GramStats` is for the criteria; `_fit_model` picks which by `criterion`). Per fold (`cv_folds`): the other blocks pooled, centred and normalised on themselves, after `lear_fit`'s rules applied to that part as if it were the window (exact twins by `without_twins`, and `_constant_dropped`, a column whose std is at most `CONSTANT_STD_RTOL` of its rms there, a rule 0.24.2 lacks); its path to α = 0; the held-out block's error from its sums about the training means, linear between the fold's kinks as scipy's `interp1d` (`held_out_mse`: the last kink put at α = 0, the first at the grid's top, a stable sort, `searchsorted` left, a zero-width segment nan and dropped). Grid: the unique kinks of all folds strided to at most `MAX_N_ALPHAS` (1000); α* the first argmin of the mean of the folds' MSEs (`cv_choice`). Coefficients: the full window's normalised path **stopped at α*** (`lars_path(R, qn, n, α*)`, its last row, divided by the norms): 0.24.2's early stop on purpose, since the fixture holds 0.24.2 to 1e-9 (not `lasso_at`, which stage 2 of the criteria uses); no refit. `solver="cd"` with it raises (`CV_SOLVER_ERROR`, in `LEARModel.__setattr__` whichever is set second, and in `_check_choices`); fewer than 5 rows raise ValueError (a `fit_error` skip). numba runs the six paths, the rest is the shared numpy code. Tests: `test_lear_cv.py` (`_lasso_lars_cv` is an in-test 0.24.2 on rows), `test_lear_lago.py::test_cv_is_old_lasso_lars_cv` against `cv_{M}.csv` / `cv_coefs_{M}.parquet` (`build.py --cv`), the default grid strided in 34 DE fits, `max_n_alphas=50` at hours 0, 8, 16. Over Lago's test periods its window average is −0.1 to +0.9 % of the MAE of `"bic"` with Lago's refit, at 1.7–1.9× a `"bic"`/`"lars"` run's cost (1.5–1.7× `"cd"`'s; a fit alone 5.0–6.8× and 3.5–4.8×); that table compares two procedures (penalty and estimator): with path coefficients for both, CV's α* has a 9–25 % lower MAE than BIC's, and with BIC's α* the refit a 9–26 % lower MAE than the path (`epftoolbox2-research/library_check_step4/blocked_cv/`).
- **Backends:** `_kernels()` returns `_lars` or `_lars_numba` (`BACKEND`), by `EPFTOOLBOX2_KERNELS=auto|numpy|numba` (auto: numba when the `[fast]` extra imports; `numba` without it raises `MissingExtraError`). ## Parallelism and determinism
- `MAX_PROCESSES` and `THREADS_PER_PROCESS` env vars control workers, read when a model runs (`_executor_config`). Defaults: one task thread per process and one process per usable CPU (`_usable_cpu_count`: the affinity mask, so a SLURM allocation, not the node), capped at the number of run days. Threads in one process share the GIL (on unless a free-threaded build starts with `PYTHON_GIL=0`; pandas 2.x re-enables it), so with it on they are slower than processes. In tests set both to `1` with `monkeypatch.setenv` — faster and deterministic.
- Each task runs BLAS and OpenMP on `NATIVE_THREADS_PER_TASK` (1) thread: the pool already runs `MAX_PROCESSES` x `THREADS_PER_PROCESS` tasks at once. The pool initialiser `_pool_init` sets the limit through `threadpoolctl`'s controllers, library by library and only where a count differs, for the worker's lifetime; environment variables alone don't work, because the libraries read them when they load, which under fork happened in the parent (they are still set, for libraries a model loads later). The OpenMP limit is per thread, so each task thread in `_run_day` sets its own. Setting an OpenBLAS's thread count in a forked child starts its thread pool again (its fork handler stopped it in the parent): one thread per CPU it counted at load, for numpy's and scipy's OpenBLAS each, spinning about 0.1 s before sleeping, in every worker of every pool (62 per worker on 32 CPUs, 3 s of CPU per worker). So the parent holds its own OpenBLAS (`_has_own_thread_pool`: not the OpenMP layer) at `NATIVE_THREADS_PER_TASK` while pools exist (`_worker.pool_native_threads`, re-entrant and shared across threads: once around all of `ModelPipeline.run`'s models and `verify`'s probes, and around each pool in `BaseModel._run_tasks` and `_engine._run_chunk` for a model's own `run`), and `_limit_native_threads` sets a library only where its count differs, so a worker starts no thread. The hold puts the caller's counts back when the outermost closes (before ensembles and evaluators), which restarts the parent's OpenBLAS pool once per run (3-10 s of CPU on S02, what one worker paid per pool before): never release it per pool. Under spawn (`_POOLS_SPAWN`, Windows) it also sets `NATIVE_THREAD_ENV_VARS` for the workers' own loads, and puts them back; under fork it leaves them, which would pin any library the parent loads during the hold. No private OpenBLAS symbol: `blas_thread_shutdown_` is not exported by numpy 2.5's OpenBLAS (0.3.34). Parent-side work during the hold does no BLAS (planning, period arrays, collection); ensembles, evaluators and exporters run after it. `_worker_init` (called directly by tests) never limits threads: the caller's process keeps its own settings. `tests/models/test_worker_threads.py` guards the limit with a probe model that reports the thread counts inside its tasks, and checks that forecasts are bitwise identical however tasks are spread over processes and threads; `tests/models/test_worker_helper_threads.py` counts a worker's OS threads in /proc (model and engine pools, one and two task threads; a spawned process under the hold), checks the hold puts the caller's counts back once and that a pipeline run holds once, after finding which libraries start threads in a forked process set to one thread (it skips, naming them, when none does or one isn't an OpenBLAS with its own pool).
- Models must be deterministic for a given input: stochastic models need a fixed `random_state` exposed as a parameter. `tests/test_golden_metrics.py` pins current numbers.
- **Exact span sums** (`models/_sums.py`, step 5c; nothing calls it yet): `SpanSums(x, y).over(rows, cols)` builds a span's sums from integer slice products, each sum under 2^53, so they are bitwise the same in any union, column order, tiling, BLAS thread count, row chunking or downdate (`tests/models/test_sums.py`). Keep that bound (β from min(n, 2^15), P'P in `pair_rows(β)` chunks, 2^15-row runs added in int64), the one combination order and the span-only shifts; never swap in a BLAS Gram. Accuracy is fixed-point, relative to each column's largest |x - c| over the requested rows (a column with none of the span's large values there is re-sliced), not to Σ|x_j||x_k|: the module docstring has the argument and the bound.
- **Scaled statistics and fits from them** (`models/_stats.py`, step 5d; nothing calls them yet): `standard_stats(raw, values, mask, scale_binary)` maps a fit's `RawSums` to `ScaledStats` (centred G, q, yy in `StandardScaler` space, z̄ 0 on scaled columns) and `StandardParams` (issue-row transform, inverse); `OLSModel`, `RidgeModel` (`_ENGINE_NEEDS = {"rows"}`, for the leverages) and `LEARModel` (through `.gram()`) fit from it in `_fit_stats`, None meaning "the model path fits this one". Keep the candidate rule (variance from the sums not positive, or std at most `CANDIDATE_RTOL` = 1e-6 of max(|mean|, rms of x - shift): decided by `mean_std` on the values, since sums about the span's shift leave √eps noise on a column constant on ρ) and the hand-backs: `StatsFallback` for `CANCELLATION_MAX` and for sums that aren't finite, OLS's two guards (the pivot ratio `GUARD` 1e5 is only a lower bound on the condition number, so `dpocon`'s estimate `CONDITION_MAX` 1e9 too), Ridge's `RIDGE_ROUNDING_MAX` (in target units: `ScaledStats.yscale` must be set, None hands back) and non-finite leave-one-out scores, and, for every class with an estimator, `estimator_params`: `_fit_stats` reads its settings from `_estimator()` and hands back unless that is exactly the scikit-learn class with parameters its own `_validate_params` accepts and every other parameter at the default the statistics honour (a float `max_iter` or `fit_intercept=1` makes the model path raise, a subclass's `eps` or `gcv_mode` fits something else); change a guard or the Ridge budget only with the sweeps in `epftoolbox2-research/library_check_step5/stats_fits/`. The issue row is centred as the sums are, `((x - shift) - offset) / scale`, never on the rounded mean (a coefficient multiplies its half ulp), and `values` must be the sums' r rows. `tests/models/test_stats_fits.py` holds OLS to 1e-8 and Ridge and LEAR to 1e-9 of the model path.
- **CV blocks and `LassoCV` from them** (`models/_cv_stats.py`, step 5e; nothing calls them yet): `block_rows(ρ)` cuts the fit's rows ρ (never the span's) into KFold's blocks in row order; `block_stats(raw, blocks, params, values)` maps each block's `RawSums` with the fit's own `StandardParams` (block means about ρ's offsets, never a block's own scaler). Keep its two rules: a column a block's sums can't call varying (`_stats`'s candidate rule) is read on the block's rows, and equal values give exact zeros (else the √eps noise of sums about the span's shift survives on a training part where the column is constant, and LEAR's fold rule `_constant_dropped` no longer drops it); and per fold, the non-constant blocks' Σ(x - c)²/σ² above `CANCELLATION_MAX` times the centred sum the fold reads (training part or held-out block, columns and target) raises `StatsFallback`, which also catches a target constant on ρ. `LassoCVModel._fit_stats` (`_ENGINE_NEEDS = {"blocks"}`) is `lassocv_fit`: the grid `alpha_grid` from the window's centred q (Z'y without an intercept), every fold through the public `enet_path(..., precompute=G_tr, Xy=q_tr, check_input=False)` with a shape-only X and y = (√yy, 0, ..., 0) of the part's n values (the Gram kernel reads y only for y·y; √yy squares to yy exactly for about half the values, 1 ulp off elsewhere), the held-out error from the block's sums about the training means by `np.einsum` (a threaded GEMM's bits move with the thread count and reach the choice; keep products outside scikit-learn's kernel off BLAS), the first argmin of the folds' mean, the final fit on the window's Gram (`LassoCV` refits on the rows: another kernel form, whose screening differs only in testing excluded features again). It hands back where a fold's training part has no more rows than columns (the model path then descends on the rows; this includes n <= p), `cv` isn't the blocks' count, or anything isn't finite. LEAR `"cv"` reads `ScaledStats` through `cv_stats_of` (TypeError without blocks), and a `"cv"` instance sets its own `_ENGINE_NEEDS = {"blocks"}`. `tests/models/test_lassocv_stats.py` holds LassoCV to 1e-8 with the same `alpha_` (a flip only as a tie of the CV error, at most 1 in 500 designs) and LEAR `"cv"` to 1e-9 at the same position; sweeps and mutants in `epftoolbox2-research/library_check_step5/lassocv_stats/`.
- **Engine groups** (`models/_engine.py`, `models/_engine_worker.py`, step 5h; `epftoolbox2-research/library_check_step5/engine_groups/`): `ModelPipeline(engine="on")` runs the models `BaseModel._engine_capable(plan, forecast_only)` takes (one class other than BaseModel defines `_fit_predict`, `_fit_model`, `_predict_fitted` and `_fit_stats`; not `_fits_nothing`; no matching plan; not `forecast_only`; the class keeps BaseModel's `run`, `_execute`, `_run_tasks`, `_build_hour_arrays`) in groups of one `_refit_block` among the models whose `_frame_readers` are all BaseModel's; each instance of a class with its own `_preprocess` (or other frame reader), or with one set on the instance (`vars(self)`), is a group of its own and reads its own frames (an instance setting can reach them: two instances must not share frames); a replaced method set on the instance makes the model not capable, then the rest through `model.run` in list order; refs in list order. A group is cut into chunks (`ENGINE_MAX_MODELS` 20,000, `ENGINE_MAX_COLUMNS` 4,096, in list order); per chunk one `_load_periods` over the union of the checks' `used_predictors`, each model's `_prepare_run(periods=, writer=)` (stores on the group's one `StoreWriter`), one `hour_arrays_of` over the union, one pool (`_engine_init`: `_limit_native_threads`, then each model's `TaskInputs` from its own `_worker_inputs`), jobs `(day or anchor, period)` holding every pending task of every model, records routed by the model's place through its `_collect`, each future popped as it is collected (so the parent holds one job's records, engine off too); then `_release` per model and one `gc.collect()`, and the chunk's `_finish_run`s (the first error raised once the chunk's others finished; later chunks don't run) and its stores closed before the next chunk, so a run's tasks and done keys live as long as its chunk; `run_group` pops each model's arguments (its check) when its chunk starts. `run_group` is called where `run` is, so `_prepare_run`'s stacklevels hold. Every task runs the model path's functions (`_run_task`, `_run_unit` with `block_units`/`block_records`) on its model's own inputs, so a model the engine doesn't fit from statistics (below) equals engine off to the bit, alone, in any group, order, chunking, process or thread count (`tests/models/test_engine_groups.py`, which sets `_engine_worker.ENGINE_FIT_PATH = None` to check the plumbing that way). No fit may read the union by position, a job's tasks of one model must reach `block_records` together, and nothing stored may name the group, chunk or union. `verify` runs a capable model's probes as a group of one (`EngineAlone`, `run_alone`).
- **Fits from shared statistics** (`models/_engine_worker.py`, step 5i; `epftoolbox2-research/library_check_step5/engine_stats/`): a group model whose `_engine_worker.fit_path_of` is `ENGINE_FIT_PATH` ("engine-1": `_ENGINE_NEEDS` without `"blocks"`, `_ENGINE_FROM_STATS` not False and a scaler that is exactly `StandardScaler`, so OLS, Ridge and LEAR with `scaler="standard"` and `solver="lars"`; LassoCV, LEAR `"cv"` and VSTs stay on the model path until 5j, LEAR `"cd"` for good: its descent stops at a tolerance and follows the Gram's last bits, 5.5e-9 apart at ordinary rows of near-collinear columns) gets `config["fit_path"]`, and `_fit_member` / `_fit_unit` hand each fit, once they have selected its rows, ρ, mask and skips, to `EngineFits` (`engine=`, a `_worker.StatsFit`): its span's `SpanSums` (span = period, horizon and the period's rows of `training_span` before any filter, never the union's rows; built per task thread over the columns the job's fits of that span read, `_job_spans`, and dropped after its last item; never shared between threads: `_batches` puts the items that read exactly the same spans on one thread, so a span read by items of two threads, a window list's and a single window's, is built on both), `over(ρ, cols)` (a downdate when at most `DOWNDATE_SHARE` τ = 0.5 of the span's rows are left out; same bits either way), `standard_stats` with the fit's own mask, `model._fit_stats`, then per issue row `params.transform`, `_predict_fitted` one row at a time and `params.inverse`. A hand-back (no column: the model path skips OLS and Ridge as a `fit_error` and LEAR forecasts the mean; fewer than `MIN_ROWS` rows in ρ; `SumsOverflow`; `StatsFallback`; `_fit_stats` None or a ValueError) returns None and the model path fits it on the same values, to the bit; so does a LEAR fit whose active columns' Gram has a condition number (`_stats.issue_metric`) above `_ENGINE_CONDITION_MAX` = 1e6 (`ill_conditioned`: the LARS solution's last bits follow it, 1.6e-5 apart at 1e10 with a near-collinear pair both active), and an issue row too far out (`far_issue`, per row: `_stats.issue_distance`, the row's largest coordinate along the eigenvectors of the active columns' Gram in training standard deviations, so a row out along a near-collinear pair's difference counts, beyond the class's `_ENGINE_ISSUE_Z`, OLS 30, LEAR 10, or Ridge's `issue_rounding_ok`, RidgeCV's rounding at the row within `RIDGE_ROUNDING_MAX`), the hook's list then holding None for that row and `_fit_unit` forecasting it on the model path (so a unit with a far row writes the model path's coefficients for it and the engine's for the others); every hand-back is decided from the fit's own rows and span and the row alone, never from the unit's other rows (a resume or another test window would move them). Engine against off: OLS within 1e-8 EUR/MWh, Ridge and LEAR within 1e-9 with the same penalty and kink, every other field and the forecast counts equal, given the bounds (`far_sweep2.py`, 540 designs with near-collinear pairs to 1e-5 and rows out along their difference: worst kept 2.2e-9 OLS, 6.1e-10 Ridge, 3.5e-10 LEAR (the re-review's pipeline; 2.2e-10 in the sweep); past them gaps grow with the distance and the condition number); change a bound only with that sweep (`tests/models/test_engine.py`); within the engine the same bits alone, in any group, shuffled, chunked, at 1 and 3 processes, 2 task threads, any BLAS thread count (a job with fits from statistics runs on one BLAS thread, `_one_blas_thread`: LAPACK's eigh and Cholesky and a threaded GEMM move bits with the thread count from about 100 columns, as 5e found for its held-out errors), any τ, after crash and resume; nothing after D and nothing before the span moves a forecast (int windows). The manifest records `fit_path` (compared: switching the engine refuses a resume, `allow_manifest_mismatch=True` overrides) and the last fitting run's `engine` provenance (`EngineCounts`: fits, fallbacks by reason, the largest distance of an issue row the engine forecast; after a crash and a resume, the resumed run's fits alone); records say nothing of the engine. A new numeric change to these fits needs a new `ENGINE_FIT_PATH` name. `_stats.estimator_params` keeps its answer per (class, plain parameter values), so the check costs a dict lookup per fit.
- **Torch determinism** (`epftoolbox2/nets.py`, `models/_torch/`, step 6g; `epftoolbox2-research/library_check_step6/torch_core/`): `trainer.train_members` is a port of the research's `stk.py` and gives its forecasts to the bit on its own inputs and member keys (CPU, float32, `port_check.py`); keep it so (every stream, the split, the shapes, Adam's and the loss's operation order). A member's numbers come from its `seed_key` alone: the early-stopping rows are `member_split` (numpy's generator seeded by the key, a share of its own `train_rows`, never another row), the stream key `pcg32(seed_key & 0xFFFFFFFF)` draws every `nets.Linear`'s initial weights, the row order of each epoch (stable argsort of hashes) and every `nets.Dropout` mask (hash of key, `step * 8 + number`, element), and torch's generator is seeded by the key around the build (and the loop's training). Shapes come from the configuration only: steps per epoch from `nominal_rows` (a member with fewer rows wraps its own order), early-stopping rows padded to the nominal count, stacks of `pad_to` slots (dummies discarded). Under vmap `nets.Linear` is the custom op `epftoolbox2::stacked_linear` (vmap's own rule, `bmm` then an add, isn't stk.py's arithmetic): one `baddbmm` on a GPU, one `addmm` per slot on fresh copies on the CPU, because a CPU's batched product gives a slot whose matrices start on another boundary other bits (7 x 12 inputs, 6 outputs), and a CPU stack runs on one intra-op thread (`_stack_threads`), so it is the same in any slot and at any count; never go back to the batched product on the CPU. The loop's bits move with the thread count, so predictions run inside the same `torch_scope` as the fit. vmap uses `randomness="error"` and `check_vmappable` refuses `torch.nn.Dropout`, batch norm and tracked instance norm; the loop takes them. `torch_scope` saves and restores both precision interfaces (the legacy flags, parents then leaves of torch's `fp32_precision` attributes, which torch keeps apart: restoring only one leaves the legacy getters raising) and the thread count; `pin_torch_threads` runs in `_pool_init` only when `config["torch_threads"]` is set, so no core model's pool imports torch. `resolve_device` probes CUDA in a subprocess (the parent of a fork pool must not initialise CUDA). `runtime_fields` (device type, dtype, tf32, threads_per_fit, stack, pad_to) is for `_runtime_fields` and every entry is compared; the GPU's name is not among them (`device_name`, to warn). `fine_tune` raises `AssertionError` for a window after `windows.cut` before any step. `tests/models/test_torch_core.py` (torch-extra CI job) holds alone ≡ stacks of 4 and 16 at 1, 2 and 4 threads, lr variants, permutations, the planted divergence, the scope, the pins and the fine-tune; `-m gpu` the H100 checks.

## Known issues (don't fix as a side effect of other work)
- Forecasts disappear silently: `_fit_one_numpy` returns `None` on NaN predictors, too few rows, or `ValueError` from the fit; a crashing day is only `print`ed in `BaseModel.run`. `ModelResultRef.count` reports planned tasks, not produced ones.
- Profile slot names don't carry their slot length: `information_set` reads `_hNN` as an hour and every two-digit `_sNN` as a quarter-hour, but `DailyProfileTransformer` names every slot length other than one hour `_s` (`_daily.slot_names`). With `freq="30min"` on hourly data, `load_actual_s30` (15:00) is judged as 07:30, a look-ahead pinned in `tests/test_known_issues.py`; three-digit names (`_s000`, 5-minute slots) aren't recognised and are judged at the row's period. Rule resolution through the built-from column is therefore limited on an hourly model: there `_sNN` needs a user's rule on its own name (`InformationSet._resolve_for`), else it stays a column without a rule. Fix direction: names that say their slot length, or a slot length the check is told.
- `_contract._check_spacing` recognises a coarser stretch only as an unbroken run of evenly spaced rows with no neighbour one step away (at least 3 rows, rows × spacing at least a day), so that gaps and scattered row loss keep passing. Some coarse data has no such run, passes, and trains some periods on fewer days: hourly rows inside 15-minute data that also lost about 30 % or more of their rows at random (always caught up to 20 %, in 6–9 of 20 seeds at 30 %, almost never from 40 %), or that keep a `:15` row every other hour.
- `check_index` applies the most-common-spacing check and `_check_spacing` only to the days a run can read (`_contract.read_days`: `[test_start - training_window - horizon, test_end + horizon]` plus one day of margin on each side), because rows outside can't reach a fit: `test_unread_coarse_history_leaves_the_forecasts_bitwise_identical` proves it, so a new read outside those days (a look-back predictor built at run time, say) must widen `read_days`. Two consequences are deliberate and pinned: the margin refuses a run whose reads start exactly on the switch day, and duplicates and several rows in one slot are refused anywhere in the frame, so `freq="1h"` is refused on a frame with 15-minute rows it would never read. `results/manifest.py` still hashes every row up to `test_end`, so unread history changing still raises `ManifestMismatchError` on resume.
- `criterion="cv"` cuts its five blocks by rows (`_lars.cv_stats`, KFold's sizes), not by dates: on a frame that keeps both rows of a doubled autumn hour (one date, one target), a block edge can fall between them, and that fold trains on one copy and is scored on the other. On test_lear's synthetic Warsaw frame over September to December: 4 of 2928 fits at W 49 and 56, 3 at 84 (about 0.05 % of hourly keys); moving the edge changed 2 of the 4 W-49 forecasts, by 0.03 and 0.07 EUR/MWh. Frames through `DSTNormalizeTransformer` have no doubled rows. Pinned by `tests/test_known_issues.py::test_cv_keeps_both_rows_of_a_doubled_autumn_hour_in_one_block`. Fix direction: the fit is handed rows without dates, so `cv_stats` would need the rows' dates (or an edge rule) from the worker; the row cut is 0.24.2's.
