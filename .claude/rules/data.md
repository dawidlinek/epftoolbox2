# Data sources, transformers, validators

## Source contract
- `fetch(start, end)` returns a DataFrame with a **UTC** `DatetimeIndex` covering at least `[start, end)`. Local time only appears after `TimezoneTransformer`. `DataPipeline` clips every source to `[start, end)` (cached or not), and a cached run is assembled from pieces fetched separately, so a fetch of a sub-range must give the same values as a fetch of a larger range.
- `get_cache_config()` must include **every** parameter that changes the output; a missing parameter means stale data is served silently. The cache key (`CacheManager`, Parquet files under `.cache/sources/<key>/`) hashes `CACHE_FORMAT_VERSION`, the source class and that dict. When parsing logic changes, add or bump `"schema_version"` in `get_cache_config()`; when the cache layout changes, bump `CACHE_FORMAT_VERSION` in `data/cache_manager.py`.
- A hole in the cache is fetched from the start of its local day in the pipeline's `timezone`, or without one in the zone the source stamps its daily values at (`_cache_day_zone`, i.e. `EntsoeSource._daily_zone()`) (`align_to_local_days`, never before the run's start), because a fetch that starts inside a day makes `EntsoeSource._clip` carry that day's daily value forward and stamp it twice (`TimezoneTransformer` rejects two values for a day). The cached rows inside such a widened range are replaced only by a refetch that returns rows, and kept when it returns nothing (ENTSO-E's "No matching data" is an empty frame).
- The cache records only what a source returned, never the last `UNSETTLED_PERIOD` (2 days) before now; each file is read only inside its recorded range; writes are atomic and each key is locked (`filelock`) around fetch + write. A multi-column source's outer join can leave the merged row index running past where one column actually stopped (e.g. `load_actual` mid-outage while `price` keeps publishing); `covered_ranges` additionally caps the whole recorded range at one step past the last value of any column still being published (last value newer than `DISCONTINUED_AFTER`, 14 days) — an older last value is treated as discontinued and doesn't cap coverage. A source can also cap the recorded range itself: `df.attrs["settled_until"]` (UTC timestamp, documented on `DataSource`) marks its rows from that instant on as not settled, so they are returned but fetched again next time. `DataPipeline._fetch_source` reads it right after `fetch` (a clip or concat may drop `attrs`, and a timestamp in `attrs` breaks `to_parquet`) and removes it from the frame. The single-file cache stores the earliest one in its sidecar and does not reuse a file whose `settled_until` is before `end`.
- Unit tests never hit the network: mock `session.get` (patterns in `tests/data/sources/test_entsoe.py`, `test_open_meteo.py`). Real-API tests get `@pytest.mark.integration` and the `entsoe_api_key` fixture, which skips without `ENTSOE_API_KEY`.

## Benchmark source
`EpftoolboxBenchmarkSource`'s files are local wall-clock time, and its `index_timezone` (a fixed offset) only labels that clock, one hour off the true instants in summer. So `information_set.source_rules` gives its `price` and exogenous columns rules in `index_timezone`: the file's 23:00 on D is delivered on D. A Brussels rule on this index would read it as 00:00 on D+1 all summer, refusing `price_h23` and `price_day_*`. A true fixed-offset index with Brussels rules does refuse them.

## Serialization contract (YAML)
`DataPipeline._serialize_component` dumps every public attribute, but a parameter its class lists in `_WRITTEN_WHEN_SET` at that value (`DailyStatsTransformer.peak_hours`, `ForecastSource.agg`: so a file saved now loads in versions from before it; `_component_fingerprint` leaves it out too, so cache keys don't move) (skipping `session`, `console`, `logger`) and reloads with `Class(**params)`. So constructor parameter names must equal attribute names, and derived/internal state must start with `_`. New components must be registered in `COMPONENT_REGISTRY` in `pipelines/data_pipeline.py` (see the `add-component` skill). A parameter value that isn't a plain type (str/int/float/bool/None/list/dict, plus numpy scalars/arrays, tuples, ranges and `Path`, all converted) raises `TypeError` on save rather than being silently dropped. The converter is `to_yaml_value` in `pipelines/_yaml.py`; `ModelPipeline` applies it to model, evaluator and exporter parameters too (a model with callable `predictors` raises `TypeError`).

`api_key` (and any component's declared secrets) is written as `${<SOURCE>_API_KEY}` by default and expanded from the environment on load; `save(path, include_secrets=True)` opts out and writes the literal value. Any string parameter may itself contain a `${VAR}` reference, expanded on load and preserved (not flattened to the expanded value) on resave. File-like parameters (`path`, `*_path`, `*_file`, `*_dir`) loaded from a relative path are resolved against the YAML file's directory, not the working directory, and are written relative to it again on save.

## Column naming (relative to the row's local date D)
- `x_d-k`: value of `x` on D-k (LagTransformer, positive lag). `x_d+h`: value of `x` on D+h as known on D (negative lag, Open-Meteo forecasts, model targets). Hourly/minute lags use `h`/`min` units, e.g. `price_h-24`.
- Day lags shift by **local calendar days** (`shift_calendar_days` in `epftoolbox2/_date_utils.py`, shared with the model's target shift): same wall-clock time on D-k; the hour skipped in spring is NaN; the repeated autumn hour maps occurrence to occurrence, else to the first occurrence (the model's targets keep NaN there instead, see `BaseModel._shift_index_by_calendar_days`). `h`/`min`/`s` lags, and any frequency that isn't whole days (`"24h"`, `"15min"`), are elapsed time and never named `d`. Day lags need a local index: run `LagTransformer` after `TimezoneTransformer` (it warns on a UTC index). The skipped spring hour gives NaN in `x_d-k` at 02:00 on the day k days later, so the model skips those forecasts (hourly with `d-1` and `d-2`: 14 a year).
- `x_day_peak` (`DailyStatsTransformer(stats=[..., "peak"], peak_hours=(8, 20))`) is the mean over the slots whose local hour is in `peak_hours`, on whole days only like every statistic there (a missing 03:00 makes it NaN), so the information set judges it at the day's last slot (`_DAY_AGGREGATE` has `peak`). `_daily.PEAK_HOURS` must equal `results.breakdowns.PEAK_HOURS` (a test holds them equal); a non-default `peak_hours` without `"peak"` raises, as in `report.aggregate`. The default `stats` stay the four without the peak, so existing frames don't move; a saved pipeline writes `peak_hours` only when not `(8, 20)` (`_WRITTEN_WHEN_SET`).
- `x_hour_mean` and `x_hour_dev` (`PeriodStatsTransformer`, `period="1h"` only, `freq` dividing it, default `"15min"`): the mean over the slots of the row's hour on every row of it (NaN unless every slot has a row with a value) and the row's value minus it. An hour is keyed by the instant it starts (`period_stats.hour_starts`), so the repeated autumn hour is two hours of four by occurrence and the skipped one has no rows; a naive index's hours are its wall clock's. The information set reads both at the hour's last slot (`_HOUR_AGGREGATE`), in the row's occurrence, and on a daily row as a day aggregate. It warns on a UTC index (`check_index`: UTC hours aren't a half-hour zone's), refuses a duplicated index (`check_unique_index`, DailyStatsTransformer too) and data with no hour of its slot count (hourly data with the default `freq="15min"`). `_DAY_AGGREGATE` and `_HOUR_AGGREGATE` are built from `daily_stats.STATS` and `period_stats.STATS`: a new statistic is read as an aggregate by itself.
- `x_day_max_d-1` and `x_d-1_day_max` differ across DST: the second aggregates the lag over the rows of D, so it is NaN on all 24 rows the day after the spring switch and leaves out the second 02:00 the day after the autumn switch. Lag the finished statistic.
- `DSTNormalizeTransformer` (optional) turns the local index into naive wall-clock time with 24/96 slots a day (Lago et al. 2021: repeated hour averaged, skipped hour = mean of its neighbours, both on the same day; `is_dst_adjusted` flags them). Run it after Timezone/Resample and before Lag; after it, day lags and the model's shifts are plain whole-day shifts and no forecast is lost to DST. Values on flagged slots are synthetic, including actuals.
- Open-Meteo uses the **previous-runs** API: `{prefix}_{col}_d+i` at row t is the forecast for t+i days issued about i days earlier, and rows later than now+13h are dropped. Never switch a backtest to the plain forecast/archive API — it returns latest or observed values, i.e. look-ahead.

## ENTSO-E specifics
- Document types: A65/A16 actual load, A65/A01 day-ahead load forecast, A65/A31 week-ahead daily min/max, A75 actual generation, A69 wind/solar day-ahead forecast, A44 day-ahead prices, A61 day-ahead forecasted transfer capacity (`transfer_capacity`, needs `neighbours`), A68/A33 installed capacity (`installed_capacity`, P1Y at local 1 January, carried to `start` via `_PERIOD_COLUMN_PREFIXES`). Parsing is `xml.etree` with namespaces stripped; responses with a DTD are refused.
- `prefix` is applied last in `fetch`, after `_clip`, so internal column names (`_PERIOD_COLUMNS`) stay unprefixed. `neighbours`/`prefix` enter `get_cache_config()` only when set.
- A77/A80 unavailability is deliberately not offered: the API gives the latest revision, and with `mRID` all revisions but with `createdDateTime` rewritten (2024 outages dated October 2025), so values known at issue time cannot be rebuilt.
- `fetch(start, end)` returns [start, end). Daily columns (`_PERIOD_COLUMNS`) whose day covers `start` are re-stamped at `start`.
- curveType A03 omits a point that repeats the previous one: every Period is expanded to positions 1..N from its `timeInterval` and forward-filled (also trailing positions). A01 gaps stay missing.
- A31 comes as one Period per request starting at local midnight of the first requested day (verified for PL and DE_LU in winter, summer and across both DST switches in 2024), and this holds for every area, not just CET/WET ones: the period always starts at *that area's own* local midnight, whatever its UTC offset. P1D positions are mapped onto local calendar days of the area (`AREA_TIMEZONES`, default Europe/Brussels), so a week with the autumn switch (169 h) still has 7 positions. When this source is part of a `DataPipeline`, each P1D value's own local day D is then re-anchored to *the market zone's* local midnight of D, not this area's own (`EntsoeSource._daily_zone`, bound via `DataPipeline._bind_component_timezones` like `CalendarSource`/`OpenMeteoSource`, though this source has no zone parameter of its own to conflict with) — a neighbouring area combined into a market pipeline (`EntsoeSource("FI", ..., prefix="fi")` inside `DataPipeline(timezone="Europe/Warsaw")`) would land its daily value an hour off the market's own day, and on the wrong calendar day around a DST switch, since FI/EET and PL/CET switch at the same UTC instant but never share a UTC offset. Standalone use (no `DataPipeline`), or an area that already is the market's own, keeps the area's own midnight stamping (a no-op in the second case) — see `TestWeekAheadDailyMarketZone` in `tests/data/sources/test_entsoe.py`. `TimezoneTransformer.daily_columns` snapping is **not** a no-op in general: its default `daily_anchor` is the resolved `target_tz` itself (DST/timezone review finding 1), matching where a same-pipeline `EntsoeSource` always anchors A31; a fixed `"UTC+02:00"` anchor would silently misplace every value in EET/EEST zones (FI, EE, LV, LT, BG, GR) every summer and every value, year-round, in a fixed-UTC+3 zone (e.g. Europe/Istanbul) — see `TestDefaultAnchorIsTargetZone` in `tests/data/transformers/test_timezone.py`. Its `daily_columns` also match a `f"_{name}"` suffix, so a prefixed neighbour's column doesn't need listing by name. `epftoolbox2.information_set.source_rules` follows the same anchor: an `EntsoeSource` with `"load"` in `type` gets its own `load_forecast_daily_min`/`_max` weekly-availability rule (prefixed the same way) whose week is read in `EntsoeSource._daily_zone()` (`week_zone=`), published at 10:00 Brussels like the built-in rule (whose week is the data's local dates, `week_zone="data"`): A31 is published 2 h before the 12:00 CET gate in every zone, so the publication instant never moves with the market, only the week does. Reading the week in Brussels dates flagged Helsinki's Monday 00:00 (Sunday 23:00 Brussels) as last week's, a look-ahead, and Lisbon's Sunday 23:00 as next week's.
- Prices: only classificationSequence 1 or absent (SDAC). DE_LU/AT also publish sequence 2, a separate 15-minute auction (EXAA), on the same timestamps; never use it as SDAC; `EntsoeSource(price_exaa=True)` (AT, DE_LU only, needs `"price"` in `type`) fetches it in a second A44 request with `classificationSequence_AttributeInstanceComponent.position=2` into `price_exaa` (rule `published("11:15", 1)`). CH's `price` is the Swiss auction (gate 11:00, rule `published("12:00", 1)` Zurich), not SDAC. Both times are legal bounds, first-seen times unmeasured. From 2025-10-01 PL and DE_LU publish only 15-minute SDAC prices, before it only hourly. Output is one grid: hourly with `prefer_15min=False` (complete quarter-hours averaged), 15-minute with `True` (hourly periods step-filled).
- A75: series in `outBiddingZone_Domain` are consumption (pumping; for AT every type, mostly zeros) and go to `generation_<type>_consumption`, never into the generation column.
- The API key travels in the `SECURITY_TOKEN` header, not the URL; error messages are redacted and carry the Acknowledgement `<Reason><text>`. 429/5xx/network errors are retried (`MAX_RETRIES`, honouring Retry-After); anything else raises `EntsoeApiError`, so a failed chunk never becomes a silent gap.
- `get_cache_config()` has `prefer_15min`, `schema_version` (`SCHEMA_VERSION`), and, only when `"load"` is requested, `daily_zone` (the resolved A31 anchor, see above — a pipeline bound to a different market zone must not share a cache entry with another); bump `SCHEMA_VERSION` whenever parsing output changes.
- Publication deadlines (Reg. 543/2013) vs 12:00 CET gate closure, i.e. what a forecast issued on D may use, are tabulated on the docs page `docs/src/content/docs/data-sources/entsoe.mdx`. Short version: `load_actual` and `generation_*` actuals only `_d-1` and older; `load_forecast` up to `_d+1`; `load_forecast_daily_*` up to `_d+2` (`_d+3` after 10:00); `generation_*_forecast` only `_d+0` and older.

## PSE specifics
- `PseSource` (`api.raporty.pse.pl`, keyless): a 15-minute row is stamped with the END of its period (`dtime_utc`), so the index is `dtime_utc - 15 min`; `business_date` is the local date of the period's start. Columns are prefixed `pse_` by default so no name falls to an ENTSO-E default rule outside a `Workflow` (only `workflow.py` applies source rules).
- `pdgsz` is hourly with one row per version. Until about spring 2025 it holds one version per hour written on the delivery day (no version on D-1: NaN); later 35-44 versions, the first around 15:55 on D-1. The source keeps, per hour, the latest version stamped at or before `pdgsz_cutoff` (Warsaw, D-1) and repeats it over four quarter-hours; the rule of `usage_fcst` is built from the same parameter.
- `publication_ts` of the other PSE tables is a last-write stamp (bulk reloads rewrite it), so it never decides availability; the built-in rules in `information_set._pse_rules` do. `rce_pln` is a different series from `csdac_pln`, never the day-ahead price. The cache records nothing newer than two days, so a later PSE reload isn't seen: caches can differ.
- Not offered, on purpose: the balancing tables `sk`, `cor`, `energy-prices` (their lag changed from D+4 to D+1 on 2026-10-08; they need `RuleChain` periods), `poze-redoze` and `unav-pk5l`.

## Forecast source (`data/sources/forecast.py`, step 7a)
- `ForecastSource(path, model, column, horizon=1, available=None)` reads the ok records (highest revision, `read_records`, JSONL or Parquet: bitwise the same frame) of one upstream horizon and puts each at its **target instant**: slot `hour` of `target_date` by the clock of the upstream manifest's `data_timezone` (`_date_utils._occurrences`): a repeated autumn slot on **both** of its instants, a skipped spring slot nowhere (3b never plans one; an old record of one is dropped), a `freq="1D"` value at the manifest's `daily_stamp` ("HH:MM", provenance written by every 1D run since 7a). One horizon per source (decision 2): the user lags it, `x_d+1` on D is the forecast for D+1 issued on D. Records of other horizons are read and dropped. A **live upstream** (`live.json` there and every leaf manifest `mode` "live"; one without the other raises, `_is_live`) is read through `LiveStore.visible("latest", cutoff=)`: each issue day from the newest revision committed (`finished`) at or before `available` (else the issue time) on that day in the issue zone (`results.live.local_instant`), with a record of the day (one revision per day); a newer commit left out on any day warns with the count (a live upstream needs `available` at or after its deadline); no committed revision at all raises, `chained_input` takes no issued spans (no test period to be outside), and `content_digest` adds `issues.jsonl`; a record with `issued_at` outside a live directory raises.
- Refuses (`UpstreamError`, a ValueError): no manifest, no `information_set`/issue time (in any leaf of an ensemble), a data zone that isn't a named zone, a 1D upstream without `daily_stamp` (the message says a resume records it), leaves with different issue times, `available` before the issue time, no record of `horizon` at all. An empty `[start, end)` while records exist elsewhere warns and returns an empty float column.
- An ensemble's results (always JSONL) are read like a model's; its issue time, data zone fallback, `daily_stamp` and late listing come from its **leaf** members' manifests (`member_results` names, recursively), which `_check_members_agree` already made agree.
- `get_cache_config()` is None (the upstream grows). `DataSource.content_digest()` (default None) is new: `_component_fingerprint` adds it as `"content"` only when not None, so the single-file cache's digest of every other source is unchanged; `ForecastSource`'s is the upstream manifest's `manifest_digest` plus the sha256 of the JSONL's bytes (33 ms for 26 MB, against 0.8 s for a fetch: a coarse mtime or a copy that keeps it can't hide a change) or of the Parquet `_catalog.jsonl`.
- `path` is kept as given (YAML writes it back) and read with `~` expanded; `ChainedInput.path` (and so the manifest's) is absolute. In a `Workflow` file an inline source's relative `path` is the YAML's (`Workflow._build_data_pipeline` passes `base_dir`).
- **What vouches for an upstream** (`Upstream.unchecked`, each leaf with its reason): no `availability` (level none); level raise with `information_set.unknown` other than "raise" (a rule-less column passed unlisted); `availability["stored_under_other_rules"]` (`manifest._keep_listing`: resumed under another information set, except a later issue time over an empty listing at warn/raise with the rules otherwise equal, `_issued_later_alone`; or over records of a level-"none" run whose span, `_issue_span` of the existing manifest, this run's own span taken before `_cover_both`/`_keep_windows` doesn't cover: `{"listing": [], "level": "none"}`); `data_unverified` or `training_cut["stored"] == "unverified"`; records whose run dates (`_issued_span`, all ok records at the source's horizon, cached by the file's size, mtime and inode) reach outside the manifest's `[test_start, test_end]`, when it has no `windows`. Any of them, or a flagged row in a leaf's listing (`late`), makes the column `late upstream` downstream. `chained_input()` therefore reads every record's run date once per file state (0.8 s for 87k JSONL records, 0.09 s Parquet).
- Its rule comes only from `source_rules` (`with_source_rules`; `Workflow.run` applies it): `published(available or issue time, days_before=horizon, timezone=issue zone, day_zone=data zone, vintage="snapshot")`. An issue zone of `"data"` in an old manifest is read as the data zone. Outside a Workflow the column has no rule: docs and examples always pass `with_source_rules(data.sources)`. `InformationSet.resolve` gives a chained column (through shifts, profiles, day aggregates) its source rule before every layer, so no user rule, assumption (`entsoe_a69_by_10`'s `generation_*_forecast`) or pattern replaces it, in the check, `explain`, `ctx` and the probes alike; a user rule naming one exactly (`x`, `x_d+1`) raises `InformationSetError` in `with_source_rules` and in `models._chained.check` (`refuse_rules_on_chained_columns`). `with_source_rules` also registers a `ChainedInput` per column (`InformationSet.chained_inputs()`, `chained_of(name)` through shifts, profiles and day aggregates), which `models._chained` reads; see `models.md`.

- **`agg`** (step 7d): `ForecastSource(..., agg="min" | "max" | "mean" | "peak")` emits `output_column` = `{column}_day_{agg}`: `DailyStatsTransformer(column, [agg], freq)` of the placed forecasts in the upstream's data zone (`_day_statistic`), bit for bit, taken on the whole placed frame before `[start, end)` is cut (a sub-range holds the same values); NaN on a date missing a slot or a prediction. A 1D upstream is refused in `upstream()`. `source_rules` and `chained_sources` key the column by `output_column`, with the source's own rule, and `ChainedInput.agg` set (`record()` writes `agg` only when set; not in `CHAINED_IDENTITY`, the column name differs anyway). It is a chained column of its own, read at the row's instant, not a day aggregate of the frame's date: every forecast of a target date is issued at one instant, so that is exactly the latest of its inputs in every zone pair, where judging the frame date's last slot would be a day late where the frame's zone isn't the upstream's (`test_a_chained_day_statistic_is_known_exactly_when_the_latest_of_its_forecasts_is`). Coverage (`_off_the_clock`) lets off every row of a date whose issue day skips a slot (3b plans no 02:00 forecast for the day after a spring switch at horizon 1: never whole), counted in `coverage[name]["let_off"]`; a `_day_` aggregate made by `DailyStatsTransformer` after the plain chained column is still counted as it stands. An hour aggregate of a chained column (`x_hour_mean_d-1`) is judged one level down, as `x_d-1` at the same row: its hour is whole only with each slot, so the unplanned hour's rows are let off. Only an hour aggregate (`_is_hour_aggregate`): a rolling statistic of a chained column (`x_roll7max_d-1`) is counted as it stands, as its window's days, not its row's slot, make it NaN.

## Generation inputs (`data/transformers/solar_geometry.py`, `rolling_stats.py`, step 7e)
- `SolarGeometryTransformer(locations, weights=None, freq="1h", prefix="", night_below=-0.05, algorithm="meeus")` adds `COLUMNS` (`sun_elevation` degrees without refraction, `sun_sin_elevation`, `clear_sky_ghi` Haurwitz, `is_night` = mean sine < `night_below`) at each row's **UTC instant + freq/2** (so the two rows of the repeated autumn hour differ, and a UTC index gives the same values); several sites are a weighted mean of each column, `is_night` read on the mean sine; the declination and equation of time are computed once for all sites (`_SUN`), each site adds its hour angle (`_sine`). A naive index is refused (no instant: run it before `DSTNormalizeTransformer`), so is `freq` of a day or more, a `prefix` ending in `_` (joined with one) and a scalar `weights`. `"meeus"` ports astral's NOAA Solar Calculator equations (about 1e-11 degrees from `astral.sun.elevation(with_refraction=False)`); `"spencer"` is NOAA's fractional-year series with a 365-day year, the renewables study's `sun_sin_elev` (0.0 from its `SINEL`), up to ~0.5 degrees off near the equinoxes: only for reproducing the study. `locations` is normalised to a list of `[lat, lon]` lists (one bare pair accepted), so YAML round-trips.
- `RollingStatsTransformer(column, window_days=365, stat="max", lag_days=1, min_days=None, freq="1h")` adds `rolling_name()` = `{column}_roll{W}{stat}_d-{lag}` (no suffix for lag 0): the stat over the W calendar days ending D-lag of each **complete** day's stat (`DailyStatsTransformer`'s completeness: every slot of its 23/24/25 hours, one row on a daily frame), NaN where fewer than `min_days` days of the window are complete (pandas `min_periods` on the calendar-day series; None = W, so a window reaching before the frame or holding one incomplete day is NaN and the forecasts reading it are skipped, never a maximum of a few days). `min_days=60` is the study's `cap_proxy` to the bit on every day.
- `_daily.py`: `slots_in_day` is 1 for a slot of a day or more (a daily frame's spring day was 0 slots, so `DailyStatsTransformer(freq="1D")` left it NaN: fixed, hourly and 15-minute unchanged); `check_spacing` refuses rows all further apart than `freq` (plus an hour for daily slots, a DST day), called by the two 7e transformers only (`slot_of_day` refuses the other direction, rows off the grid).
- `information_set`: static built-in rules for the four solar names **exactly** (`_SOLAR_COLUMNS`, which a test holds equal to `COLUMNS`; no pattern, so a measured `x_is_night` or `cams_clear_sky_ghi` gets none); a prefixed transformer's exact names come from `source_rules`, which handles a `SolarGeometryTransformer` among its items, and `Workflow.run` passes `[*dp.sources, *dp.transformers]`. `installed_capacity_*` is `_CAPACITY` = `published("00:00", 7, timezone=None)` (both the delivery date and the instant in the data's zone), `latest_revision`: A68 is due a week before its year, so `_d+7` is known and `_d+8` late (not `static`, which let a long lead read next year's value; decision 8 amended by the 7e review); an `EntsoeSource` with that type, prefixed or not, gets `{prefix}installed_capacity_*` = `_capacity_rule(source._daily_zone())` (the same rule in its market's dates and clock, as A31's `week_zone`: a UTC or New York frame read the market's 1 January a day early under the data-zone default); `DailyStatsTransformer` calls `check_spacing` too. A prefixed `CalendarSource` copies only the rules equal to `_CALENDAR`. `_ROLLING` names resolve through `_built_from_name` like a day aggregate (a rule on the rolling name itself first, then the built-from column's whole resolution, so `generation_*` never catches `generation_solar_roll365max` at its row's hour; a user column named `load_roll24mean` is read as one too, a stricter verdict); `ResolvedColumn.window` is W. Judged at the last slot of the window's newest day (`_available_array`'s day-aggregate path) where no rule changes over time; under rules over time `_window_available` reads every day of the window as a day aggregate of the built-from column (through its own shifts and windows, so `x_d-5_roll10max` and `x_roll7max_roll10max_d-1` read what they hold), each day once over the span of the rows' windows, then a running maximum (`sliding_window_view`); for `as_of`/`weather_cutoff` rules each row's read-day offset (`issue - reached`) is a group of its own. `_delivered_span` starts W-1 days before the newest day (`explain`: `T-366 00:00 … T-2 23:00` for the proxy). Tests: `tests/data/transformers/test_solar_geometry.py`, `test_rolling_stats.py`, `test_daily_features.py` (the daily frame), `tests/test_information_set_generation_inputs.py`, `tests/models/test_generation_inputs.py`; mutants in `epftoolbox2-research/library_check_step7/generation_inputs/`.

## Known issues (don't fix as a side effect of other work)
- Open-Meteo `{prefix}_{col}_d+i` columns are shifted by `24h * i` in UTC (`open_meteo.py`, `_parse_weather_data`), not by local calendar days, so around each DST switch they point one hour off the model's targets (23 rows per switch per i). `shift_calendar_days` is the fix.
