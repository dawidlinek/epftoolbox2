# PseSource

Downloads Polish market and system data from the PSE reporting API v2 ([api.raporty.pse.pl](https://api.raporty.pse.pl)). **No API key required.**

Every PSE record carries a `publication_ts`, so the source can return each value **as it was known at a given issue time**: a value lands on a row of day D only if it was published by `issue_time` on D. This makes PSE data usable as predictors in backtests without look-ahead.

## Basic Usage

```python
import pandas as pd
from epftoolbox2.data.sources import PseSource

source = PseSource(
    series=["rce", "demand", "wind"],
    issue_time="11:30",      # forecasts are issued at 11:30 Europe/Warsaw on day D
    lags=[0, 1, 7],          # D, D-1 and D-7 (same local hour), as known at 11:30 on D
)

df = source.fetch(
    start=pd.Timestamp("2025-01-01", tz="UTC"),
    end=pd.Timestamp("2025-06-01", tz="UTC"),
)
# pse_rce, pse_rce_d-1, pse_rce_d-7, pse_demand (empty), pse_demand_d-1, pse_demand_d-7, pse_wind, ...
```

A typical pipeline uses one raw instance for the target and one as-of instance, with a **different prefix**, for predictors:

```python
from epftoolbox2.pipelines import DataPipeline
from epftoolbox2.data.sources import PseSource
from epftoolbox2.data.transformers import TimezoneTransformer

pipeline = (
    DataPipeline()
    .add_source(PseSource(series=["rce"], issue_time=None))  # target column pse_rce
    .add_source(PseSource(series=["rce", "demand", "wind", "solar"], issue_time="11:30", lags=[1, 2, 7], prefix="asof"))
    .add_transformer(TimezoneTransformer(target_tz="Europe/Warsaw"))  # required: the source's `timezone`
)
```

<Aside type="caution">
  Give the as-of instance its own prefix. With the same prefix, a raw `pse_rce` target and an as-of `pse_rce_d+1` column would collide with the target columns `pse_rce_d+1`, … that `ModelPipeline` creates, and two instances would produce duplicate column names. Neither is detected yet; both give wrong numbers without an error.
</Aside>

<Aside type="caution">
  The pipeline must convert the index with `TimezoneTransformer(target_tz=...)` set to the source's `timezone`. The source decides day D and the issue time in that zone; `ModelPipeline` takes D from the index. On a UTC index, the late-evening rows would belong to a different day than the source assumed, and some would see values published after their issue time.
</Aside>

## Parameters

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `series` | List[str] | Yes | - | Series to fetch (see below) |
| `issue_time` | str \| None | No | `"11:30"` | Local time `"HH:MM"` (in `timezone`) at which forecasts are issued on day D. Must be a string: quote it in YAML (`issue_time: "17:00"`), since unquoted `17:00` is read as a number. `None` returns raw values at delivery time, without any availability filtering |
| `lags` | int \| List[int] | No | `0` | Calendar-day offset(s) relative to D: positive = past, negative = future, `0` = D itself. Without `issue_time` only `0` is allowed |
| `as_of` | str | No | `"publication"` | Availability rule: `"publication"` (the record's `publication_ts`) or `"schedule"` (nominal publication times, see below) |
| `timezone` | str | No | `"Europe/Warsaw"` | Time zone that defines day D, the same local hour and the issue time. Must match `TimezoneTransformer(target_tz=...)` |
| `freq` | str | No | `"1h"` | `"1h"` (mean of the four quarter-hours; hours with a missing quarter are left empty) or `"15min"` (native) |
| `prefix` | str | No | `"pse"` | Column prefix (`{prefix}_{series}`); `""` for none |

## Series

| Series | API entity / field | Meaning | Unit | Published |
|--------|-------------------|---------|------|-----------|
| `rce` | `rce-pln` / `rce_pln` | RCE, PSE's market price of electricity (Rynkowa Cena Energii) | PLN/MWh | day before delivery |
| `csdac` | `csdac-pln` / `csdac_pln` | SDAC day-ahead price of the PL bidding zone | PLN/MWh | day before delivery |
| `demand` | `his-wlk-cal` / `demand` | KSE power demand | MW | after delivery |
| `wind` | `his-wlk-cal` / `wi` | Total wind generation | MW | after delivery |
| `solar` | `his-wlk-cal` / `pv` | Total photovoltaic generation | MW | after delivery |
| `generation_scheduled` | `his-wlk-cal` / `jg` | Generation of scheduling units (JGw, JGm, JGz, JGa) | MW | after delivery |
| `generation_non_balancing` | `his-wlk-cal` / `jnwrb` | Generation of units not active in the balancing market | MW | after delivery |
| `exchange_parallel` | `his-wlk-cal` / `swm_p` | Cross-border exchange balance, parallel (synchronous) | MW | after delivery |
| `exchange_non_parallel` | `his-wlk-cal` / `swm_np` | Cross-border exchange balance, non-parallel | MW | after delivery |

The data are quarter-hourly. Before 2025-10-01 the day-ahead market was hourly, so `rce` and `csdac` repeat the hourly price in each quarter. `rce` and `csdac` are different prices (they differ by a few percent). The `kse-load` report's `load_actual` is practically identical to `demand` and is not offered separately.

**History:** API v2 starts with business day **2024-06-14**. Rows before that date are empty and a warning is logged.

## As-of columns

With `issue_time` set, each lag `k` gives one column. The row is the issue day D (the local date of the row), exactly as in `ModelPipeline`, and the value is taken from the same local wall-clock time on another day:

| Lag | Column | Value on row (D, hour) |
|-----|--------|------------------------|
| `0` | `pse_{series}` | `series` at (D, hour), if published by `issue_time` on D |
| `k > 0` | `pse_{series}_d-{k}` | `series` at (D-k, hour), if published by `issue_time` on D |
| `-h < 0` | `pse_{series}_d+{h}` | `series` at (D+h, hour), if published by `issue_time` on D |

This matches the library's naming: `x_d-k` is x on D-k, `x_d+h` is x on D+h as known on D. Values published after the issue time are `NaN`, and a warning reports how many values each column lost.

Examples at `issue_time="11:30"`:
- `pse_rce` is filled: RCE for D is published around 14:00 on D-1.
- `pse_rce_d+1` is empty: RCE for D+1 appears around 14:00 on D, after 11:30. With `issue_time="15:00"` it would be filled on most days (with its own prefix, see above).
- `pse_demand` is empty: realised values for D are published on D+1. Use `lags=[1, ...]`.

Lags follow **local calendar days**, not 24-hour offsets. On the day after a DST switch, 10:00 takes 10:00 of the switch day. The spring switch day S has no 02:00, so lag `k` leaves 02:00 empty on day S+k (lag 7: a week later; lag -1: the day before S). Both 02:00 hours of the autumn switch day take 02:00 of the day before.

<Aside type="caution">
  Don't apply `LagTransformer` to as-of columns. It shifts by elapsed time and ignores publication times; ask the source for the lags you need instead.

  Keep as-of columns out of `ResampleTransformer`'s gap filling: it currently interpolates every `NaN` from the neighbouring values (the default `method="linear"`), which fills "not yet published" with later values. The source already returns hourly data with `freq="1h"`; if you resample other columns, list them in `ResampleTransformer(columns=[...])`.
</Aside>

<Aside type="caution">
  `NaN` predictors are not reported by `ModelPipeline`: a forecast whose predictors contain `NaN` is skipped, and training rows with `NaN` predictors are dropped, which silently shortens the training window. An empty or sparse as-of column therefore drops forecasts in blocks (see the re-publication periods below). Check how many forecasts each model produced, and compare models on identical forecast keys.
</Aside>

## `publication_ts` is the time of the last version

The API keeps only the **last version** of each record. When PSE re-publishes a day, its `publication_ts` moves to the re-publication time and the earlier version is gone. Publication times over the full history (2024-06-14 to 2026-09-24, checked in September 2026):

| Data | First publication | Re-publications |
|------|-------------------|-----------------|
| `rce`, `csdac` | D-1, median ~13:50 local; 99% before 15:15; latest 17:05 (`rce`) and 18:00 (`csdac`) | 3 RCE days re-published on D: 2024-06-26 13:06, 2025-10-23 12:34, 2026-03-04 08:05 |
| `his-wlk-cal` (demand, generation, exchange) | Unknown before 2026-01-18. Since then D+1 ~03:00 local; Feb–Apr 2026: 99% by 04:00; Jul–Sep 2026: ~5% of days later, up to 19:00 | **Every** business day from 2024-06-14 to 2026-01-17 was re-published on 2026-01-18; so were all of June 2026, 13 days of May 2026 and 4 days of July 2026 (weeks later) |

The two `as_of` rules handle this differently:

- **`"publication"`** (default): a value counts as known from its `publication_ts`. This never uses a value before it existed in its current form. But re-published values count as late: realised lags are **empty for every row before 2026-01-18** and for most of May–June 2026, and at 11:30 `pse_rce` loses two days (2024-06-26 and 2025-10-23).
- **`"schedule"`**: a value counts as known once a nominal time has passed — market results (`rce`, `csdac`) at 18:00 on D-1, realised values at 06:00 on D+1 (local Polish time) — **and**, wherever `publication_ts` is known, the actual (re-)publication has also happened by the issue time. The nominal time is only a fallback for when `publication_ts` is missing; a known, later `publication_ts` still makes the value unavailable. Because every realised record before 2026-01-18 carries a `publication_ts` (from the mass re-publication above, however late), `"schedule"` agrees with `"publication"` there: realised lags are still **empty for every row before 2026-01-18**. The nominal assumption only helps where the actual publication time is genuinely unrecorded.

<Aside type="note">
  Because re-publications move `publication_ts`, the `"publication"` output can change between downloads. Cache the data (`pipeline.run(..., cache=True)`) to keep an experiment reproducible, and clear `.cache/sources/` deliberately when you want fresh data.
</Aside>

## Not offered: PSE forecasts and balancing prices

PSE forecasts (for example `kse-load`'s `load_fcst`, the PK5L coordinated plan, `price-fcst`) also keep **only the last version**. The PK5L record for 2025-06-01 01:00, for instance, was last published at 21:52 that day. A backtest that uses them would see forecasts revised up to delivery, which is look-ahead, so this source doesn't offer them. The only way to backtest them is to record their vintages yourself over time.

Balancing (imbalance) prices are left out for the same reason: they are first published on D+1 and revised during settlement, often days or months later.

## Caching

`get_cache_config()` returns `source_type`, a `schema_version` and every parameter (`series`, `issue_time`, `lags`, `as_of`, `timezone`, `freq`, `prefix`), so changing any of them uses a separate cache.
