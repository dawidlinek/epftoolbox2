---
title: Information Set
description: Check, at the level you choose, that every predictor only uses data known at the time a forecast is issued
---

import { Aside, Tabs, TabItem } from '@astrojs/starlight/components';

A forecast issued on day D may only use values that are actually known at the moment it is issued, not
everything that ends up in the historical data. `epftoolbox2.information_set` declares when each column
becomes known and compares every expanded predictor (and the newest training target) with that boundary
before any model is fitted. What happens then depends on the [level](#three-levels) you choose.

A [predictor function of `ctx`](/epftoolbox2/model-pipeline/predictor-functions/) chooses each forecast's list with
`ctx.published()` and `ctx.value()`, which answer through these rules, and its lists are compared the same way, on the cells
each list reads.

**The convention:** a predictor's availability, including a raw, unshifted (lag 0) column such as `price`
used to forecast a different target, is decided purely by comparing its publication time to `issue_time`,
never by a fixed lag cutoff. This is independent of the model's own training-target boundary (the newest
training target is that of D-1 by default; a model with `newest_target="published"` reads it from the target's rule, see
[The newest target](/epftoolbox2/model-pipeline/time-and-calendars/#the-newest-target)). Changing one is not a side effect of
changing the other.

---

## Quick Start

```python
from epftoolbox2.pipelines import ModelPipeline

pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels")
```

`issue_time`/`issue_timezone` is a shortcut for `InformationSet(issue_time, issue_timezone)` with the built-in
availability rules. `InformationSet()` with no arguments issues at `11:45` `Europe/Brussels`, 15 minutes before the 12:00
CET gate closure of the day-ahead auction.

## Three levels

```python
from epftoolbox2.information_set import InformationSet
from epftoolbox2.pipelines import ModelPipeline

ModelPipeline()                                                          # none: no issue time, no checks
ModelPipeline(issue_time="11:45", issue_timezone="Europe/Berlin")        # warn: late predictors listed, run goes on
ModelPipeline(issue_time="11:45", issue_timezone="Europe/Berlin", availability="raise")  # raise: late predictors refused
ModelPipeline(information_set=InformationSet("11:45"), availability="raise")             # the same with your own rules
```

| `availability` | Default | A predictor (or the newest training target) known after the issue time | A column without a rule |
|---|---|---|---|
| `"none"` | without an issue time | Nothing is checked or listed | Nothing |
| `"warn"` | with an issue time or an information set | Listed, and the run goes on | Listed as `no rule`, whatever `unknown` says |
| `"raise"` | | `InformationSetError` before any fit | Follows `unknown` |

`"raise"` suits published results and CI. `"none"` with an issue time is allowed: nothing is listed, and the information set
still answers a [predictor function's](/epftoolbox2/model-pipeline/predictor-functions/#the-issue-time-check) `published()`.
`"warn"` or `"raise"` without an issue time or an information set raises `ValueError`, and so does an unknown level.

**The level doesn't change a number.** With fixed lists, forecasts and records are bit for bit the same at every level, and so
are those of a predictor function that passes `"raise"`, as long as it doesn't catch the error a late `ctx.value()` raises and
choose another list. The manifest doesn't compare the level, so changing only the level resumes a run. `pipeline.verify()` [tests the same boundary at every level](/epftoolbox2/model-pipeline/verification/#at-each-level):
a late predictor is a `leak` also where `run()` only lists it.

### What `"raise"` says

`ModelPipeline.run()` and `Workflow.run()` check every model's predictors before fitting anything:

```
OLS: 98 use(s) of inputs not known at the issue time (11:45 Europe/Brussels on the issue day D):
  - predictor load_actual: 'load_actual' is known 1h after the end of the period. Periods 10-23, horizons 1-7;
    e.g. load_actual for period 23 is known D+1 01:00, issued D 11:45.
Use values known by then (e.g. `x_d-1` instead of `x`), or, if a rule is too strict for your data, override it
with InformationSet(rules={...}).
```

### What `"warn"` lists

One `UserWarning` for all models before any fit, then a table at the top of what the run reports:

```python
from epftoolbox2.exporters import TerminalExporter
from epftoolbox2.models import OLSModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels")
pipeline.add_model(OLSModel(predictors=["load_actual", "price_d-1", "my_forecast_d+1"], name="OLS"))
pipeline.add_exporter(TerminalExporter())

report = pipeline.run(df, test_start="2024-01-01", test_end="2024-12-31", horizon=2)
print(report.availability().to_string(index=False))
```

```text
model       predictor      role  status list periods horizons                                 rule     known  issued note
  OLS     load_actual predictor    late       10-23      1-2 known 1h after the end of the period D+1 01:00 D 11:45
  OLS my_forecast_d+1 predictor no rule        0-23      1-2
```

| Column | Meaning |
|---|---|
| `model` | The model's name |
| `predictor` | The column |
| `role` | `predictor`, `training target` (the newest one is the value of D-1; with `refit` it is the value of the day before the refit day, checked at the issue time on the refit day, where the fit's rows are cut; a model with `newest_target="published"` has no such row, since what it trains on is known by construction), or what a predictor function read it with: `ctx.value`, `ctx.published` |
| `status` | `late` or `no rule` |
| `list` | The hash of the [predictor function's](/epftoolbox2/model-pipeline/predictor-functions/#results) list, which is listed per list. Empty for fixed lists and for what a function only read |
| `periods`, `horizons` | Exactly the uses of this row: a predictor used at other periods on other horizons gets one row per set of periods |
| `rule` | What the rule says, empty for `no rule` |
| `known`, `issued` | Relative to the issue day D, on the day and period it comes latest |
| `note` | An assumption or setting that would make it known in time |

The table is empty, with the same columns, when there is nothing to list. Otherwise the same rows are in three more places:

- **the warning**, up to five rows per model;
- **the terminal**: [`TerminalExporter`](/epftoolbox2/exporters/terminal/) prints them first, without `rule`;
- **the manifest** next to the results, under `availability`, with the level. So `ModelPipeline.report()` after array jobs, and
  a resumed run, show what the run listed, once. A resumed run lists what a fresh one does. A run over a narrower test period
  into the same directory keeps what was listed for the records it leaves out, unless the rules changed, in which case
  this run's rows replace them. A run at level `"none"` lists nothing in its own report and writes nothing there, but leaves what
  an earlier run wrote, unless the rules changed: results that were flagged don't read as clean because of how they were last
  resumed.

A column of a data source that needs the index in the market's zone raises `InformationSetError` at `"warn"` too (see below):
nothing true can be said about it.

### Reading a model's predictors: `explain`

`pipeline.explain()` shows what a forecast's predictors hold, relative to the target day T = D + horizon, and when each is known.
It is an optional view and has no effect on a later run. Suffixes are relative to the row's date D, so at horizon 2 `price_d-1`
is `T-3` and `x_d+2` is `T`:

```python
from epftoolbox2.models import OLSModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Warsaw")
pipeline.add_model(OLSModel(predictors=lear_names, name="LEAR"))

tables = pipeline.explain(df, model="LEAR", test=("2024-01-01", "2024-12-31"), horizon=1, hour=12)
tables["predictors"]  # one row per predictor
tables["grouped"]     # what it prints: runs of slots as one row
```

```text
LEAR: horizon 1, period 12 (12:00); T = D + 1; issued 11:45 Europe/Warsaw on D; issue days 2024-01-01 … 2024-12-31
                             predictor   target-relative                                               rule               known status
    price_h00_d-1 … price_h23_d-1 (24) T-2 00:00 … 23:00 published 13:00 Europe/Brussels on D-1 of delivery           D-2 13:00     ok
                     load_forecast_d+1           T 12:00 published 10:00 Europe/Brussels on D-1 of delivery             D 10:00     ok
load_actual_h00 … load_actual_h09 (10) T-1 00:00 … 09:00               known 1h after the end of the period   D 02:00 … D 11:00     ok
load_actual_h10 … load_actual_h23 (14) T-1 10:00 … 23:00               known 1h after the end of the period D 12:00 … D+1 01:00   late
                     price_day_max_d-1 T-2 00:00 … 23:00 published 13:00 Europe/Brussels on D-1 of delivery           D-2 13:00     ok
```

| Argument | Meaning |
|---|---|
| `model` | The model's name |
| `test` | (first, last) issue day to judge on; `None` takes every day of the data, for fixed lists only |
| `horizon`, `hour` | The forecast shown: days ahead, and the period of the target day (0-23, 0-95 for 15-minute data, 0 for a daily frame). `hour=None`, the default, is 12, or 0 at `"1D"` |
| `target`, `freq`, `echo` | Target column, `"1h"`, `"15min"` or `"1D"`, and whether to print |

At `"1D"` the header gives the time the rows are stamped at, `period 0 (12:00)`, and `target-relative` counts from it: `load_actual_h-1`
of a noon row is `T-1 11:00` at horizon 1 (see [Daily Rows](#daily-rows)).

`target-relative` reads the name the way the check does: a [profile](#profile-columns) at its slot, a [day
aggregate](#day-aggregates) over the whole day, an hour lag in elapsed time. On a DST day labels stay wall-clock times and
calendar days, and a day aggregate still ends at 23:00. An hour lag lands on another hour next to a switch, so across such a
window the label is the usual one and says how many days differ: `T-2 12:00 (else on 1 of 4 days)`. `status` is `ok`,
`late`, `late on 3 of 10 days`, `no rule`, `no issue time`, `not in data` or `no row` (a period no issue day of `test`
has, as on the day the clocks go forward), judged on every issue day of `test` with a row at that period, and
`known` is that of the day it comes latest, as an instant shown on the data's clock (see [Clock Changes](#clock-changes)). A
period the issue day doesn't have (02:00 on the day clocks go forward) is
noted under the table. On hourly data `_sNN` can be a slot of any length, so its time is `?`.

For a predictor function it shows [the distinct lists first](/epftoolbox2/model-pipeline/predictor-functions/#seeing-the-lists).

## Built-in Availability Rules

| Column | Available from | [Class](#vintage-classes) |
|---|---|---|
| `price` (ENTSO-E A44) | published ~13:00 Brussels on D-1 (within about 1h of the 12:00 gate closure) | `snapshot` |
| `price_exaa` (A44, `EntsoeSource(price_exaa=True)`, AT and DE_LU) | published 11:15 Vienna (Berlin for DE_LU) on D-1: one hour after the EXAA gate at 10:15 (legal bound, Art. 12.1.d; first seen about 10:35 in one check, unmeasured) | `snapshot` |
| `price` of an `EntsoeSource("CH", ...)` | published 12:00 Zurich on D-1: the legal bound for the Swiss auction (gate 11:00). Its first-seen time, about 11:05 to 11:30, is unmeasured: measure it before issuing at 11:45 | `snapshot` |
| `load_actual` (A65/A16) | 1h after the end of the delivery period | `latest_revision` |
| `load_forecast` (A65/A01) | published 10:00 Brussels on D-1 | `latest_revision` |
| `load_forecast_daily_min`/`_max` (A65/A31) | published Friday 10:00 Brussels for the whole following Monday-to-Sunday week of the data's local dates, each market's own (a bound `EntsoeSource` names its market's zone, see below) | `latest_revision` |
| `generation_*_forecast` (A69 wind/solar) | published 18:00 Brussels on D-1 (legal deadline, Reg. 543/2013 Art. 14(2)(d)) | `latest_revision` |
| `generation_*` (A75 actual generation) | 1h after the end of the delivery period | `latest_revision` |
| Calendar columns (`is_holiday`, weekday/month dummies, `sunrise`/`sunset`/`daylight_hours`, ...) | static, known in advance | none |

An `OpenMeteoSource` column's rule (below) is a `snapshot`, and so is an `EpftoolboxBenchmarkSource`'s `price`.

A31 holds one value per local date of each market's Monday-to-Sunday week, and every TSO publishes the next week on Friday two hours
before the 12:00 CET gate closure. So the built-in rule is `Availability.weekly("friday", "10:00", week_zone="data")`: the week is
read in the data's local dates, and the publication instant is 10:00 Brussels in every zone. On an hourly frame in Helsinki the first
hour of a Monday belongs to the week it starts, though it is Sunday in Brussels, and in Lisbon or Dublin the last hour of a Sunday to
the week it ends.

A frame in another zone than the issue time's (left in UTC, or at a fixed offset) still holds each value of the market's date: with
`DataPipeline(timezone=None)` Warsaw's Monday starts at 23:00Z on Sunday. There the week is read in the issue zone's dates too, and
the later of the two weeks counts, so it is never early. With the issue in the market's zone (`InformationSet("12:00",
"Europe/Lisbon")`) that is exact on any frame; with neither zone the market's, a Lisbon frame issued on Brussels time say, the last
hour of a Sunday is taken as published a week late. A rule from `with_source_rules` (below) or one of your own with `week_zone=` the
market's zone reads the market's week on any frame.

The day-ahead load forecast `load_forecast` (A01) keeps a Brussels day: it is the forecast of the day-ahead market's delivery day,
a CET day in every SDAC zone, so in Lisbon or Dublin the hour from 23:00 belongs to the next day's forecast, published on the day
before that. `load_forecast_h+35` on a noon row there is 23:00 on D+1, delivered on D+2 CET, and is late at a noon issue.

<Aside type="caution">
  A69 wind/solar's *legal* deadline (18:00 D-1) is after the day-ahead gate closure (12:00 D-1), and ENTSO-E
  gives no publication time per value, so the default rule is conservative and will flag `generation_*_forecast`
  predictors used same-day-ahead. Accept `assumptions=["entsoe_a69_by_10"]` to instead assume 10:00 D-1 (the
  same slot as the day-ahead load forecast). This is a documented assumption, not the default.
</Aside>

Column names are parsed the same way predictors are: `price_d-1` resolves to the base column `price` shifted
one calendar day back. There is no built-in default rule for weather columns, a `*_temperature_2m`-style
name alone doesn't say whether it's a forecast or an observed value. A `DataPipeline`'s sources refine the
check: `with_source_rules()` (called automatically by `Workflow`) teaches it about a `CalendarSource(prefix=...)`,
overrides the default week-ahead rule for an `EntsoeSource`'s own columns, and assigns a rule to exactly the
columns an `OpenMeteoSource` or an `EpftoolboxBenchmarkSource` emits:

- An `EntsoeSource` with `"load"` in `type` gets its own `load_forecast_daily_min`/`_max` rule (prefixed the
  same way as its other columns): published Friday 10:00 Brussels like the built-in one, for the week of the source's
  bound market zone (`EntsoeSource._daily_zone`, as `week_zone=`), the zone the value's local midnight is stamped at,
  rather than of the data's, so it holds on a frame left in UTC too. A neighbouring area combined into another market's
  `DataPipeline` (e.g. `EntsoeSource("FI", ..., prefix="fi")` inside `DataPipeline(timezone="Europe/Warsaw")`) is read on
  the market's week, not Finland's own, matching where the value is stamped.
- An `EpftoolboxBenchmarkSource` gets its rules on the files' own wall clock, its `index_timezone`: `price` published
  13:00 on D-1 and the two exogenous forecasts 10:00 on D-1. That index only labels the wall clock, one hour off the
  true instants in summer, so a Brussels rule would read the file's 23:00 on D as 00:00 on D+1 all summer.
- `weather_cutoff(source.run, f"{delay}h")`, `delay` coming from `publication_delay_hours(source.model)`, known
  `delay` after `source.run`:00 UTC on the issue day itself, unaffected by a leading `_d+k`. A shift after
  the leading `_d+k` moves the day the run is read from: `temperature_2m_d+1_d+1` (a `LagTransformer` with
  `lags=[-1]` on `temperature_2m_d+1`) holds the value of D+1 and is known only after D+1's run, so it is
  flagged, while `temperature_2m_d+1_d-1` comes from D-1's run. This is a conservative, model-side estimate of the run's real-world publication lag (ICON 4.5h, GFS 6.5h, ECMWF IFS 9h,
  JMA 9.6h, 10h for an unknown model): `OpenMeteoSource` itself has no notion of issue time or delay, only of
  the nominal cutoff `run`.

`run` and `model` are read with `getattr` and default when a source doesn't set them, so this works with any
`OpenMeteoSource`-like object.

An `OpenMeteoSource` column cut each local day D of its market zone off at D's own run. The check and the probe
read a row's issue day D from the data's index, so they need the index in that zone. On a UTC index (a pipeline
without `TimezoneTransformer`) the row at 22:00Z in summer belongs to the next day of `Europe/Warsaw`, whose run is
published only the next morning, and the check would read the wrong run. `check()`, `violations()` and
`leakage_probe` therefore raise `InformationSetError` when such a column sits on an index whose wall clock differs
from the source's market zone, and say to add a `TimezoneTransformer` (it takes its zone from
`DataPipeline(timezone=...)`). A zone with the same wall clock on every row, such as `Europe/Berlin` for a Warsaw
source, passes.

## Custom Rules and Assumptions

```python
from epftoolbox2.information_set import Availability, InformationSet

info = InformationSet(
    "11:45", "Europe/Brussels",
    rules={
        "fuel_ttf": Availability.daily_close("18:00"),          # a daily settlement price
        "my_forecast": Availability.published("09:00", days_before=1),
    },
    assumptions=["entsoe_a69_by_10"],
    unknown="raise",   # "warn" or "ignore" also accepted
)
pipeline = ModelPipeline(information_set=info)
```

## Vintage Classes

A rule says when a value was first out. A class says what the frame you backtest on holds of it, which is another question: the
archive of most series keeps only the newest revision, not the value a forecast saw on its issue day.

| Class | What the archive holds | Examples |
|---|---|---|
| `snapshot` | each value as published at a stated time | an auction's price, A69's 18:00 vintage, Open-Meteo's previous runs |
| `row_stamp` | every value with a trustworthy stamp of its first publication | PSE `pdgsz` |
| `last_write_stamp` | a stamp of each value's last write: it can tell a leak, but it is no vintage | other PSE tables |
| `latest_revision` | the newest value only | ENTSO-E A65, A69 `current`, A75, SMARD, Energy-Charts `current` |

The library has no source for PSE, SMARD or Energy-Charts yet: they are here to say what each class means, and a rule of yours for
such a column can carry its class.

```python
from epftoolbox2.information_set import Availability, InformationSet

info = InformationSet(rules={
    "de_wind_forecast_da": Availability.published("18:00", 1, vintage="snapshot"),
    "flows": Availability.realised("2h", vintage="latest_revision"),
})
```

A class decides no number: the check, the probes and every forecast are the same with it or without it. What it changes is how
far a backtest can be taken at its word. In one measurement (Germany, 2025, Energy-Charts), the TSO's own wind and solar forecasts
had an RMSE against actual generation 29–45 % lower in their latest revision than in their day-ahead vintage, with the vintages matched
by name only; what that does to a price model reading them was not measured. ENTSO-E's load was revised after the gate on 22 of 42
days. So a model that reads a `latest_revision` series can look more accurate in a backtest than it would have been live.

- A rule of yours has no class unless you give it one, and is shown as `unknown`. The [built-in rules](#built-in-availability-rules)
  have theirs, and a rule of yours for the same name replaces the class too.
- [`report.vintages()`](/epftoolbox2/model-pipeline/results/#vintage-classes-of-the-inputs) lists the class of every input of every
  model, and the [terminal exporter](/epftoolbox2/exporters/terminal/#output) prints the revised ones next to the availability
  listing. A run records them in its manifest as `vintages`, never compared on resume.
- Compared models that read one series with different classes [warn](/epftoolbox2/model-pipeline/comparing-models/#vintage-classes),
  and don't refuse: almost all usable history today is a latest revision.
- [`verify`](/epftoolbox2/model-pipeline/verification/#the-positive-control) calls a predictor function `inconclusive` when a
  `train_on="matching"` list reads a `latest_revision` or `last_write_stamp` column on a day it trains on.

None of this replays what was known then: that needs data with its vintages, which this library doesn't read yet. The classes make
visible what a backtest reads.

## Rules Over Time

A publication lag can change in the middle of a history. An observed example: PSE's settlement prices for the business dates from 14
September to 7 October 2026 were first out four days after the business date, at about 14:30, and from 8 October one day after it;
weekends varied. A list of rules with disjoint validity periods says so (the library has no PSE source yet):

```python
from epftoolbox2.information_set import Availability, InformationSet

info = InformationSet("11:45", "Europe/Warsaw", rules={
    "sk": [
        Availability.published("14:30", -4, "Europe/Warsaw").during(valid_until="2026-10-07"),
        Availability.published("14:30", -1, "Europe/Warsaw").during(valid_from="2026-10-08"),
    ],
})
```

- **Which rule.** A rule holds for the values whose day is in its period, both ends included: the day the value is delivered, a date
  of the rule's `timezone` for `published`, of its week's zone for `weekly` (`week_zone`, else its `timezone`), and of the data's
  zone for `realised`, `weather_run` and `static`. For
  `as_of` and `weather_cutoff` it is the day the value is read on, the issue day moved by a shift after a leading `_d+k`. So
  `sk_d-1` on 9 October holds 8 October's value, which the one-day rule describes.
- **Date a switch by delivery day.** The rules are read on the delivery day, so a period's dates are business dates, not
  publication dates. That is conservative when a lag shortens, as above, and exact when the switch is dated by delivery day. When a
  lag lengthens and you know only when publication slowed, the values delivered just before that day were published under the
  slower lag: start the slower rule early enough to cover them.
- **Outside every period** a value is never known: it is late, conservatively, and a gap between two periods is allowed. Two
  periods that share a day raise `ValueError`.
- **Everywhere alike.** The check, the listing (its `known` reads `never (no rule holds then)`), `ctx.published()` and
  `ctx.value()`, `explain`, `leakage_probe` and `newest_target="published"` all read through it. With the rules above, at 11:45 the
  newest known settlement price is that of D-5 up to issue day 11 October, though 8 October's value is out on the 9th, since 7
  October's comes only on the 11th at 14:30; from 12 October it is D-2.
- **Older values aren't implied.** With a rule that doesn't change, a value known on the issue day's row says every older one is
  known. Under rules over time an older value can come later (`sk_d-2` of 10 October is the 8th's, out on the 9th, while the row of
  the 8th, which a forecast at horizon 1 trains on, holds the 6th's, out on the 10th at 14:30). So for such a column the check reads
  every row the fits read, the training target on every target they read, and a day aggregate, or a daily row whose date reaches two
  delivery days of the rule's zone, on every slot of its day; `newest_target="published"` needs every target of its window known back
  to the oldest, and raises otherwise. With `refit` the rows are those of the refit day's fit, the forecast's own, judged as of the
  issue time of D. A row dated before the frame's first date doesn't exist and isn't judged, so a rule that starts on the frame's
  first date passes whatever the window. A use late on a training row is listed with a note that says so. Any other column is
  checked as before, and no slower.
- A single rule takes a period too, `Availability.realised("1h").during(valid_from="2024-06-13")`: before it nothing is known.
- In YAML the list is written as a list, and the new keys only when set, so a file without them is written back as it was:

```yaml
information_set:
  issue_time: '11:45'
  issue_timezone: Europe/Warsaw
  rules:
    sk:
    - kind: published
      time: '14:30'
      days_before: -4
      timezone: Europe/Warsaw
      vintage: last_write_stamp
      valid_until: '2026-10-07'
    - kind: published
      time: '14:30'
      days_before: -1
      timezone: Europe/Warsaw
      vintage: last_write_stamp
      valid_from: '2026-10-08'
```

`info.rules["sk"]` is then a `RuleChain`, the rules in the order of their periods.

**Unknown columns.** With `availability="raise"`, a predictor whose base column has no rule anywhere is, by default, a hard
error (`unknown="raise"`): a check that silently skipped columns it knows nothing about would report a pass it
cannot vouch for. Pass `unknown="warn"` to log instead, or `"ignore"` to skip silently once you've reviewed
which columns that affects. With `availability="warn"` such a column is listed as `no rule` and is no error, whatever
`unknown` says. `leakage_probe` and `verify` follow `unknown` at every level, because they can't perturb such a column.

## Profile Columns

A [`DailyProfileTransformer`](/epftoolbox2/transformers/daily-profile/) column holds one slot of its row's local
day, the same value on every row of that day: `price_h05` is the price of 05:00–06:00 on D, and `_s00` … `_s95` are
the quarter-hours of 15-minute data. The check and the probe judge it at that slot, not at the row's period, and
the shifts after the slot pick the day: `load_actual_h23_d-1` is 23:00 on D-1, and `load_actual_h23_h-12` reads the
profile of the row 12 elapsed hours earlier: D-1's on the rows before noon and D's from noon on, except on a DST day,
where that boundary moves to 11:00 in autumn and 13:00 in spring. A profile of a lag (`LagTransformer` before
`DailyProfileTransformer`) keeps its lag: `load_actual_d+1_h05` is the load at 05:00 on D+1.

A profile needs no rule of its own. It takes the whole resolution of the column it was built from: your rules, a data
source's rule, the built-in rules and accepted assumptions. So `price_h05_d-1` is judged by the rule of `price` and
`generation_solar_forecast_h12` by that of `generation_*_forecast`, not by `generation_*`, and a rule you write for a
column covers its profiles too. A key in `rules=` that matches the profile's own name comes first. It still describes
the series the profile was built from and is read at the slot:

```python
from epftoolbox2.information_set import Availability, InformationSet

info = InformationSet(
    "11:45", "Europe/Brussels",
    rules={
        "fuel_ttf": Availability.daily_close("18:00"),               # also fuel_ttf_h05, fuel_ttf_day_max, ...
        "price_h*": Availability.published("12:45", days_before=1),  # only the profiles of price
    },
)
```

With the built-in rules `load_actual_h05` (known 07:00 on D) passes at every period, and `load_actual_h23` (known
01:00 on D+1) fails at every period. On a DST day the skipped spring slot is NaN, and the repeated autumn slot holds
its first occurrence, as the transformer fills them. A `_d+k` after the slot always shifts the row, so `as_of`,
`weather_cutoff` and `weather_run` rules read `x_h05_d+1` from D+1 and never treat it as a source's own lead. An exact
key on a shifted name (`x_h05_d+1`) describes that very column at its row, as for any column.

<Aside type="caution">
  `_hNN` is read as an hour and `_sNN` as a quarter-hour, which on 15-minute data is all a two-digit `_sNN` can be. A
  profile with another slot length (`freq="30min"` on hourly data also gives `_sNN` names) cannot be told apart by
  name, so on an hourly model `_sNN` doesn't take the rule of its column and needs a key of its own in `rules=`. It is
  then read as a quarter-hour, which for such a profile is the wrong time.
</Aside>

## Day Aggregates

A [`DailyStatsTransformer`](/epftoolbox2/transformers/daily-stats/) column (`_day_min`, `_day_max`, `_day_mean`,
`_day_last`) holds a statistic of its row's whole local day, the same value on every row of that day, so it is known
only when the day's last slot is: 23:00 for hourly data and 23:45 for 15-minute data, on the 23- and 25-hour DST days
as on any other. The check and the probe judge it at that slot, not at the row's period, and the shifts after it
pick the day, as for profile columns: `load_actual_day_max_d-1` is the maximum of D-1, and
`load_actual_day_max_h-12` reads D-1's maximum on the rows before noon and D's from noon on, with the same boundary
of 11:00 on the 25-hour day and 13:00 on the 23-hour day.

An aggregate of a lag (`LagTransformer` before `DailyStatsTransformer`) keeps its lag, so `load_actual_d-1_day_max` is
also judged at the last slot of D-1. It is not the same column as `load_actual_day_max_d-1`, though. It summarises the
lagged column over the rows of D, so across a DST switch it isn't the maximum of D-1: on the day after the spring
switch the lag has no value for the skipped 02:00, the day is incomplete and the aggregate is NaN on all 24 rows, so
all of that day's forecasts are skipped (and reported), and on the day after the autumn switch it leaves out the second
02:00. Use `load_actual_day_max_d-1`, which lags the finished statistic and only misses its 02:00 row after the spring
switch.

An aggregate takes its rule as a profile does: a key in `rules=` that matches its own name first, then the whole
resolution of the column it was built from. With the built-in rules alone `price_day_max` (the expert model's maximum
price of D, published 13:00 on D-1) passes at every period, `load_actual_day_max` (known 01:00 on D+1) fails at every
period, `load_actual_day_max_d-1` (known 01:00 on D) passes, and `generation_solar_forecast_day_max` passes as the
forecast it summarises.

A `_d+k` after the aggregate always shifts the row, so `as_of`, `weather_cutoff` and `weather_run` rules read
`x_day_max_d+1` from D+1, while a `_d+k` before it (`temperature_2m_d+1_day_max`) stays the source's own lead.
`is_day_mean` and `warsaw_is_day_max` are never read as aggregates, whoever's rule covers them: they are an
`OpenMeteoSource`'s `is_day` averaged over locations.

A profile or aggregate of an `OpenMeteoSource` column also gets that source's `run` and its check that the index is in
the market zone. A key that matches the derived name replaces the source's timing but not the zone check, which only a
rule for the plain column itself lifts.

<Aside type="caution">
  The day's last slot can be delivered on the next day of the rule's zone. On an index at a true fixed offset
  (`Etc/GMT-1`) with Brussels rules, 23:00 is 00:00 CEST on D+1 in summer, so on summer days `price_day_max` of D is
  published only at 13:00 on D and is refused at every period, like `price_h23`. `EpftoolboxBenchmarkSource` is not
  such a case, although it uses that zone: its 23:00 is 23:00 on D of the files' wall clock, and its rules
  (`with_source_rules`) say so, so `price_day_max` and `price_h23` pass all year.
</Aside>

## Clock Changes

The check and the probe compare instants, not clock readings, so on a day the clocks change a value known after the
issue can't read as known before it:

- **Clock times in a rule** (`published("13:00")`, `as_of("09:00", ...)`, `weekly(...)`) are wall-clock times in the
  rule's own zone, converted at the instant they denote on that day. A time the clocks repeat is read at its second
  occurrence and one they skip at the switch, so a rule never reads earlier than it may be: `as_of("02:30")` on
  2024-10-27 in Warsaw is 01:30Z. A `weather_cutoff` run is a UTC hour: its rule is in UTC, `timezone=None` means UTC
  too, and any other zone raises. A `weekly` rule's week can be another zone's dates (`week_zone`), its publication time
  staying in `timezone`.
- **A period the clocks skip** (02:00 on the day they go forward) has no row, so it holds no value and gets no verdict:
  it is never late, `ctx.published()` is False there, and `explain` shows its status as `no row`.
- **Delays and period lengths are elapsed time.** When Warsaw's clocks go forward, the hour starting at 01:00 ends at
  03:00, so `realised(delay="1h")` makes it known at 04:00.
- **Shifts match `LagTransformer`.** A `_d` shift keeps the row's wall-clock time; `_h` and `_min` shifts are elapsed
  time. Several shifts apply from the end of the name: `x_d+1_h-24` is `x_d+1` of the row 24 elapsed hours earlier.
- **An issue time the clocks skip** is read at its earliest, so the issue is never later than asked: 02:30 Brussels
  on 2024-03-31 is 00:30Z. An issue time the clocks repeat is its first occurrence.
- **A row in the repeated autumn hour** is checked at its second occurrence, the row the model forecasts from. Times
  inside that hour are shown with their UTC offset, in messages, `report.availability()` and `explain`, because the clock
  alone can't order them: `known D 01:00 (UTC-05:00), issued D 01:30 (UTC-04:00)`.
- **A naive index** (after `DSTNormalizeTransformer`) is read in `issue_timezone` and shifted on its own wall clock,
  as `LagTransformer` does; its averaged repeated hour counts as the second occurrence. Normalise the data in that
  same zone: nothing can check a zone the index doesn't carry.
- **`ctx.published()` and `ctx.value()`** read the same instants, so a predictor function can answer otherwise on such a
  day than a clock reading would, and get another list there. A forecast is otherwise untouched: availability never reads
  a number.

## Daily Rows

A frame run with `freq="1D"` has one row per local date, stamped at the time of day the row stands for (see
[Daily frames](/epftoolbox2/model-pipeline/time-and-calendars/#daily-frames)). The stamp is read from the index. Each kind of
rule reads a daily row like this, with the rule's own clock times and delays as everywhere:

| Rule | Read on a daily row |
|---|---|
| `static` | Always known |
| `published`, `weekly`, with no `h`, `min` or `s` shift | The value of its whole local date, known when the date's last slot is: a date that spans two of the rule's delivery days (a Helsinki date against Brussels rules) is known when the later one is, whatever the stamp |
| `published`, `weekly`, with an hour shift | That hour, counted from the stamp |
| `realised`, with no `h`, `min` or `s` shift | The value of its whole local date, known `delay` after that date ends |
| `realised`, with an hour shift | That hour, counted back from the stamp |
| `weather_run`, `as_of`, `weather_cutoff` | As on an hourly row, from the stamp |
| A profile or a day aggregate | The column it was built from, at its slot or last slot, as on an hourly row |
| A `_sNN` slot | Needs a rule of your own, as on hourly data |

With `realised("1h")` and a noon stamp:

| Column | Holds | Known |
|---|---|---|
| `actual_daily_max` | The maximum of D | D+1 01:00: late at every issue time on D |
| `actual_daily_max_d-1` | The maximum of D-1 | D 01:00 |
| `load_actual_h-1` | The load of 11:00 to 12:00 on D | D 13:00: late at a 12:00 issue |
| `load_actual_h-2` | The load of 10:00 to 11:00 on D | D 12:00, which counts as known at a 12:00 issue |

A plain `realised` column is the date's value, not an hour's. Read from the stamp like `load_actual_h-1`, a daily maximum would be
known at 13:00 on its own date, when the date isn't over. That holds for the column named alone: what a profile or an aggregate is
built from is read at its slot, as on hourly rows. A plain `published` or `weekly` column is read the same way, at its date's last slot: a Helsinki date runs from 23:00 to 23:00 Brussels time, so read at a midnight stamp, `price_daily_max_d+1` under `published("13:00", 1)` would pass as known a day before D+1's prices are out. With `newest_target="published"`, `realised("1h")` on a daily target gives k = -1:
the newest training row at horizon 1 is D-2 (see [The newest target](/epftoolbox2/model-pipeline/time-and-calendars/#the-newest-target)).

<Aside type="caution">
  A frame stamped at midnight that holds what is true at noon hides the hour before noon: `load_actual_h-1` reads as 23:00 on D-1
  and passes. Restamp it to noon, as [Daily frames](/epftoolbox2/model-pipeline/time-and-calendars/#stamp-at-noon-not-at-midnight)
  shows. Neither the check nor `verify` can see this; a run warns when the stamp is at or near midnight and a predictor counts hours from it.
</Aside>

## Leakage Probe

`InformationSet.check()`, which `availability="raise"` runs, is a static analysis of predictor *names*, and
`InformationSet.late_uses()`, which `availability="warn"` runs, returns what it refuses. A model run tells both which rows its fits
read, `training_rows=TrainingRows(window, reach=0, to_issue=False, refit=None, first_day=None, members=())`, which matters only for a
column whose [rules change over time](#rules-over-time); a model passes the frame's first local date as `first_day`, before which no
row is judged, and with [`refit="auto"`](/epftoolbox2/model-pipeline/time-and-calendars/#refitauto) each training window's
`(window, rule)` as `members`, so that each window's own rows are judged and none between them. Called without it they judge the issue day's row alone, and say so in a warning for such a
column:

```python
from epftoolbox2.information_set import Availability, InformationSet, TrainingRows

info = InformationSet("11:45", "Europe/Warsaw", rules={"sk": [
    Availability.published("14:30", -4, "Europe/Warsaw").during(valid_until="2026-10-07"),
    Availability.published("14:30", -1, "Europe/Warsaw").during(valid_from="2026-10-08"),
]})
rows = TrainingRows(60)  # training_window=60; reach, to_issue and refit as the model's newest target and refit say
```

Both take `check_target=False`, which
leaves out the newest training target, as a model with `newest_target="published"` does: it trains on what
`InformationSet.newest_targets(target, freq, index, days, horizon)` says the target's rule calls known, period by period (see
[The newest target](/epftoolbox2/model-pipeline/time-and-calendars/#the-newest-target)). `leakage_probe` checks the same
boundary empirically, against real data and a real model:

```python
from epftoolbox2.information_set import leakage_probe

result = leakage_probe(model, data, run_day="2024-06-03", information_set=info, target="price", horizon=7)
result.assert_ok()  # raises AssertionError listing the forecasts that moved
```

It perturbs every value in `data` that is not known at `information_set`'s issue time on `run_day` (replacing
it with noise), runs `model` on the original and the perturbed data, and checks that every forecast issued on
`run_day` is unchanged. Any forecast that moves depends on information from after the issue time. Use it as a
regression test for a specific model and information set, alongside (not instead of) the static `check()`.

**`check_target_boundary=True`** additionally perturbs the target column for every row on or after `run_day`,
regardless of its own Availability rule: the model's own boundary (training targets end at D-1) is a deliberate,
conservative choice that can be stricter than a column's factual publication time, a day-ahead price, for
example, really is published before its own delivery day. A model with `newest_target="published"` trains on what the
target's rule says is known, D's prices for example, so for it the rule is the boundary: `check_target_boundary=True` raises,
and the probe perturbs what the rule calls unknown, as for any column.

**`rebuild`** catches a leak a transformer bakes into a derived column, which perturbing the already-built
column by its parsed name cannot see (a wrong shift moves the *right* raw value into the *wrong* row, and
that row's name still looks fine). Pass raw, pre-transform data as `data` and a callable that reproduces the
transformer pipeline:

```python
def rebuild(raw):
    df = raw.copy()
    for transformer in data_pipeline.transformers:
        df = transformer.transform(df)
    return df

result = leakage_probe(model, source_data, run_day="2024-06-03", information_set=info, rebuild=rebuild)
```

Perturbation is applied to the raw `data` by its own columns' availability, then `rebuild` is called on both
the original and the perturbed raw data before the model runs.

**`availability`** (default `"raise"`) is the level a predictor function is planned at. With `"raise"` a late `ctx.value()`
stops the probe with `InformationSetError`. With `"warn"` or `"none"` it returns the value, and the forecasts that read it are in
`changed` and `late_reads`.

**`positive_control`** tests the probe. A probe that finds nothing is evidence only if its perturbation reaches the
model, so this one perturbs the freshest values that *are* known, with `perturb_recent`, and reports which forecasts
moved. For a model with `newest_target="published"`, whose row of D-1 may train, it changes only rows dated D or later
(`perturb_recent(first_row_day=0)`). `ModelPipeline.verify()` runs both on sampled issue days and turns them into a verdict: see
[Verifying a Pipeline](/epftoolbox2/model-pipeline/verification/).

```python
from epftoolbox2.information_set import positive_control

control = positive_control(model, data, run_day="2024-06-03", information_set=info, target="price", horizon=7)
assert control.ok  # at least one forecast moved
print(control.moved, control.perturbed)
```

## YAML and the CLI

```yaml
model_pipeline:
  information_set:
    issue_time: "11:45"
    issue_timezone: Europe/Brussels
    assumptions: [entsoe_a69_by_10]
  availability: raise   # none, warn or raise; left out it is warn with an information_set, none without
  models: [...]
```

`save()` writes `availability` when you asked for a level, and leaves it out when you didn't, so a file made before the levels
existed loads with today's default. A file with an issue time and no `availability` therefore warns where it used to
refuse ([release notes](/epftoolbox2/reference/release-notes/)): add `availability: raise` to keep refusing.

`epf model` accepts `--issue-time HH:MM`, `--issue-timezone ZONE` and `--availability {none,warn,raise}`, which override
the YAML (or add an information set if the YAML has none):

```bash
epf model model_pipeline.yaml --data data.csv --test-start 2024-02-01 --test-end 2024-03-01 \
  --issue-time 11:45 --issue-timezone Europe/Brussels --availability raise
```
