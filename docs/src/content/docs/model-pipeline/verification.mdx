`InformationSet.check()` reads predictor *names*. A column can have a legal name and hold the wrong value, and a model
can read more than it declares, so a look-ahead can pass that check and give numbers that look fine.
`ModelPipeline.verify()` tests the boundary against real data and real models instead, including models whose lists come
from a [predictor function](/epftoolbox2/model-pipeline/predictor-functions/#the-issue-time-check).

```python
from epftoolbox2.models import OLSModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels")
pipeline.add_model(OLSModel(predictors=["load_forecast_d+1", "price_d-1", "is_monday_d+1"], name="OLS"))
pipeline.add_model(OLSModel(predictors=["is_monday_d+1", "is_sunday_d+1"], name="Calendar"))

verified = pipeline.verify(df, test_start="2024-01-01", test_end="2024-12-31", horizon=1, days=5)
print(verified.table().to_string(index=False))
verified.assert_ok()  # raises AssertionError naming what is wrong
```

```text
   model  days  forecasts  changed  max change  control moved  rerun  co_batch       status
     OLS     5        120        0         0.0            120   <NA>      <NA>           ok
Calendar     5        120        0         0.0              0   <NA>      <NA> inconclusive
```

`verify` probes the period you give it, not the windows of a run. After a run with
[validation](/epftoolbox2/model-pipeline/validation-and-test/), call it on the validation period and on the test period.

It needs an information set: without `issue_time` or `information_set`, `verify` raises `InformationSetError`.

---

## At each level

The [`availability` level](/epftoolbox2/model-pipeline/information-set/#three-levels) decides what `run()` does about a late input,
not where the boundary is, so `verify` tests the same boundary at every level. A late predictor is a `leak` also where `run()`
only lists it, and a pipeline whose `report.availability()` lists something is expected to fail here.

The one difference is a [predictor function](/epftoolbox2/model-pipeline/predictor-functions/#the-issue-time-check) that reads a late
`ctx.value()`. With `availability="raise"` that read raises `InformationSetError`, as in `run()`. With `"warn"` or `"none"` the function
gets the value, as in `run()`, and the forecasts that read it are a `leak`, whether or not the noise moved them, so the other
models still get their row. `verified.checks[i].probe.late_reads` counts those cells per column.

A predictor function is planned on the whole test period anyway, so at every level what it uses late on any issue day, in a list or
through `ctx.value()`, is a `leak` even if no sampled day reads it, and `verified.checks[i].late_in_period` names the columns.
`changed` can then be 0, since nothing was perturbed to see it.

A column without a rule can't be perturbed at any level: it follows `unknown` of the information set, as described below.

---

## What it does

For each model, `days` issue days are sampled with `seed` from the test period (from its days of the weekdays in `issue_days`, if you pass them).
Every model gets the same days, so they don't depend on which models you verify or in what order, and the same seed gives the same
table. On each day two experiments run, and two more for the models that need them (see
[Rerun and co-batch](#rerun-and-co-batch)):

| Experiment | What is perturbed | Forecasts must | Otherwise |
|---|---|---|---|
| Leakage probe | Every value not known at the issue time, and what the model trains on from the issue day on | not move | `leak` |
| Positive control | The freshest values that are known | move | `inconclusive` |
| Rerun | Nothing: the issue day runs twice, from other seeds | be the same, bit for bit | `inconclusive` |
| Co-batch | As the probe, in runs that also hold the other items of the issue day's call | not move | `leak` |

| Column | Meaning |
|---|---|
| `model` | The model's name |
| `days` | Issue days checked |
| `forecasts` | Forecasts compared, summed over those days |
| `changed` | Forecasts that moved under the probe, or exist in only one of its runs, or whose [predictor function](/epftoolbox2/model-pipeline/predictor-functions/#the-issue-time-check) read a cell the probe moved |
| `max change` | Largest move under the probe |
| `control moved` | Forecasts that moved under the control (missing with `positive_control=False`) |
| `rerun` | Forecasts that differ between two unperturbed runs (missing when the rerun didn't run) |
| `co_batch` | Forecasts that moved under the co-batch probe (missing when the check didn't run) |
| `status` | `ok`, `leak` or `inconclusive` |

`verified.ok` is true only if every model is `ok`, so an `inconclusive` model doesn't pass. `verified.problems()` gives
one line per thing that is wrong, and `verified.checks` holds each day's `leakage_probe` and `positive_control` result, and
its `rerun` and `co_batch` results where those ran.

Only copies of the models run, in memory, so `verify` has no effect on a later `run()`. Each issue day costs four one-day
runs per model (two for the probe, two for the control), six with `rebuild` or with the target among a model's predictors.
The rerun adds two, and the co-batch check runs the probe and the control once more, over the issue day's block and the other
days of its call.

A model with [`refit`](/epftoolbox2/model-pipeline/time-and-calendars/#refitting-on-a-calendar) fits once for every issue day of
its block, so a leak can need several days of a block in one run to show (a fit that read the block's last day, say). Its runs
therefore go from the issue day to the end of its block, or of the frame, and only that day's forecasts are compared: the same
number of fits as a one-day run, but every later day of the block forecast as well, up to 6 more days under `"7D"`, about a month
under `"1MS"` and up to a year under `"12MS"`. A predictor function is planned on those days too, and its reads are the issue
day's. `leakage_probe` and `positive_control` do the same.

### The probe

The probe is [`leakage_probe`](/epftoolbox2/model-pipeline/information-set/#leakage-probe): a value is replaced by noise
if its availability rule says it isn't known at the issue time on D. A forecast that moves used information from after
the issue time.

It also replaces the target from D on, whatever its rule says. A day-ahead price of D is published on D-1, so by its rule
it is known, but training targets end at D-1, so a model that reads or trains on it has crossed its own boundary. Reading
today's published price to forecast tomorrow is legal when a model declares it, among its predictors or as a feature built
from it such as `price_day_max`. Those inputs are judged by their rule, and what the model trains on still ends at D-1.

A model with [`newest_target="published"`](/epftoolbox2/model-pipeline/time-and-calendars/#the-newest-target) trains on every
target its rule says is known, so for it the rule alone is the boundary: the target is replaced where its rule says it isn't
known yet, like any column, and not from D on. A model that trains one day further than its rule allows moves, and is a `leak`.

### The positive control

A probe that finds nothing is evidence only if its perturbation reaches the model. The control perturbs the other side of
the boundary, one local day back, and the forecasts must move. A value is replaced if all of these hold:

- its availability rule says it is known at the issue time on D;
- it is delivered on D-1 or later, or first known on D-1 or later;
- it sits on a row dated D-1 or later;
- its rule isn't `static`, and it isn't missing.

So on D's row, for an issue at 11:45:

| Column | Holds | Replaced | Why |
|---|---|---|---|
| `price_d-1` | the price of D-1, published on D-2 | yes | delivered on D-1 |
| `load_forecast_d+1` | today's forecast for D+1, published at 10:00 on D | yes | delivered on D+1 |
| `load_actual_d-1` | the load of D-1 | yes | delivered on D-1 |
| `price_d-2` | the price of D-2, published on D-3 | no | older than D-1 on both counts |
| `is_monday_d+1` | a calendar value | no | never unknown |
| `load_forecast_d+2` | a forecast published on D+1 | no | not known yet: that is the probe's |

Moving the issue time back a day would not do: the price of D-1 was published on D-2, so it was known at 11:45 on D-1
already, and the commonest input of all would never change.

The target is never perturbed in what a model fits on, nor any row older than D-1. Every model trains on the target, so a
control that changed it would move every model and could never fail. For the same reason, with `newest_target="published"`, whose
row of D-1 may train, only rows dated D or later change (with `rebuild`, every built row before D is put back, while the source values
of D-1 still change, so `x_d-1` on D does). That is what makes it useful:

| Model | Control | Status |
|---|---|---|
| Inputs such as `price_d-1` or `load_forecast_d+1` | moves | `ok` |
| Only calendar inputs | doesn't move | `inconclusive` |
| Only inputs older than D-1, such as `price_d-7` | doesn't move | `inconclusive` |
| A fresh input in some periods only | doesn't move the others | `inconclusive` |
| Ignores the row it is given | doesn't move | `inconclusive` |
| A `rebuild` that doesn't read its argument | doesn't move | `inconclusive` |

The control asks this of every forecast: each (period, horizon) must move on at least one sampled day, and on every day
some forecast of each horizon must. One forecast moving says little about another, which may read other inputs. A sparse
model such as a Lasso can drop its fresh inputs for a period on a given day, so it may need more `days`.

`inconclusive` doesn't say a model leaks. It says this check can't vouch for it. A predictor function with an input that no
sampled day reads is `inconclusive`, until `days` covers it. These are `inconclusive` too:

- an input with no availability rule (with `InformationSet(unknown="warn")` or `"ignore"`, otherwise it raises), because a
  leak through it can't be seen;
- a horizon with no forecast on any sampled day, because nothing checked it;
- a predictor function that reads a column of [class](/epftoolbox2/model-pipeline/information-set/#vintage-classes)
  `latest_revision` or `last_write_stamp` through `ctx` on a day a
  [`train_on="matching"`](/epftoolbox2/model-pipeline/predictor-functions/#training-only-on-the-days-with-the-same-list) list
  trains on, on the sampled days or anywhere in the test period. The frame holds that value as revised later, not as it was out on
  that day, so a forecast's set of days can be one no live run would have chosen, and no probe can see it: the value is known by
  its rule either way. The line names the columns and their classes. A `snapshot` or `row_stamp` column, one without a class, a
  read on the issue day alone and a list that trains on every day are not affected.

`positive_control=False` skips the control, and then `ok` only says that no forecast moved.

### Rerun and co-batch

The probe compares two runs, so it trusts a model to give the same forecast twice, and it runs a model on the issue day (or its
refit block), so a forecast that reads another item of its call can show only if that item is in the run. Models that predict
several items in one call, such as an in-context model given every issue row of its refit block at once, or a zero-shot model
given a batch of issue days, can break either. Two checks test that:

- **Rerun.** The unperturbed issue day runs twice first, each run from other seeds of the process's global generators
  (`numpy.random`'s legacy one, which scikit-learn's `random_state=None` uses, `random`, and torch's if it is imported; their
  states are put back afterwards). Without that, both runs would fork their workers from the same state and a model drawing
  from them would give the same numbers twice. If any forecast differs at all (atol 0, not the probe's 1e-9), the model is
  `inconclusive` with the line `nondeterministic`, never `ok`. A forecast that moves under the probe or the co-batch probe on
  such a day can be its own noise: a move of up to 100 times that day's largest rerun difference (`verification.NOISE_MARGIN`)
  is `inconclusive`, a larger one a `leak`, judged day by day. A day whose two runs agree judges its moves as the probe does, and
  a rerun with a forecast missing from one run, or finite in one and not the other, bounds nothing: every move on that day is
  `inconclusive`. A late value a [predictor function](/epftoolbox2/model-pipeline/predictor-functions/#the-issue-time-check)
  reads is a `leak` whatever the noise: seeing it needs no comparison of forecasts. Verify a nondeterministic model on the CPU or
  with its deterministic settings. One draw the rerun can't see: a model that first imports torch inside a worker starts from
  torch's fixed default seed in both runs, so its draws agree; seed it from `random_state` (step 6's torch families do).
- **Co-batch.** The model names the other items of the call that predicts the issue day's forecasts (the other days of its
  refit block, the other days of its batch). The probe and the control run once more, over runs widened to cover those days, so
  that the call holds them, and only the issue day's forecasts are compared. The perturbation is the probe's: every value not
  known at the issue time on D, each row read as of its own issue day where that is later than D. So the other items' prices
  (the issue day's own future targets), their late inputs and a later row's weather forecast, which comes from that row's own
  run (`weather_cutoff`, `as_of`), change. What the information set calls known at D's issue time for that row stays, such as a
  forecast published days ahead on another item's row, a block's earlier days and every training row. A forecast that moves reads, through another item of its call, something it can't know: a
  `leak`. The plain probe misses it where the call is made of the run's own days, which holds the issue day alone in its runs. A
  model that reads known values of other items, a block's earlier days say, is no leak by this definition.

  A model that predicts its refit blocks in one call ([`_predict_block`](/epftoolbox2/reference/extending/#predicting-a-refit-block-in-one-call))
  gets one more comparison: its call holds the block's later days that the frame has, which a run on the issue day doesn't, so
  the issue day's forecasts are run again on the frame cut after its date and must be the whole frame's to the bit (within the
  rerun's noise margin, as any other move). A forecast that depends on how many rows its call holds, or which, though it reads
  no unknown value, is a `leak`: a backtest and a run on the day would give different numbers. A model that predicts each row
  on its own passes, since its call has one shape and the issue day's row the same place in both. The `co_batch` column counts
  the forecasts that moved either way, each once.

Both run by default for the models that need them: those that predict several items in one call (`_predicts_together`), name
the other items (`_co_batch_items`) or have a card (a family with an extra or weights). For every other model, which predicts
each forecast on its own and is deterministic, both are off by default and their columns are empty. A model with a card is
also checked first as `run` checks it: a missing extra, runtime package or weight file raises before any probe (see
[Licences and Weights](/epftoolbox2/models/licences-and-weights/)). `rerun=` and `co_batch=` turn them on or off for every model
verified:

```python
from epftoolbox2.models import RidgeModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels")
pipeline.add_model(RidgeModel(predictors=["load_forecast_d+1", "price_d-1"], refit="7D", name="Ridge"))

verified = pipeline.verify(df, test_start="2024-01-01", test_end="2024-12-31", days=5, rerun=True, co_batch=True)
```

A model that predicts each issue day on its own has no other item to add, so its co-batch check runs nothing and counts 0.
`device="cpu"` sets an attribute named `device` on every copy of a model that has one, for every run of the check, so a GPU
model is verified where it is deterministic; the models themselves keep their device. `verified.devices` names the models it
set, and a warning says so when no model verified has the attribute (every model of the core): then it changed nothing.

`leakage_probe`'s companion for one model and day is `co_batch_probe(model, data, run_day, information_set)` in
`epftoolbox2.information_set`, which is `leakage_probe(..., span=...)` over the named days.

<Aside type="note" title="For a model family">
  A class that predicts several items in one call sets `_predicts_together = True` and names them with
  `_co_batch_items(run_day)`, which returns the other issue days whose items share `run_day`'s call: the other days of its refit
  block, or of its batch. Name the whole call as the model forms it from the issue day alone, whatever the run's start, as a
  fixed-shape call is (a block on the refit calendar, a batch on a calendar of its own). A batch whose items share history,
  such as contexts of consecutive issue days, needs nothing more: only values unknown at the issue time change, so the history
  they share stays. A class that predicts together but names nothing is `inconclusive`. The shared checks every family passes
  are in `tests/models/adapter_suite.py`.
</Aside>

## Leaks in the data: `rebuild`

On a frame that is already built, a column only has its name to go by. A transformer that writes tomorrow's price into
`price_d-1` passes: by its name that column is known. To see it, give `verify` the source data and a function that
reproduces the transformers. The noise then goes into the raw columns, by their own rules, and through your code:

```python
from epftoolbox2.data.transformers import LagTransformer


def rebuild(raw):
    return LagTransformer(columns=["price"], lags=[1], freq="day").transform(raw)


verified = pipeline.verify(source_df, test_start="2024-01-01", test_end="2024-12-31", days=5, rebuild=rebuild)
```

Every numeric column of the source data needs a rule then, since nothing says which of them a model ends up using. The
source may be in UTC, as sources return it: days are those of the frame `rebuild` returns.

For a daily model (`freq="1D"`) whose `rebuild` cuts hourly source rows to one a date (`at_time("12:00")`), the source is perturbed by its hours, and the daily frame built from it is then perturbed as daily rows too, where a plain `realised`, `published` or `weekly` column is the value of its whole date (see [Daily Rows](/epftoolbox2/model-pipeline/information-set/#daily-rows)): a daily maximum the source repeats on every hour is a leak on its own date, though its early hours are known in time.

An input that stays the same whatever the source data holds isn't built from it, so a leak in it can't be seen, and the
model is `inconclusive`. If it really is known in advance, for example a column computed from the index, declare it:
`InformationSet(rules={"peak": Availability.static()})`.

## Limits

- **It checks the horizons you ask for.** `horizon` defaults to 1 and `run()` to 7, so pass the horizon you run, or `horizons=` with
  the list you run: a leak in another horizon can't be seen. With a list, a horizon it doesn't name is no blind spot.
- **It checks the weekdays you ask for.** Without `issue_days=` it samples every weekday and plans a predictor function on all of
  them. Pass the weekdays you run, and only those are sampled and planned: a column published weekly, which is late on a Monday, is
  no leak of a run on Fridays and is one of a run of every day (see
  [Some weekdays only](/epftoolbox2/model-pipeline/time-and-calendars/#some-weekdays-only)).
- **It samples.** A leak that exists only on some days shows up only if one of them is sampled. Run it on the days around
  a DST switch on their own: `pipeline.verify(df, "2024-10-26", "2024-10-29", days=4)`. See
  [Time and Calendars](/epftoolbox2/model-pipeline/time-and-calendars/#checking-it).
- **A model must be deterministic.** Two runs of a model with no fixed `random_state` differ, which shows up as a leak, or as
  `inconclusive` (`nondeterministic`) with the rerun check, the default for the models that need it.
- **It trusts your rules.** A rule that says a value is known earlier than it really is keeps that value out of the probe.
- **It can't see revisions.** A value in the frame revised after the issue day is known by its rule, so nothing perturbs it. A
  predictor function reading it can move its list or its [set of days](/epftoolbox2/model-pipeline/predictor-functions/#training-only-on-the-days-with-the-same-list) without a word.
  Where a rule's [class](/epftoolbox2/model-pipeline/information-set/#vintage-classes) says the archive is revised, a read on a
  day a `train_on="matching"` list trains on makes the model `inconclusive` (see the list above); a series you don't classify
  can't be told.
- **A day the model can't forecast at all stops it** with the reason, as `run()` does: `no forecasts produced`.

<Aside type="tip">
  Columns from an `OpenMeteoSource` or a prefixed source get their rules from the data pipeline:
  `ModelPipeline(information_set=InformationSet("11:45").with_source_rules(data_pipeline.sources))`. A `Workflow` does
  this when it runs, but `verify` only knows the information set you give it, and `epf verify` only the rules its YAML
  lists.
</Aside>

## From the command line

`epf verify` runs it on a ModelPipeline YAML and a CSV, and exits with code 0 only if every model is `ok`:

```bash
epf verify model_pipeline.yaml --data data.csv --test-start 2024-01-01 --test-end 2024-12-31
```

`--device cpu` runs every model that has a device on the CPU, and `--rerun`/`--no-rerun` and `--co-batch`/`--no-co-batch`
turn those checks on or off for every model. See the
[CLI reference](/epftoolbox2/getting-started/cli/#epf-verify-check-for-leaks) for its flags.
