The `ModelPipeline` class trains and evaluates forecasting models with rolling-window validation.

## Basic Usage

```python
from epftoolbox2.pipelines import ModelPipeline
from epftoolbox2.models import OLSModel, LassoCVModel
from epftoolbox2.evaluators import MAEEvaluator
from epftoolbox2.exporters import ExcelExporter, TerminalExporter

pipeline = (
    ModelPipeline()
    .add_model(OLSModel(predictors=predictors, name="OLS"))
    .add_model(LassoCVModel(predictors=predictors, name="LassoCV"))
    .add_evaluator(MAEEvaluator())
    .add_exporter(TerminalExporter())
    .add_exporter(ExcelExporter("results.xlsx"))
)

report = pipeline.run(
    data=df,
    test_start="2024-02-01",
    test_end="2024-03-01",
    target="price",
    horizon=7,
    freq="1h",                   # Optional. Allows sub-hourly testing like "15min"
    save_dir="results",
)
```

## Predictor Specification

Predictors can be specified in four ways:

<Tabs>
  <TabItem label="Static Columns">
    ```python
    predictors = [
        "load_actual",
        "load_actual_d-1",
        "price_d-1",
    ]
    ```
  </TabItem>
  <TabItem label="Templates">
    Use `{horizon}` placeholder: replaced with 1, 2, ..., horizon at runtime:

    ```python
    predictors = [
        "warsaw_temperature_2m_d+{horizon}",
        "is_monday_d+{horizon}",
        "is_holiday_d+{horizon}",
        "daylight_hours_d+{horizon}",
    ]
    ```

    <Aside type="tip">
      String templates are the only form compatible with YAML serialization. Use them instead of lambdas when saving pipelines with `save()` or `Workflow`.
    </Aside>
  </TabItem>
  <TabItem label="Callables">
    Callables receive `horizon` (1 param) or `(horizon, hour)` (2 params):

    ```python
    # horizon-only
    predictors = [
        lambda horizon: f"weather_d+{horizon}",
    ]

    # horizon + hour: different feature per hour of day
    predictors = [
        lambda horizon, hour: f"load_h{hour:02d}_d+{horizon}",
    ]
    ```

    <Aside type="caution">
      Callables cannot be serialized to YAML: `save()` raises a `TypeError` naming the model. If you need to save the pipeline or use `Workflow`, replace callables with `"{horizon}"` string templates.
    </Aside>
  </TabItem>
  <TabItem label="Function of ctx">
    A function with one parameter named `ctx` returns the whole list for one forecast, chosen by its horizon, period, day or whether an input is out at the issue time. See [Predictor Functions](/epftoolbox2/model-pipeline/predictor-functions/).

    ```python
    def by_period(ctx):
        x = ["price_d-1", "load_forecast_d+{horizon}"]
        if 6 <= ctx.period <= 20:
            x.append("generation_solar_forecast_d+{horizon}")
        return x
    ```
  </TabItem>
  <TabItem label="Loop Generation">
    Use list comprehensions for many features:

    ```python
    predictors = [
        "load_actual",
        *[f"load_actual_h-{i}" for i in range(1, 169)],
        *[f"price_d-{i}" for i in range(1, 8)],
    ]
    ```
  </TabItem>
</Tabs>

## Parallelism

Models use a **process pool**. Each worker process handles whole forecast days (24 hours × horizon), `THREADS_PER_PROCESS` tasks at a time, and runs each task's BLAS and OpenMP code on one thread, which it sets itself: `OMP_NUM_THREADS` and the like are not needed.

| Variable | Default | Description |
|---|---|---|
| `MAX_PROCESSES` | usable CPUs `// THREADS_PER_PROCESS` | Worker processes |
| `THREADS_PER_PROCESS` | `1` | Tasks each process runs at once, on threads |

```python
import os

# Read when a model runs; both optional
os.environ["MAX_PROCESSES"] = "4"
os.environ["THREADS_PER_PROCESS"] = "1"  # more only helps with the GIL off (free-threaded build, PYTHON_GIL=0)
```

See [Installation](/epftoolbox2/getting-started/installation/#parallel-model-training) for full setup including platform notes.

## Feature Scaling

Models scale each task's data with a scaler fitted on that task's training rows only. By default this is `StandardScaler`:

<Steps>

1. **Numeric features** are standardized (mean=0, std=1)

2. **Binary features (0/1)** are auto-detected and skipped

3. **Target variable** is scaled, predictions are inverse-scaled

</Steps>

Set a model's `scaler` parameter to `"asinh"` or `"npit"` to use a variance-stabilising transformation instead, which damps price spikes and handles negative prices. See [Scalers and VSTs](/epftoolbox2/models/scalers/).

## Run Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `data` | DataFrame | Required | Input data with DatetimeIndex |
| `test_start` | str | `None` | Test period start; or `test` |
| `test_end` | str | `None` | Test period end; or `test` |
| `target` | str | `"price"` | Target column name |
| `horizon` | int | `7` | Max forecast horizon (days) |
| `freq` | str | `"1h"` | Forecasting frequency (e.g., `"15min"`) |
| `save_dir` | str | `None` | Directory for incremental results |
| `forecast_only` | bool | `False` | Skip evaluators/exporters. `test_start`/`test_end` default to `"today"` if omitted |
| `validation` | tuple \| str | `None` | Validation period `(start, end)`, or `"previous_year"`. Alone it forecasts only those days. See [Validation and Test](/epftoolbox2/model-pipeline/validation-and-test/), and [Ensembles](/epftoolbox2/model-pipeline/ensembles/) for what can choose on it |
| `test` | tuple | `None` | Test period `(start, end)`, the same as `test_start` and `test_end`; giving both raises |

Model names must be unique: they name the result files in `save_dir`.

## Data Checks

Before any model is fitted, `run()` checks every model's input and raises `ValueError` with a description of the problem:

- **Resolution:** rows must be `freq` apart, with one row per local day and period (hour, or quarter-hour for `freq="15min"`). Only the hour repeated when clocks fall back may occur twice. Data finer than `freq` would put the issue day's prices into the training set. Resample it first (`ResampleTransformer`) or pass the matching `freq`. Gaps (missing days, periods or scattered rows) are allowed, but rows off the `freq` grid are not, and neither is more than a day of rows evenly spaced at a multiple of `freq`, e.g. hourly prices before 15-minute ones with `freq="15min"`: that would train the quarter-hour periods on far fewer days than the full hours. The spacing is checked only on the days a run can read, from `test_start` minus `training_window + horizon + 1` days to `test_end` plus `horizon + 1` days, so hourly history before the switch doesn't block a run that stays inside the 15-minute part. If the run does reach it, bring those rows to one grid with `ResampleTransformer(freq="15min")` or shorten the training window. Duplicates and several rows in one slot are refused anywhere in the frame.
- **Timestamps:** no duplicates. Rows are sorted by time.
- **Names:** the data must not contain the model's target columns (`{target}_d+1` … `{target}_d+{horizon}`, e.g. from a `LagTransformer` with negative lags on the target) or columns named `hour` or `day`, which the model uses internally (use `CalendarSource(prefix=...)` for its `hour` column).
- **Predictors:** every expanded predictor (for every hour and horizon) must exist, be numeric, and must not be one of the model's targets.

Only the target and the predictors are used, so other columns (e.g. text columns such as `holiday_name`) can stay in the data.

## Information Set

The checks above don't know *when* a forecast is issued, so they can't tell a legitimate lag from look-ahead
(same-day `load_actual` passes them, even though it isn't known until after the hour it describes). Pass
`issue_time` to `ModelPipeline` to add that check:

```python
pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels")                       # listed
pipeline = ModelPipeline(issue_time="11:45", issue_timezone="Europe/Brussels", availability="raise")  # refused
```

Before any fit, a predictor (or the newest training target) not known at issue time is listed in `report.availability()`, a
warning, the terminal exporter and the manifest, and the run goes on. With `availability="raise"` it raises
`InformationSetError` instead. The rules are built in for the shipped sources (ENTSO-E prices/load/generation,
Open-Meteo weather, calendar). See [Information Set](/epftoolbox2/model-pipeline/information-set/) for the
levels, the full rule reference, custom rules, `pipeline.explain()` and the empirical `leakage_probe`, and
[Verifying a Pipeline](/epftoolbox2/model-pipeline/verification/) for `pipeline.verify()`, which runs it on sampled
issue days.

## EvaluationReport

The pipeline returns an `EvaluationReport`:

```python
report.summary()           # Overall metrics, with a `forecasts` count per model
report.forecast_counts()   # Planned vs produced forecasts and skip reasons
report.availability()      # Inputs not known at the issue time or without a rule
report.by_hour()           # Breakdown by hour
report.by_horizon()        # Breakdown by horizon
report.by_hour_horizon()   # Combined breakdown
```

See [Working with Results](/epftoolbox2/model-pipeline/results/) for what the counts mean.
