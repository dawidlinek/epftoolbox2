When training models over long test periods, epftoolbox2 can save intermediate results and resume if interrupted.

## Enabling Incremental Training

```python
report = pipeline.run(
    data=df,
    test_start="2024-01-01",
    test_end="2024-12-31",
    save_dir="results",  # Enable incremental saving
)
```

## How It Works

1. Each task (date × hour × horizon × model) is saved after completion
2. If the script is interrupted, re-running loads completed tasks
3. Only missing tasks are computed

On one machine a resumed file is bit for bit a fresh run's. On another, the linear algebra library (BLAS) rounds sums differently, so
records can differ in their last digits, by up to about 3e-9 EUR/MWh for [`LEARModel`](/epftoolbox2/models/lear/#kernels) on the
benchmark data: resume where a file was started if it must be one machine's. A resume on the other backend of LEAR's kernels warns.

## Cache Directory Structure

Each model gets a results file (a directory with [Parquet results](#parquet-results)) and a manifest next to it, and a lock file that a run holds while it writes them:

<FileTree>

- results/
    - ols.jsonl
    - ols.manifest.json
    - ols.lock
    - lasso.jsonl
    - lasso.manifest.json
    - lasso.lock

</FileTree>

A second run into the same model's results, from another process or the same one, raises `ResultsLockedError` naming the lock
file at once, before it reads or writes anything: two writers would put two forecasts on one key. The lock is the operating system's
(`flock`), so a run that is killed holds none. On a file system that refuses locks the run warns and goes on, and nothing then stops
a second writer: run one writer per model's results there. The empty `.lock` file stays in the directory.

## Results File Format

Each line of `<model>.jsonl` is a JSON object, written as UTF-8. A forecast:

```json
{"run_date": "2023-04-12", "target_date": "2023-04-13", "run_weekday": 2, "hour": 3, "horizon": 1, "day_in_test": 0, "prediction": 72.41, "actual": 70.84, "coefficients": [0.16, -0.75, 0.65, -0.25], "freq": "1h", "status": "ok", "list_hash": "6fc96c3892ad", "refit_anchor": "2023-04-12", "revision": 1}
```

and a key that has none, a **skip record**:

```json
{"run_date": "2023-04-12", "target_date": "2023-04-13", "run_weekday": 2, "hour": 4, "horizon": 1, "day_in_test": 0, "prediction": null, "actual": 71.02, "coefficients": [], "freq": "1h", "status": "missing_test_predictors", "list_hash": "6fc96c3892ad", "refit_anchor": "2023-04-12", "revision": 1}
```

Every record ends with four keys, after the ones before them, which keep their order and values:

- `status`: `"ok"` for a forecast, the [skip reason](/epftoolbox2/model-pipeline/results/#forecast-counts) for a key without one
  (`missing_test_predictors`, `missing_test_row`, `not_published`, `too_few_rows`, `no_finite_training_rows`, `no_matching_days`,
  `fit_error`).
- `list_hash`: a hash of the forecast's predictor list and its training rule, for a fixed list the one a
  [predictor function](/epftoolbox2/model-pipeline/predictor-functions/#results) returning that list gets.
- `refit_anchor`: the date of the fit the forecast came from, its own `run_date` without `refit`.
- `revision`: 1 for every record a backtest writes.

A skip record has the key fields, `prediction` null, `actual` the target of the row the forecast would have been issued from (null
when there is no such row), `coefficients` empty, the four keys, and `detail` where the reason has one (`"window 56"`: the member of a
[training window list](/epftoolbox2/model-pipeline/training-windows/) that failed). Records a run keeps in memory, without `save_dir`,
are the forecasts alone. An [ensemble](/epftoolbox2/model-pipeline/ensembles/)'s records end with `status` and `revision` only.

A record also has `window` in a run with [validation](/epftoolbox2/model-pipeline/validation-and-test/) (its `day_in_test` counts from
the start of that window), `predictor_list` for a predictor function, `member_predictions` for a training window list, and a model with
[`refit`](/epftoolbox2/model-pipeline/time-and-calendars/#refitting-on-a-calendar) has `refit_anchor` after `freq`, where it always
had it.

**What is read.** Every table, count, ensemble and exporter reads the forecasts alone: records with `status` `"ok"`, or without
`status` (written before it). **Code that reads the lines of a results file itself must do the same**: keep the records whose
`status` is `"ok"`, and take a record without `status` as one, or skip records come in with `prediction` null. Per key
`(hour, horizon, run_date)` the highest `revision` counts, and within it a forecast counts over skip records. A forecast repeated with
the same numbers (equal but for the four keys, so an old line and a new one of one forecast are one) is read once, with a warning; a
key with two different forecasts raises `ValueError` naming the file and a key, since they are two configurations' forecasts and no
table may pick one: two runs that wrote one file at once, or files joined by hand. The per-window skip counts of
`report.forecast_counts()` come from the manifest, as before. Files written before these keys resume and report as they did, and a
file holding both kinds reads as one.

**Resuming.** A task is done by its `(hour, horizon, run_date)`, the actual calendar date, not the `day_in_test` offset from
`test_start`, so extending or shifting `test_start` between runs into the same directory can't make an unrelated date look already
computed. A key is done when the record a reader takes for it is a forecast: a skipped key is tried again by every run, and gets a new
skip record only when its reason changed, so resuming again doesn't grow the file. What a run writes for a key whose records reach a
higher `revision` gets that revision, so that it is the record read.

**A crash while writing** can leave the last line half-written. Reading skips it with a warning, and the next run into the file cuts
it off, with a warning naming its bytes, before it appends: its key is forecast again, and the file ends as a fresh run's would. A line
that isn't a record anywhere else raises `ValueError` with its line number, if it is read: a damaged line that a later record replaces
(a lower `revision`, or a skip record under a forecast) isn't parsed, so it isn't reported, while the line read for a key, and a line
repeating it, raise with their line numbers. A file replaced while it is read (an ensemble's, rewritten by every `report()`) is read as
it was when opened; one written in place meanwhile raises.

**The lock** is taken on a lock file the run can't write as well (another user's, in a shared directory), since `flock` needs no
write access; only a lock file that can't be opened at all counts as a file system that refuses locks (on NFS, where `flock` is
emulated by an `fcntl` lock that needs write access, such a run warns). Pool workers don't inherit it,
so a worker outliving a killed run doesn't keep the next run out.

<Aside type="tip">
  For long training runs, use `save_dir` to avoid losing progress if the script crashes or is interrupted.
</Aside>

## Parquet Results

For studies of thousands of models, `save_format="parquet"` writes each model's results as a directory of Parquet files in place
of `<model>.jsonl`. The records are the JSONL records, read by the same rules, so every table and count is the same to the last
bit; JSONL stays the default and defines the record. On 10,000 models over a year of hourly forecasts (87.6 million records, no
coefficients) Parquet results take 1.2 GB where JSONL takes about 26 GB, a model's year is read in under 10 ms where JSONL takes
about 110 ms, and `report.summary()` over all 10,000 models takes under two minutes.

```python
report = pipeline.run(
    data=df,
    test_start="2024-01-01",
    test_end="2024-12-31",
    save_dir="results",
    save_format="parquet",      # results/<model>.parquet/
    save_coefficients=False,    # optional: coefficients written as [], everything else as it is
)
```

<FileTree>

- results/
    - ols.manifest.json
    - ols.lock
    - ols.parquet/
        - _catalog.jsonl
        - year=2024/
            - part-20241231T101500-3f2a9c1d-000001.parquet

</FileTree>

- **Parts.** Records are buffered per year of their `run_date` (converted to columns in the background as they come) and written
  as a part (zstd, rows sorted by `run_date`, `hour`, `horizon`) when a buffer reaches 200,000 rows, is 5 minutes old, and when the
  run ends; the environment variables `PARQUET_ROWS_PER_PART`, `PARQUET_FLUSH_SECONDS` and `PARQUET_MAX_BUFFERED_ROWS` (1,000,000,
  all of a writer's buffers together) change those.
- **The catalog.** A part is written under a temporary name, synced and renamed, and only then gets its line in `_catalog.jsonl`
  (file, rows, bytes, first and last run date, its sha256, and a CRC-32 of the line). Readers read the parts the catalog lists and
  nothing else, so a crash leaves at most an orphan file that no reader sees: the next run forecasts its keys again, `epf results
  verify` reports it and `epf results compact` removes it. A catalog line a crash left half-written is skipped with a warning and
  cut off by the next writer, as a JSONL line is.
- **The same records.** One column per record key (dates as dates, `hour`, `horizon`, `revision` as small integers, `prediction`
  and `actual` as float64, `coefficients` and `member_predictions` as lists of float64, `freq`, `window`, `status` as dictionary
  strings), and a column `_keys` with each record's keys in their order, so that a record converts both ways exactly: its keys in
  its order, a `null` where it had one and no key where it had none, floats bit for bit. A record with a key the schema has no
  column for raises when it is saved, rather than losing it.
- **The same rules.** One record per key `(hour, horizon, run_date)`, the highest `revision`, a forecast over skip records, the first
  forecast in catalog order; forecasts alone by default; a repeat with the same forecast warns, one with another raises. Resuming,
  the lock (`<model>.lock`, the same file for both formats), skip records and the manifest work as for JSONL. The manifest records
  `save_format: "parquet"`, as provenance.
- **One format per model.** A run with `save_format="jsonl"` into a `save_dir` where a model has Parquet results raises before any
  fit, and the other way round, naming the command that converts them. [Array tasks](/epftoolbox2/workflow/overview/#slurm-arrays-one-model-or-a-block-per-task)
  write Parquet with `model_pipeline.save_format: parquet`, and `report()` / `epf report` read either format.
- **Coefficients.** `save_coefficients=False` writes `coefficients` as `[]`, as a training window list's records have them, and
  changes nothing else: no table reads them. A study of 10,000 models over a year of hourly forecasts with 140 coefficients a record
  is 271 GB of JSONL.

Three commands work on a `save_dir` (`--model NAME` for one model):

```bash
epf results convert results --to parquet   # or --to jsonl: every record, compared before the old results are removed
epf results compact results                # each (model, year)'s parts into one; orphans and superseded parts removed
epf results verify results                 # catalog CRCs, part checksums, orphans, repeated keys; exit 1 on an error
```

`convert` takes each model's lock, writes the new results beside the old ones, reads them back and compares them record for record
with the old ones before removing those and recording the format in the manifest, so JSONL converted to Parquet and back gives the
same lines byte for byte. `compact` keeps every record, in its order, and compacting twice changes nothing. An ensemble's file is
always JSONL: every run and report computes it again.

Reading the parts with another tool (pyarrow, DuckDB, polars) gives every record of the committed parts: keep the files the
catalog lists and no later line supersedes, and apply the rule above (the highest `revision` per key, `status` `"ok"`), or skip
records and superseded revisions come in.

---

An [ensemble](/epftoolbox2/model-pipeline/ensembles/#results-on-disk-and-slurm-arrays) has a results file and a manifest next to its members', but it is never resumed: both are recomputed from the members' results every time.

## The Manifest

`<model>.manifest.json` records what produced `<model>.jsonl`: the model class and its hyperparameters (all
of them: whatever the model returns from its `_model_kwargs`), the predictors' per-`(period, horizon)`
order (not just which names are used: a reordering changes what stored coefficients mean, and a hash of
the ordered layout tells `["price_d-1", "price_d-2"]` apart from `["price_d-{horizon}"]`), target, horizon,
freq, training window (an int, `"expanding"` or a [list](/epftoolbox2/model-pipeline/training-windows/#resuming-and-yaml) as normalised), a content hash of the data columns used up to `test_end` (rows after `test_end`
don't affect any forecast in this run, so appending them between runs isn't a mismatch), and the data's own
time zone (converting the same instants to a different zone keeps the same hash, since it's over each
value's own representation, not the zone label), and how the training rows are chosen (`training_cut`): everything that defines what
a forecast in the file actually *is*. A manifest without `training_cut` was [made with counted rows](/epftoolbox2/model-pipeline/time-and-calendars/#results-made-with-counted-rows)
and is refused; results accepted anyway are marked unverified, for good. It also records provenance (package version, git SHA if available, when it was first and
last written, and for [`LEARModel`](/epftoolbox2/models/lear/#kernels) the backend of its kernels, `kernels`, a list once a resume
used the other, whose two agree within 1e-9 and not to the bit, so a resume warns while a file mixes them) and the
[information set](/epftoolbox2/model-pipeline/information-set/) settings, but neither is compared: a
version bump or a new commit does not by itself invalidate a results directory, and the information set
gates which predictors are allowed before fitting rather than changing what a fitted model predicts.
A run that reads an input with a [vintage class](/epftoolbox2/model-pipeline/information-set/#vintage-classes) records each
input's class as `vintages`, never compared either; a run whose inputs have none has no such key. A resume under the same
information set keeps the rows of inputs only an earlier run read, and under other rules this run's rows replace them.

Before resuming, the pipeline compares a manifest built from the current run to the one on disk. If they
disagree, it raises rather than silently mixing forecasts made under two configurations:

```
ManifestMismatchError: OLS: the results in results were produced with a different configuration than this
run (ols.manifest.json):
  - predictor_layout_hash: '9c2c1f...' (existing results) vs 'a71e08...' (this run)
Resuming would silently mix forecasts made under two configurations. Use a different save_dir, remove the
existing results, or pass allow_manifest_mismatch=True (`epf model --allow-manifest-mismatch`) to overwrite
the manifest and resume anyway.
```

```python
report = pipeline.run(
    data=df,
    test_start="2024-01-01",
    test_end="2024-12-31",
    save_dir="results",
    allow_manifest_mismatch=True,  # overwrite the manifest and resume anyway
)
```

A [predictor function of `ctx`](/epftoolbox2/model-pipeline/predictor-functions/#results) has no fixed list to compare: resuming compares each stored forecast's list and binary columns with what a fresh run would give it, and each record stores its list's hash.

Every run also records `column_hashes`, a hash of each column it reads (its predictors, the target and what a predictor function reads through `ctx`) on its own, with numbers as float64, and `frame_hash`, a hash of the whole frame, over the same rows up to `test_end`. They never refuse a resume, so a change in a column the run doesn't read still resumes. They are what an [ensemble](/epftoolbox2/model-pipeline/ensembles/#what-is-refused) compares between its members. Manifests written before them load, and an ensemble then warns.

These hashes describe the frame of the last run. Where resuming didn't compare it with what the stored forecasts read, on an override with `allow_manifest_mismatch=True` that accepted other data or on results with no manifest, the manifest also records `data_unverified: true`, for good, and an ensemble warns by name.

A run with [validation](/epftoolbox2/model-pipeline/validation-and-test/#resuming) adds to the manifest its windows and segments (`windows`), a digest of the binary columns per window (`binary_masks`, under each list for a function, a test mask under the key a plain run gives it) and a hash of the target up to the last day a stored `actual` reads (`actuals`). A plain run's manifest has none of them, except `binary_masks` for fixed lists where a column with no value on the test's first day was [read on a later day](/epftoolbox2/models/scalers/#binary-columns) and that changed its mask: results of such a run whose manifest has no digests were scaled before that rule, and resuming them raises `ManifestMismatchError` ("the scaling rule changed"). Resuming compares each stored forecast's window and mask with what a fresh run would give it, and the data on what the stored forecasts read, so a run with a test period can follow one with only a validation period.

A model with [`refit`](/epftoolbox2/model-pipeline/time-and-calendars/#refitting-on-a-calendar) adds `refit` (such as `"7D"`) and
`refit_epoch` (`"1970-01-05"`) to `training_cut`, and only then, so changing `refit` raises `ManifestMismatchError`. Its manifest has
no `binary_masks`, as a fit's mask is read from its own rows, which the data hash covers. Resuming compares each stored forecast's
`refit_anchor` with the one a fresh run would give it, for fixed lists too. A fit with pending forecasts is made again and only the
pending forecasts are written: they are bit for bit a fresh run's.

A model with an [`"expanding"` window](/epftoolbox2/model-pipeline/training-windows/#expanding) (alone or in a list) adds `expanding_from`, the frame's first local date, to `training_cut`, so a resume with a frame that starts on another day raises.

**A `.jsonl` file with no `.manifest.json` next to it** is not
a mismatch: by default it is accepted with a warning, and a manifest is written from then on. Pass
`require_manifest=True` to refuse them instead, if you want the stricter guarantee for every results
directory you resume into:

```python
report = pipeline.run(..., save_dir="results", require_manifest=True)
```

<Aside type="caution">
  A `training_window`, `refit`, predictor list, model hyperparameter, or the data itself changing between runs into
  the same `save_dir` raises by default. Moving `test_start` does not. Moving `test_end` does in a plain run, since the data
  hash reaches up to it; a run with [windows](/epftoolbox2/model-pipeline/validation-and-test/#resuming) may go on past where
  the stored forecasts end.
</Aside>
