A live pipeline is judged on what it delivered, a day at a time. The raw error of a month says little about it: when prices swing
wider, every model's RMSE rises and the benchmark's rises more. In the S02 pipelines the RMSE of a German price forecast rose 41 %
from August to September while its skill against naive d-1 improved. So `ModelPipeline.monitor` leads with **skill**, the ratio of
a member's MAE to a benchmark's on the keys both have, and reports every number with how many forecasts stand behind it.

```python
from epftoolbox2.ensembles import FallbackEnsemble
from epftoolbox2.models import NaiveModel, OLSModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = (
    ModelPipeline(issue_time="11:45", issue_timezone="Europe/Berlin")
    .add_model(OLSModel(predictors=["price_d-1", "load_forecast_d+{horizon}"], training_window=364, name="OLS"))
    .add_model(NaiveModel(predictors=["price_d-1"], name="naive"))
    .add_ensemble(FallbackEnsemble(["OLS", "naive"], name="live"))
)
monitored = pipeline.monitor(data, "live/de_price", windows=(7, 30, 90), benchmarks=["naive"])
print(monitored.tables())          # one row per (window, member), skill first
print(monitored.alerts)            # the rules that fired
```

`data` is the frame the pipeline forecasts from, refreshed (a `DataPipeline.run`): a live record has no actual at issue, so the
actuals come from it. The pipeline needs its information set (`issue_time=`), whose rule for the target says when each actual is
out. `monitor` writes nothing: it reads the live directory (`live.json`, `issues.jsonl`, `delivered.jsonl`, the members' records
and each revision's `quality.json`) and the clock.

| Parameter | Default | What it does |
|---|---|---|
| `data` | required | The frame the actuals come from, with the `target` column |
| `save_dir` | required | The live directory; a backtest's raises `LiveDirectoryError` |
| `windows` | `(7, 30, 90)` | Numbers of issue days; each window ends at the newest due issue day |
| `benchmarks` | `None` | Names of members to measure skill against; `None` takes the pipeline's `NaiveModel`s |
| `policy` | `"latest"` | Which committed revision of an issue day each key is read from: `"latest"`, `"first"` or `"delivered"` |
| `cutoff` | `"deadline"` | Which revisions are seen at all: those committed by the deadline `live.json` records (as for `ModelResultRef`) |
| `backtest` | `None` | An `EvaluationReport` (or a mapping of member to frame of forecasts) of the same pipeline over the same days, for the live/backtest skill ratio |
| `alerts` | `None` | A list of rules, or the path of a YAML file holding one (see [Alerts](#alerts)) |
| `target` | `"price"` | The column the actuals are read from |
| `issue_days` | `None` | The weekdays the pipeline issues on, as for `run` (`["friday"]`); `None` takes `live.json`'s, else every day. Only those are due |

Every model and ensemble of the pipeline that has results in the directory is a member; the others are listed in
`monitored.missing`.

## What is scored

- **A key's actual** is what a run's `actual` is: the target's value at the same wall-clock period `horizon` local days after the
  issue day. On the autumn switch day the repeated hour has two prices and no run scores it, so it is not scored here either; the
  skipped spring hour has no forecast to score. A day of 23 or 25 hours is scored over the periods the clock has, as in every
  report.
- **A key is scored once its actual is known by now.** The target's rule (`Availability.published("13:00", 1)` for a day-ahead
  price: out at 13:00 on the day before it) is read on the clock (`epftoolbox2.clock`), whatever the frame holds. A forecast issued
  at 11:45 for tomorrow is scored from 13:00 today; the keys of horizon 2 wait for tomorrow's 13:00. Forecasts not yet scored are
  counted in `unscored`.
- **Two kinds of day**, as `LossPanel` has them. An *issue day* is a run date: `days_<b>`, `wins_<b>`, `participation` and every alert's `for_days` count those, and a day's loss is the mean over its horizons of their MAEs. A *curve* is one issue day at one horizon, the delivered forecasts of one target date: `rmse_daily`, `level`, `shape` and `partial_days` are over curves. The error of a key is `prediction - actual`.
- **The data's zone.** A record's date and period are in the zone of the data it was made on (the members' manifests' `data_timezone`). `data` is converted to it (the same instants), so a frame in UTC or London time gives the same report; a naive frame, or manifests that name different zones, raise.
- **Windows** are the last `n` calendar issue days up to the newest *due* one. An issue day is due once its deadline has passed
  on the clock (once the day has ended when `live.json` records no deadline: today never counts), only on the weekdays the pipeline issues on, and no day before the directory's first call counts.
  A window longer than the directory is as long as the directory.

## The tables

`monitored.tables()` has one row per (window, member); `monitored.by_window()` cuts it by window. Its columns, in order:

| Columns | Meaning |
|---|---|
| `window`, `member` | The window in issue days, and the member |
| `skill_<b>`, `common_<b>`, `days_<b>`, `wins_<b>` | Per benchmark `b`: the member's MAE over the benchmark's on the keys both have (below 1 beats it), how many keys, how many issue days, and those on which the member's loss is lower |
| `backtest_skill_<b>`, `live_vs_backtest_<b>`, `matched_days_<b>`, `matched_keys_<b>` | With `backtest=`: see [Against the backtest](#against-the-backtest) |
| `forecasts`, `unscored` | Forecasts scored, and forecasts of the window whose actual isn't known yet (or doesn't exist) |
| `check_failed`, `check_failed_days` | Keys and issue days the member's checks before export turned into `check_failed` skip records: out of its keys and of the common keys. See below |
| `mae`, `rmse`, `rmse_daily`, `bias` | On the member's own scored keys: MAE, RMSE pooled, the mean of the days' RMSEs (the arena's convention), and the mean error |
| `level`, `shape`, `partial_days` | See below; and the curves with fewer scored forecasts than their target date has periods (23 of 24 is partial; a 23-hour day with 23 isn't) |
| `issue_days`, `committed_days`, `participation` | Due issue days in the window; those with a revision committed before the deadline; their share |
| `delivered_days`, `delivered` | Due issue days with a delivery recorded (`mark_delivered`), and their share |
| `member_days` | Issue days the member has a forecast on |
| `fallback_days`, `skipped_days`, `fallback_mae` | For a `FallbackEnsemble`: issue days a rung above 0 served, issue days no rung served, and the MAE of the keys a rung above 0 served |
| `quality_records`, `quality_days` | Days with a `quality.json`, and of them days that record a missing or imputed cell or a source that didn't refresh |

**Skill is on common keys.** `skill_naive` of a member is its MAE over naive's on the keys where both have a forecast and an
actual, and `common_naive` says how many. A model that skipped a key the benchmark made is not compared on it, and its own
`mae` is on all of its keys: the two numbers have different samples by design, and each says its count. All of it goes through the
same `LossPanel` as the comparison tables of a report.

**Level and shape split the error.** `level` is the mean over days of |the day's mean error|: what the forecast got wrong about the
whole curve, such as a load or weather input shared by every model. `shape` is the MAE after removing each day's mean error: what
it got wrong inside the day. A constant error of 5 a day has level 5 and shape 0; an error of +4, -4, +4, ... has level 0 and shape
4. Per day, mean|e| is at most |mean e| plus the mean of |e - mean e|, so with days of equal size `mae <= level + shape`.

**Checks before export.** A member's day that failed its checks has no forecasts, so it leaves the member's own score and every common key it would have been in: a model's worst days can drop out of its own skill. `check_failed` and `check_failed_days` count them per window, and `tables()` warns and sets `attrs["check_failed"]` to the keys per member. To judge what was delivered, read the `FallbackEnsemble`'s row and `rungs()`.

**Participation does not depend on the policy.** `participation` counts the days with any revision committed before the deadline,
and `delivered` the days with a delivery before it, whichever `policy` reads the forecasts: a day the pipeline failed to deliver
is a missing day in the window, not a day left out of it.

### Policies

Each issue day has revisions (every call that changed anything commits one, see [Live records](/epftoolbox2/model-pipeline/caching/#live-records)).
`policy` picks the one each key is scored from:

- `"latest"`: the newest committed by the deadline: what a reader of the directory sees by default.
- `"first"`: the first committed by it: how the forecast did before any revision improved it.
- `"delivered"`: up to the newest revision recorded as delivered; a day with no delivery has no forecasts. The revision must have been committed by the cut-off, but **when its delivery was recorded does not matter** here (deliveries happen between the forecast deadline and the market's gate, or are marked later from a receipt), and so for `delivered` and `delivered_below`. `ModelResultRef(policy="delivered")` and `LiveStore.visible`, which live readers need, keep asking for a delivery recorded by the cut-off.

An uncommitted revision, or one committed after the cut-off, is never read.

## Fallback rungs

`monitored.rungs()` reads each `FallbackEnsemble` under all three policies and gives, per window: the `rung`, the ladder's member at
it (`rung_member`), the `days` (issue days with a key it served) and `forecasts` it served, its `share` of the planned days, and the `scored` forecasts and their
`mae`. A row with `rung` -1 and `rung_member` `"skipped"` counts the days no rung served: a committed day on which a planned horizon has no forecast from any rung, or one short of its planned periods (no curve to deliver, as `forecast()` says `skipped`). A fallback is known the day it is issued; its MAE waits for the actuals. `fallback_mae` in the table scores the days a
rung above 0 served, so a late input shows as days on a lower rung with a worse MAE, never as a better-looking average.

## Input quality

`monitored.quality()` has one row per issue day with a committed revision, from the `quality.json` of the revision the policy reads:
`record` (whether it has one), `missing_cells`, `imputed_cells`, the columns with either, the sources that didn't refresh, and
`problem`. `quality_days` in the table counts the problem days of the window.

## Against the backtest

A live pipeline is the one that was backtested. With `backtest=` (the report of that pipeline over the same days, or a mapping of
member to a frame with the forecast keys, `prediction` and `actual`) each member gets, per benchmark:

```python
monitored = pipeline.monitor(data, "live/de_price", windows=(30,), benchmarks=["naive"], backtest=backtest_report)
print(monitored.tables()[["member", "skill_naive", "backtest_skill_naive", "live_vs_backtest_naive", "matched_days_naive"]])
```

`backtest_skill_<b>` is its skill in the backtest, `live_vs_backtest_<b>` the live skill over it, both on the **forecast keys** (run date, target date, hour, horizon) where the live window and the backtest both have the member and the benchmark (`matched_keys_<b>` of them, on `matched_days_<b>` issue days): one sample on both sides, however far the backtest reaches beyond the window. A backtest equal to the live forecasts gives exactly 1. Where there are no matching keys the columns are NaN. A ratio near 1 says the live pipeline performs as its backtest did; much above 1 says something in production
differs. Absolute errors are not compared: the periods differ.

## Alerts

`alerts` is a list of mappings, each with one rule key, or the path of a YAML file holding the list:

```python
from epftoolbox2.results.monitor import load_alerts

rules = load_alerts("alerts.yaml")
monitored = pipeline.monitor(data, "live/de_price", alerts=rules)
for alert in monitored.alerts:
    print(alert.rule, alert.member, alert.message)
```

```yaml
- skill_above: 0.8            # member MAE / benchmark MAE above 0.8 on each of the last for_days issue days
  for_days: 3                 # default 1: consecutive due issue days; a day without a score breaks the run
  member: OLS                 # optional: every member but the benchmarks
  benchmark: naive            # optional: every benchmark
- participation_below: 0.9    # the share of the window's issue days with a revision committed before the deadline
  window: 30                  # default: the first window
- delivered_below: 0.9        # likewise with a recorded delivery
- rung_at_least: 1            # a fallback ensemble's day served by rung 1 or worse on each of the last for_days days (a skipped day is worse than any)
  member: live
- stale_input: load_forecast  # the column's last valid timestamp is more than age days before the issue day's midnight
  age: 1                      # a finite number from 0; default 1
  for_days: 1                 # on each of the last for_days issue days with a quality record
```

Each alert that fires is an `Alert` in `monitored.alerts` with its `rule`, `message`, `member`, `benchmark`, observed `value`,
`threshold` and `through` (the last issue day it looked at); no alert is an empty list. The rules read the report as it is:
`skill_above` the skill of each issue day, `rung_at_least` every key of the days up to the newest due one, scored or not,
and `stale_input` the quality records (a record that doesn't name the column says nothing about it). A key the rule doesn't know
raises, so a typo never silently disables an alert. `epf monitor experiment.yaml --windows 7,30,90 --alert alerts.yaml` ([CLI](/epftoolbox2/getting-started/cli/#live-commands-forecast-refit-mark-delivered-status-monitor-snapshot)) prints the tables and exits 3 when an alert fires, 0 otherwise.
