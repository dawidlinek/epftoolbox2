`T0Model` and `ChronosModel` forecast the target from its own history and its covariates' with pretrained weights:
[t0-alpha](https://huggingface.co/theforecastingcompany/t0-alpha) (The Forecasting Company, 102 M parameters) and
[Chronos-2](https://huggingface.co/amazon/chronos-2) (Amazon, 120 M). They read series, not predictor columns: `context` local
days of the target and the base columns you name as `known_ahead` (known through the end of the target day at the issue time,
such as the TSO load forecast) and `past` (known up to now, read over the context only). Each forecast is the median of the
model's quantiles. `T0Model` is zero-shot or fine-tuned from the base weights on a calendar (`fine_tune_every`, yearly by
default); `ChronosModel` is zero-shot. Both share the base class `FoundationModel`, which three more families build on, all
zero-shot: `PatchTSTFMModel` ([PatchTST-FM-r2](https://huggingface.co/ibm-granite/granite-timeseries-patchtst-fm-r2), IBM, 385 M,
univariate), and two whose weights carry **flagged licences**, `TimestralModel`
([Timestral](https://huggingface.co/mistralai/Timestral-209M), Mistral AI, 209 M / 123 M / 28 M, a revenue cap) and
`TimesFMModel` ([TimesFM-3.0](https://huggingface.co/google/timesfm-3.0-pytorch), Google, 331 M, non-commercial); see
[the flagged families](#patchtst-fm-timestral-and-timesfm-3).

In the research behind this library (`recent` DE_LU and AT, test year 2025-10 to 2026-09, issued at 11:45 the day before the
target day),
zero-shot t0-alpha with the load forecast and a 364-day context had a test MAE of 20.15 EUR/MWh on DE_LU (LEAR's window average
20.89), a monthly re-fine-tune of it over three seeds 18.96 and 16.33 on DE_LU and AT, and Chronos-2 with a 182-day context 20.56
and 17.33. Alone they are about as good as LEAR's window average (17.78 on AT); the fine-tuned t0 is a member of the research's
best clean ensembles. Timestral-209M with the load forecast and a 364-day context was the best single model of the research's
zoo (18.48 and 15.90, though possibly contaminated: see its card), TimesFM-3 19.79 on DE_LU and PatchTST-FM-r2, univariate,
19.85 and 16.51.

## Installing

Each family is an extra of its own, imported when a model first forecasts: the classes import, save to YAML and load without it,
and a run's pre-flight names a missing extra (or missing weights) before any model fits.

```bash
pip install 'epftoolbox2[t0]'            # T0Model: tfc-t0 0.5.0, torch, huggingface_hub
pip install 'epftoolbox2[chronos]'       # ChronosModel: chronos-forecasting 2.x, torch
pip install 'epftoolbox2[patchtst-fm]'   # PatchTSTFMModel: granite-tsfm 0.3.x (Python < 3.14), torch < 2.12
pip install 'epftoolbox2[timesfm]'       # TimesFMModel: timesfm[torch] 3.0.2
pip install 'epftoolbox2[timestral]' \
  'timestral @ git+https://github.com/mistralai/timestral@a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff'   # TimestralModel
```

- **`tfc-t0` is pinned to 0.5.0.** Its git head moved single hours of the research's forecasts by up to 161 EUR/MWh, so the
  version (and a VCS commit, if any) is in the manifest and a resume with another one is refused.
- **Python 3.11 to 3.15 with the GIL.** Every family loads safetensors, which has no free-threaded wheel: on 3.14t the extras
  don't install. `[patchtst-fm]` needs Python 3.13 or older (granite-tsfm's own limit).
- **The timestral package is not on PyPI.** Its extra installs its PyPI dependencies (torch, safetensors, huggingface_hub), and
  the package itself comes from the commit the research ran, `a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff`, as above. The
  pre-flight reads the commit pip recorded (PEP 610's `direct_url.json`) and refuses another one, or a build not installed from
  the repository, naming this command; see [Timestral's runtime](#timestrals-runtime).
- **granite-tsfm pins torch below 2.12 and scikit-learn below 1.8.** The lock resolves `[patchtst-fm]` apart (`uv sync` refuses
  it together with `[torch]`; it brings its own torch), so no other extra and no core install moves; an environment with it
  runs scikit-learn 1.7.
- **torch.** The lock and `uv sync` take the CPU build. For a GPU, install a CUDA build first (for example
  `pip install torch --index-url https://download.pytorch.org/whl/cu126`), then the extra.

## Basic usage

```python
from epftoolbox2.information_set import InformationSet
from epftoolbox2.models import ChronosModel, T0Model
from epftoolbox2.pipelines import ModelPipeline

pipeline = (
    ModelPipeline(information_set=InformationSet("11:45"))
    .add_model(T0Model(known_ahead=["load_forecast"], fine_tune_every=None, name="t0_zero_shot"))
    .add_model(T0Model(known_ahead=["load_forecast"], name="t0_yearly"))  # fine-tuned every 1 January, 3 seeds
    .add_model(ChronosModel(context=182, known_ahead=["load_forecast"], name="chronos2"))
)
report = pipeline.run(df, "2025-10-01", "2026-09-30", horizon=1, save_dir="runs/foundation")
```

## Parameters

| Parameter | Default | What it is |
|---|---|---|
| `context` | `364` | Local days of the target's history a forecast reads (T = days x periods per day steps) |
| `known_ahead` | `()` | Base columns read over the context and the steps ahead, known through the end of the target day |
| `past` | `()` | Base columns read over the context only, NaN after their own newest known step |
| `fine_tune_every` | `"12MS"` (`T0Model`) | A refit rule whose anchors fine-tune (`"12MS"` every 1 January, `"1MS"` monthly), or `None` for zero-shot |
| `seeds` | `3` (`T0Model`) | Fine-tunes per anchor and horizon, their medians averaged |
| `fine_tune` | the research's recipe | The fine-tune's settings, merged over the defaults (below) |
| `random_state` | `0` | The base seed of every fine-tune (each seed's from a hash of it, the anchor, the horizon and the seed's number) |
| `batch_size` | `64` | Items per backend call, every call padded to it; compared on resume |
| `device` | `"auto"` | `"auto"`, `"cpu"`, `"cuda"` or `"cuda:N"` |
| `weights` | `None` | The card's weights from the cache, or a file or directory used as given |
| `newest_target` | `"d-1"` | Where the target's context (and a fine-tune's targets) end: D-1, or `"published"` where the rule says |
| `name` | `"t0"`, `"chronos2"`, `"patchtst_fm"`, `"timestral"`, `"timesfm3"` | The model's name |
| `size` | `"209m"` (`TimestralModel`) | Which Timestral: `"209m"`, `"123m"` or `"28m"`, each with its own weights and card |
| `symmetric_averaging` | `True` (`TimestralModel`) | Average the forecast with the reflected forecast of the negated context (the package's default) |
| `clip_nonnegative` | `False` (`TimestralModel`) | Clamp the forecast at 0 where the context has no negative value (off: prices can be negative) |
| `runtime_commit` | `None` (`TimestralModel`) | Another commit of the timestral package to run on instead of the pinned one ([below](#timestrals-runtime)) |

`ChronosModel`, `TimestralModel` and `TimesFMModel` take the same but `fine_tune_every`, `seeds`, `fine_tune` and
`random_state` (they are zero-shot); `PatchTSTFMModel` takes neither those nor `known_ahead` and `past` (it is univariate).
`FoundationModel` is the base of both, for a family of your own: it defines `_card`, `_load_backend(resolved, device)` returning
a backend (`epftoolbox2.models._fm.Backend`: `predict(call)` with the quantiles of each step ahead of each item, and for a
fine-tune `fine_tune`, `save_state`, `load_state`, `reset`) and which covariates it takes.

A foundation model needs an information set: its series are cut where the rules say they are known at the issue time, so each
series needs a rule (the built-in ones cover the shipped sources' columns; declare your own with
`InformationSet(rules={...})`). `report.availability()` lists one row per series, with the newest step it reads; at
`availability="raise"` a run refuses a `known_ahead` series not known through the target day.

## What a forecast reads

For the forecast issued on D at horizon h:

- **The target's context** is its last `context x periods per day` steps in physical time, ending at D-1's last step with
  `newest_target="d-1"` (the default of every model) or at the newest step its rule calls known at the issue time with
  `"published"` (with prices published at 13:00 on D-1, D's prices at 11:45). The research's forecasts were made with D's prices
  in the context: pass `newest_target="published"` to reproduce them.
- **Known-ahead series** cover the same steps and the steps ahead, to the end of the target day; **past series** the context,
  NaN after their own newest known step.
- **The steps ahead** run from the context's end to the end of the target day: 24 for an hourly price under `"published"` at
  h = 1, 48 under `"d-1"` (D and D+1), 23 or 25 on a DST target day. The context has the same length on every day; no day is
  resampled.

Calendar covariates are not offered: in the research they hurt every family. Outputs are point forecasts (the 0.5 level);
quantiles are not stored.

## Zero-shot calls

A zero-shot forecast is its own: no fit, and its record's `refit_anchor` is its run date. The calls hold the issue days of a
fixed calendar of `batch_size` days (64 by default, counted from Monday 1970-01-05), every day of it the frame has, the run's or
not, grouped by the number of steps ahead and padded to `batch_size` items with copies of the first. A call has one shape
whatever the run covers, so on a CPU a forecast is the same bits alone, in a full year, after a resume and whatever the test's
first day; `verify`'s co-batch check replaces the other items of a call by noise and requires no forecast to move.

## Fine-tuning t0

`T0Model(fine_tune_every="12MS")` (the default) fine-tunes at each anchor of the refit calendar (here every 1 January), for each
horizon and each of `seeds` seeds (3), a copy of the **base** weights, never the previous anchor's:

- **The windows** are the target days up to the anchor's cut, the newest whole day of targets known at its issue time (D-1 under
  `"d-1"`, the anchor itself under `"published"` with a 13:00 price rule), each read as the forecast issued `horizon` days
  before it; `fine_tune={"window": 365}` keeps the newest 365 days instead of every one from the frame's start (`"expanding"`).
  A window is dropped where its context starts before the frame, where a forecast couldn't be made from it (a known-ahead value
  missing over its steps ahead, a series with no value in its context), where its target context has no two neighbouring
  values (no step-to-step change to scale its loss by) and where its target day has no target; a missing value inside a context
  is kept, masked by t0 as in a forecast, so one missing hour of the load forecast costs the two windows whose steps ahead need
  it, not every window whose year-long context holds it. A run warns with each anchor's counts (kept, kept with gaps, dropped
  and why) where data dropped any or a kept window has a gap, and the manifest records them (`fine_tunes`). The research's
  `t0_ft.py` dropped no window: its DST-resolved data had no missing value. The model raises if a window's target is after the
  cut, before the trainer runs, and the trainer checks it again; a training or holdout loss that isn't finite stops the
  fine-tune with `FloatingPointError` (`NonFiniteLoss`) instead of keeping the base weights as its best state. It names the
  model, the anchor, the horizon and the seed, and says "training diverged" where the weights are no longer finite after a
  step (lower `lr`, or keep `grad_clip`), else the issue days of the windows whose loss isn't finite.
- **The recipe** is the research's (`fine_tune`, a dict, merged over these defaults): AdamW at `lr` 1e-5, batches of 16
  windows, at most 400 steps, the last 61 days of windows held out and evaluated every 25 steps, a stop after 4 evaluations
  without a gain and the best state restored, gradients clipped at norm 1. The loss is t0's pinball loss over its five native
  quantiles on the target day's steps, divided by the mean absolute step-to-step change of the window's context.
- **A forecast** is the mean over the seeds of each seed's median.
- **Stored fine-tunes.** With a `save_dir` each fine-tune is written to `<save_dir>/<name>.fits/` (the name in lower case, as
  the results file) with a sidecar: its sha256, the data end, the best step, the holdout losses, the windows' counts and digests
  of its windows and of everything that decides it, `random_state` and the seed included. A resume or a re-forecast loads it
  instead of fine-tuning again, since GPU fine-tunes are not repeatable (the research's repeats differed by up to 0.16 EUR/MWh).
  A stored fine-tune that doesn't match (its file gone or changed, another seed, other windows, or one stored under another key,
  which the warning names) is fine-tuned again with a warning, as is the folder `<name>.fits/` of a version that kept the
  name's capitals (it is named, not read); a checkpoint is written under a name of its own content before its sidecar names it, so a run stopped anywhere leaves
  the old pair or the new one whole, and a refit removes the checkpoint it replaces. A changed `fine_tune`, `seeds`,
  `fine_tune_every` or `random_state` refuses the resume.
- **Disk.** A t0-alpha checkpoint is about 407 MB, one per anchor, horizon and seed: yearly fine-tunes with 3 seeds take about
  1.2 GB per horizon and year, a monthly re-fine-tune about 14.6 GB per horizon and year (29 GB over two years). Checkpoints of a
  key no current run uses (an earlier `fine_tune`, another `random_state` let in by `allow_manifest_mismatch=True`) stay until
  you remove them:

  ```python
  from epftoolbox2.models.foundation import prune_fine_tunes

  removed = prune_fine_tunes("runs/foundation", "t0_yearly")  # keeps the last run's key, as its manifest records it
  ```

  It takes the results file's lock, so it raises `ResultsLockedError` while a run of the model is writing there.

<Aside type="caution">
Yearly fine-tunes are the default but untested: the research measured a monthly re-fine-tune against none (1.55 % better on
DE_LU, 1.7 % on AT, pooled over both markets), not a yearly one. `fine_tune_every="1MS"` is the monthly recipe on one market.
</Aside>

## PatchTST-FM, Timestral and TimesFM-3

Three zero-shot families on the same base, each with its own extra and card:

```python
from epftoolbox2.information_set import InformationSet
from epftoolbox2.models import PatchTSTFMModel, TimesFMModel, TimestralModel
from epftoolbox2.pipelines import ModelPipeline

pipeline = (
    ModelPipeline(information_set=InformationSet("11:45"))
    .add_model(PatchTSTFMModel(context=341, name="patchtst_fm"))  # the target alone
    .add_model(TimestralModel(size="209m", known_ahead=["load_forecast"], name="timestral"))
    .add_model(TimesFMModel(known_ahead=["load_forecast"], name="timesfm3"))
)
report = pipeline.run(df, "2025-10-01", "2026-09-30", horizon=1, save_dir="runs/flagged")
```

| Class | What its package gets | The forecast | Notes |
|---|---|---|---|
| `PatchTSTFMModel` | the target alone (`past_values`, float32): it has no `known_ahead` or `past` parameter, and setting either raises | the middle of the research's 19 levels of its 99, sorted per step (the 0.5 level) | Its window holds 8,192 steps with the forecast: the newest 8,192 - max(S, 128) context steps go in (8,064 for a day of hours), and the whole context's mean fills the rest of it and any gap; a longer context warns. On a CUDA device the package runs its backbone in bfloat16 autocast (the research's H100 runs did too; the manifest's runtime records `autocast`), on the CPU in float32 |
| `TimestralModel` | `known_ahead` as `known_covariates` (over the context and the steps ahead), `past` as `past_covariates` (over the context), the context with NaN where a step has none (masked) | the level nearest 0.5 of its 21 (0.01, 0.05 to 0.95, 0.99) | `size` is 209m (the research's best), 123m (close on DE_LU, worse on AT) or 28m (the CPU option, 3 to 4 times cheaper); `symmetric_averaging` is the package's default; `clip_nonnegative` is **off** (prices can be negative; the research ran the package's clip on, which changed no forecast at 182 days of context or more). It reads up to 32,768 steps |
| `TimesFMModel` | `known_ahead` as `past_future_covariates`, `past` as `past_only_covariates`, one batch per call | its median, decile index 4 | It reads at most 15,360 steps (640 days of hours; a longer context is cut to its newest steps and warns). The package fills a gap by linear interpolation and holds a past series' newest value after its newest known step, so nothing after the issue time goes in |

Covariates go to each package in the order you list them.

### Flagged licences

- **TimesFM-3** is under the TimesFM Non-Commercial License v1.0: testing, evaluation and research not tied to commercial gain,
  production or revenue. `epf weights fetch TimesFMModel` refuses without `--accept TimesFM-Non-Commercial-1.0`, and every
  report shows `commercial_use: False`.
- **Timestral** is under a modified MIT licence (`Mistral-Modified-MIT`): no rights at all if the global consolidated monthly
  revenue of your company, or of your employer, exceeded USD 20 million in the preceding month (it reaches derivatives and
  combined works), and the attribution "2026 - Mistral AI" goes with every copy. `epf weights fetch TimestralModel --size
  <size>` refuses without `--accept Mistral-Modified-MIT`. Check the revenue figure of your organisation, and your employer's,
  before relying on it.
- **Every report** prints the licence, the revenue cap and the attribution with the verdict of each window
  (`report.provenance()`, the terminal exporter's "Model provenance", the CSV exporter's `<stem>.provenance.csv`, the Excel
  "Provenance" sheet), and the manifest records the card.
- **Contamination.** Timestral's post-training corpus is undocumented and it was released on 2026-10-15, after the research's
  test year: every window starting on or before that day is `possibly contaminated`, so don't present it as a clean benchmark
  result. TimesFM-3's corpus ends in November 2023 (`clean` from December 2023); PatchTST-FM-r2's is documented and stated
  `clean`.
- Neither flagged extra is part of an extra that installs several families.

### Timestral's runtime

The pre-flight compares the timestral package installed with the pinned commit, `a534bdbd244d64f3d9d743f46c7bf6fc330ed4ff`
(the commit pip records in the package's `direct_url.json` when it installs from git):

- **Installed from the repository at that commit**: it runs.
- **Another commit, or a build not installed from the repository** (a wheel, a local directory): refused before any model fits,
  naming the install command and, for another commit, the setting that runs on it.
- **`TimestralModel(runtime_commit="<commit>")`** runs on that commit instead (7 to 40 hex digits), and refuses any other.
- **`weights="/your/directory"`** (weights of your own) runs on whatever build is installed, with a warning.

The manifest records the version and commit installed (`runtime.packages.timestral`, `1.0.0@a534bdb...`) whichever way, and a
resume with another one is refused.

## CPU and GPU

A foundation model runs one model at a time, not in a worker pool: on `device="auto"` (CUDA when a matmul runs on it, else the
CPU), `"cpu"`, `"cuda"` or `"cuda:N"`, with `THREADS_PER_PROCESS` torch threads (default the smaller of 8 and
the usable CPUs), TF32 off, inside a scope that puts the process's torch settings back afterwards. The backend loads once per
process from the cached weights. The manifest records and compares the runtime packages, the weights' hashes, the device type,
dtype, TF32 and the thread count; the GPU's name is recorded and a change only warns.

Chronos-2 reads at most 8,192 steps: 341 days of hours, 85 days of quarter-hours. A longer context is cut to its newest 8,192
steps by the package; each model's run warns about it, and its manifest records the steps read (`runtime.context_steps`), so
`context=350` and `context=364` on hours are the same model, and `context=364` on a 15-minute frame reads about 85 days.

On the CPU the backend runs in the process that runs the pipeline. On a GPU it runs in one spawned process that hosts the GPU
work, started by the first such model and shared by the ones after it, so the pipeline's process never initialises CUDA and
the worker pools of the models after it still fork (a process forked from one that has initialised CUDA can't use CUDA). Each
batch of contexts, each fine-tune's windows (as their series' values once and offsets into them, not a copy of each window's
context) and each checkpoint's path pass to it and its forecasts come back, so the numbers are the in-process ones. Each call
runs there with the pipeline process's `THREADS_PER_PROCESS` and its process-wide torch flags (deterministic algorithms,
cuDNN's, the attention kernels', reduced-precision reductions) as they are at that call, and the manifest records what the
host ran on (`gpu_host`: the threads it really used, the flags it was given). An environment variable CUDA reads as it starts
(`CUBLAS_WORKSPACE_CONFIG`, `PYTORCH_CUDA_ALLOC_CONF`, `CUDA_VISIBLE_DEVICES`, ...) must be set before the first GPU model of
the process runs: one set later doesn't reach the host, and the run warns.

Spawning re-runs the main script in the host, so a script that runs a foundation model on a GPU needs its work under an
`if __name__ == "__main__":` block; one without it is refused before the host starts. A notebook, an interactive session or
`python -c` needs none, but a model class defined there (or inside a function) can't be imported by the host and is refused:
define a subclass of a foundation model in a module.

```python
from epftoolbox2.models import T0Model
from epftoolbox2.pipelines import ModelPipeline


def main(data):
    pipeline = ModelPipeline(issue_time="11:45").add_model(T0Model(device="cuda"))
    return pipeline.run(data, "2024-01-01", "2024-12-31", horizon=1)


if __name__ == "__main__":
    main(data)  # your frame
```

The host ends with the process that started it, also when that is killed in the middle of a call (on Linux the kernel tells
it; elsewhere it watches its parent), so a killed pipeline leaves no process holding the GPU. If the host dies (the machine's
RAM ran out, a crash in native code, a kill), the call raises an error that names the cause from its exit code and points at
its own message on stderr; an out-of-memory error on the device is raised as itself. The next model of the run loads its
backend again in a new host.

If CUDA is initialised in the pipeline's process anyway (GPU work of your own, or another library's, before the run), every
worker pool spawns its workers from then on, as on Windows: their start costs a few seconds more, a class or setting changed in
the session after import doesn't reach them, and a class defined in `__main__` or a notebook cell can't be found. The first such
pool warns, once per process, and the manifest lists the start methods its file's records were made under (`pool_start`,
kept over resumes: `["spawn: CUDA was initialised ...", "fork"]` for a file resumed by a forking run).
