The neural-network models train a network of your choice with the library's own trainer: the library owns the training rows and
their cut, the scaling, the loss, Adam, the early-stopping days, the seeds and the shapes, so a forecast is the same alone, in a
loop of other models and after a resume. `TorchModel` takes any `torch.nn.Module` class; `MLPHourlyModel` and `MLPDailyModel`
are its two presets with the library's `epftoolbox2.nets.MLP`.

```python
from epftoolbox2.models import MLPDailyModel, MLPHourlyModel, TorchModel
from epftoolbox2.pipelines import ModelPipeline
from epftoolbox2.presets import lear_predictors

lear_x = lear_predictors(["load_forecast"])  # day-level: every slot of the day as its own column

pipeline = ModelPipeline()
# One network per horizon with an output for every period of the target day (the Lago-style DNN).
pipeline.add_model(MLPDailyModel(lear_x, hidden=[256, 128], dropout=0.1, training_window=728, refit="7D", seeds=4,
                                 name="mlp_daily"))
# One network per (period, horizon), one output.
pipeline.add_model(MLPHourlyModel(lear_x, hidden=[64], training_window=728, seeds=3, name="mlp_hourly"))
# Your own network, saved to YAML by its import path.
pipeline.add_model(TorchModel(module="my_nets:ResidualMLP", module_params={"width": 256, "depth": 3}, output="day",
                              predictors=lear_x, training_window=1456, seeds=4, name="resmlp"))
```

## TorchModel

```python
from epftoolbox2.models import TorchModel
from epftoolbox2.nets import MLP

model = TorchModel(module=MLP, module_params={"hidden": [256, 128], "dropout": 0.1}, output="day",
                   predictors=["price_h00_d-1", "price_h12_d-1", "is_monday_d+{horizon}"], name="mlp")
```

| Parameter | Default | What it is |
|---|---|---|
| `module` | | The `torch.nn.Module` class, or its import path `"package.module:Class"` |
| `predictors` | `None` | Full predictor names (with `{horizon}`), a `(horizon)` function or a function of `ctx`, for a module with one flat input. Give this or `inputs` |
| `inputs` | `None` | Named blocks `{"block": [names], ...}` for a module that takes one tensor per block (see [Named blocks](#named-blocks)) |
| `module_params` | `None` | Keyword arguments of the module's `__init__` (its architecture), as plain values |
| `output` | `"day"` | `"day"`: one network per (horizon, refit day) with an output for every period of the target day, day-level predictors only; `"period"`: one network per (period, horizon, refit day) with one output |
| `training_window` | `728` | Days of rows per fit, `"expanding"`, or a list of them averaged in EUR/MWh, as for every model |
| `refit` | `"7D"` | The fixed refit calendar: `"7D"` on Mondays, `"1MS"`, `"1D"`, `"auto"`; `None` fits every forecast (`output="period"` only) |
| `seeds` | `4` | Networks per fit, each with its own seed; a forecast is their mean in EUR/MWh |
| `loss` | `"l1"` | `"l1"`, `"mse"` or an elementwise function `(prediction, target) -> loss` as `"package.module:function"`, in the scaled target space; the library masks missing slots and averages |
| `lr` | `3e-4` | Adam's learning rate |
| `max_epochs` | `300` | At most this many epochs |
| `patience` | `20` | Stop after this many epochs without a better early-stopping loss |
| `batch_size` | `64` | Rows per step |
| `early_stopping` | `0.2` | Share of each fit's own training days held out for early stopping; `0` trains every epoch and keeps the last weights |
| `weight_decay` | `0.0` | Adam's L2 weight decay |
| `stack` | `"auto"` | `"auto"` (one network after another on a CPU, a padded stack on a GPU), `"loop"` or `"vmap"` |
| `pad_to` | `None` | The size a stack is padded to (16 when `None`) |
| `device` | `"auto"` | `"auto"` (CUDA when a product runs on it, else the CPU), `"cpu"`, `"cuda"`, `"cuda:N"` |
| `tf32` | `False` | TF32 products on a GPU for this model's fits |
| `random_state` | `0` | The base seed every network's seed is drawn from |
| `newest_target` | `"d-1"` | The newest training target, as for every model ([Time and Calendars](/epftoolbox2/model-pipeline/time-and-calendars/)) |
| `binary_mask` | `None` | Which rows decide the binary 0/1 inputs left unscaled; with `refit`, each fit's own |
| `scaler` | `"standard"` | How the inputs are scaled; `output="day"` takes any scaler (the Invariant, `{"name": "asinh", "params": {"standardise": False}}`, did much better on price inputs, see [the research's recipe](#the-researchs-recipe-reproduced)), `output="period"` only `"standard"` |
| `name` | `"torch"` | The model's name |
| `module_hash` | `None` | Set by a saved file: the hash of the module's file and its package's version (for a class with no module file, a `session-` token) when it was saved (see [Saving and loading](#saving-and-loading)) |
| `normalise_by`, `bounds`, `zero_when` | `None` | A per-row target, as for every model, with `output="period"`; a model with `output="day"` refuses them before any fit (see [Generation targets](/epftoolbox2/models/common-parameters/#generation-targets)) |

`stack`, `pad_to`, `tf32`, `device`, the loss and the learning rate change the numbers and are compared when a run resumes.

### The module contract

With `predictors`, the module is built as `Module(n_inputs, n_outputs, **module_params)` and called as `forward(x)` with `x` of
shape (batch, n_inputs); with named blocks as `Module(input_sizes, n_outputs, **module_params)`, `input_sizes` the width of each
block in the order given, and called as `forward(blocks)` with a dict of one (batch, width) tensor per block. Either returns
(batch, n_outputs): `n_outputs` is the periods of a day (24, or 96 at 15 minutes) for `output="day"` and 1 for `"period"`. The
first two parameter names are checked when the model is built, and so is every key of `module_params`. The module sees scaled
inputs only, never dates or targets, and its outputs are in the scaled target space; see [A network of your own](#a-network-of-your-own).

### What the library does around the module

- **Rows.** `output="day"`: the rows are local dates, the targets the target day's periods, a slot the clock doesn't have (the
  02:00 hour of the spring switch, the repeated autumn hour) or a missing value masked, never filled from another period.
  `output="period"`: the rows of one period, as every model fits. Both on the fixed refit calendar: a forecast issued on D uses
  the fit of its refit day, whose targets end the day before it, never warm-started from an earlier fit.
- **Scaling.** The inputs are standardised, binary columns kept, on each fit's own rows (each window of a list on its own); the
  target of each output goes through its own Invariant, `asinh((y - median) / MAD)`, and back.
- **Seeds and their mean.** Network s of a fit is seeded by a hash of `random_state`, the fit (period, horizon, refit day,
  window, and for a predictor function the content of its list, never the number its plan gave it) and s; never by the model's
  name, its place in a pipeline, the process, the shard, or the days, windows or weekdays a run holds. A forecast is the mean of
  its networks' forecasts in EUR/MWh. A network that diverged (no finite early-stopping loss) makes every forecast of its fit a
  `fit_error`, counted in `forecast_counts()`, never a mean of the others.
- **Early stopping** holds out a random share of each fit's training dates: a date's rows go together, so both rows of a repeated
  autumn hour are on the same side.
- **Shapes.** The steps of an epoch come from the days of a full window, so a fit at the start of the data trains as many steps
  as a later one; a day model predicts every issue day of its refit block in one call of the block's length, so a forecast is
  the same alone, in its block and after a resume.
- **Device, threads, TF32.** Each fit runs on one torch thread with TF32 off (unless `tf32=True`), and puts both back after the
  fit. One fit at a time per worker process: `THREADS_PER_PROCESS` is not used for these models, and `MAX_PROCESSES` (every
  usable CPU by default, one process when the device is a GPU) is how many fits run at once.
- **Not in this step:** a network can't be pooled over the zones of a run (`PooledModel`, refused when it is built: its fits
  come outside the units its seeds are drawn from), nor be a [ResidualModel](/epftoolbox2/models/residual/)'s learner (refused
  when the `ResidualModel` is built).

### Day-level predictors

`output="day"` reads one value of each predictor per local date: daily profiles such as `price_h05_d-1`
([DailyProfileTransformer](/epftoolbox2/transformers/daily-profile/) and a day lag), calendar flags such as `is_monday_d+{horizon}`.
A column that changes with the period of the day raises before any fit, naming its profile names as the fix:

```text
mlp: a day unit reads one value of each predictor per local date, but 'price_d-1' holds values from 61.2 to 98.4 on 2024-03-05
(28 dates like it): it changes with the period of the day. Give its daily profile instead: price_h00_d-1 … price_h23_d-1
```

A [predictor function of `ctx`](/epftoolbox2/model-pipeline/predictor-functions/) may change the list with the horizon and the
issue day, not with the period (`ctx.period`, `ctx.hour`): one fit reads one list for every period of its day, and a function
that returns two raises. `output="period"` takes any predictor and any function.

### Named blocks

```python
import torch
from epftoolbox2 import nets
from epftoolbox2.models import TorchModel
from epftoolbox2.presets import profile_columns


class HourShared(torch.nn.Module):
    """One small layer shared by the 24 hours of each block, then a head."""

    def __init__(self, input_sizes, n_outputs, width=8):
        super().__init__()
        self.names = list(input_sizes)
        self.embed = nets.Linear(len(self.names), width)
        self.head = nets.Linear(width * 24, n_outputs)

    def forward(self, blocks):
        x = torch.stack([blocks[name] for name in self.names], dim=-1)  # (batch, 24, blocks)
        return self.head(torch.relu(self.embed(x)).flatten(1))


model = TorchModel(
    module=HourShared,
    inputs={
        "price_d-1": [f"{c}_d-1" for c in profile_columns("price")],
        "price_d-6": [f"{c}_d-6" for c in profile_columns("price")],
        "load_d+h": [f"{c}_d+{{horizon}}" for c in profile_columns("load_forecast")],
    },
    output="day",
    name="hour_shared",
)
```

The blocks are flattened into the model's predictors for every check (the information set, the day-level check, `verify`), and
the module gets them as views of the flattened columns. The blocks, names and order, are in the manifest: the same columns split
into other blocks are another model to a resume.

### Saving and loading

The module is saved by its import path with a hash of the file that defines it and of its package's version:

```yaml
models:
- class: TorchModel
  params:
    predictors: [...]
    name: resmlp
    refit: 7D
    output: day
    inputs: null
    module_params: {width: 256, depth: 3}
    module: my_nets:ResidualMLP
    module_hash: 3f2a9c0d81b7e4a5
    ...
```

What `module_hash` covers, and so what a resume compares:

- **A network in a module file** (`my_nets.py`, imported) is hashed by that file and its package's version, plus the source of
  any method compiled elsewhere (a decorator from another file that doesn't keep `__wrapped__`): a change to the class, or to a
  layer next to it in the file, refuses a resume, and loading a saved file whose `module_hash` differs warns that the forecasts
  will differ from the saved run's. A change in another module the file imports isn't seen: there the package versions in the
  manifest (torch's, the library's) and its other fields are what guard.
- **A network defined in a notebook, by `exec`, inside a function or in the script being run** resumes only within its session:
  its hash is a token of the class object, the same while that object stands as it is. A run interrupted in a kernel resumes in
  that kernel; after the cell runs again (even unchanged), the class is changed in place (`Net.forward = f`, `Net.SCALE = 3.0`)
  or the kernel restarts, a resume refuses (`ManifestMismatchError`, which says why). The library can't tell what such a class
  calls (another cell's layer, a global, a decorator), so it never takes two definitions for one. Define the network in a module
  file to resume across sessions; pass `allow_manifest_mismatch=True` only if you know the class is unchanged.

`save()` raises for a class defined in the script being run (`__main__`) or inside a function, which a later load can't import;
such a model still runs. `MLPHourlyModel` and `MLPDailyModel` save their architecture (`hidden`, `dropout`, `activation`) and no
`module_hash`: a preset is checked by its manifest alone, which records the hash of `epftoolbox2/nets.py` and the library's
version, so a resume after either changed refuses, and loading its file doesn't warn. Without torch installed, every one of them
builds, saves and loads, and `run()` names the extra to install before any model fits.

## MLPHourlyModel and MLPDailyModel

```python
from epftoolbox2.models import MLPDailyModel, MLPHourlyModel
from epftoolbox2.presets import lear_predictors

lear_x = lear_predictors(["load_forecast"])
daily = MLPDailyModel(lear_x, hidden=[256, 128], dropout=0.1, activation="relu", training_window=[364, 728, "expanding"],
                      seeds=4, lr=3e-4, early_stopping=0.2, name="mlp_daily")
hourly = MLPHourlyModel(lear_x, hidden=[64], dropout=0.0, seeds=3, name="mlp_hourly")
```

`MLPDailyModel(predictors, hidden=(256, 128), dropout=0.1, activation="relu", ..., seeds=4, name="mlp_daily")` is
`TorchModel(module=MLP, module_params={"hidden": [256, 128], "dropout": 0.1}, output="day", ...)` and
`MLPHourlyModel(predictors, hidden=(64,), dropout=0.0, activation="relu", ..., seeds=3, name="mlp_hourly")` is
`TorchModel(module=MLP, module_params={"hidden": [64]}, output="period", ...)`, forecast for forecast. Every other parameter is
`TorchModel`'s, with its defaults: `training_window=728`, `refit="7D"`, `loss="l1"`, `lr=3e-4`, `max_epochs=300`,
`patience=20`, `batch_size=64`, `early_stopping=0.2`, `weight_decay=0.0`, `stack="auto"`, `pad_to=None`, `device="auto"`,
`tf32=False`, `random_state=0`, `newest_target="d-1"`, `binary_mask=None`, `scaler="standard"`, `module_hash=None`;
`MLPHourlyModel` also takes `normalise_by=None`, `bounds=None` and `zero_when=None` ([Generation
targets](/epftoolbox2/models/common-parameters/#generation-targets)), which `MLPDailyModel`, of day units, doesn't.

One network per horizon with an output per hour beat 24 single-hour networks in the research (DE benchmark 3.550 against 3.623
EUR/MWh) at a 24th of the fits. Several configurations matter more than several seeds, and both help: the top 4 configurations
of a search with 4 seeds each beat the best one with 4 seeds. The default search is a loop of models and an
[AverageEnsemble](/epftoolbox2/model-pipeline/ensembles/) of the best on validation: `examples/mlp_search.py`. `tune.BayesSearch` is
the option with proposals and successive halving, see [Hyper-parameter Search](/epftoolbox2/model-pipeline/hyperparameter-search/).

### The research's recipe, reproduced

The research's MLP ensemble (zoo_dl, `dlMLPens top4x4`: the 4 best of 192 configurations on the validation year, 4 seeds
each, weekly refits) rebuilt with `MLPDailyModel`: the helper's hidden sizes, windows (728 or 1,456 days), learning rates,
dropout rates and LEAR input blocks, the 175 LEAR inputs of `lear_predictors(["load_forecast"])`, test year 2025-10-01 to
2026-09-30 on the recent DE_LU and AT data, 8,760 forecasts per model, each configuration a model and their
`AverageEnsemble`, on the CPU:

| Inputs scaled by | DE_LU test MAE | AT test MAE |
|---|---|---|
| the research's stored forecasts | 20.62 | 17.56 |
| the Invariant, `scaler={"name": "asinh", "params": {"standardise": False}}` (as the research) | 20.54 (−0.4 %) | 17.64 (+0.5 %) |
| standardisation, `scaler="standard"` (the default) | 22.18 (+7.5 %) | 19.03 (+8.4 %) |

The configurations were chosen with Invariant inputs, so the second row isn't a search of its own; but `MLPDailyModel` with
its defaults on DE_LU gave 23.04 standardised against 21.10 with Invariant inputs too. Prices have spikes, which
standardisation leaves as large inputs. The research's L1 penalty on the first layer (on 2 of the DE and 3 of the AT
configurations, 3e-6 to 9e-5) and its seeds aren't the library's, and it refitted on every seventh day from the test's
first, where the library refits on Mondays.

Cost per market-year, weekly refits, one torch thread per fit: `MLPDailyModel` with its defaults 4.6 CPU-minutes (212
networks, 1.3 CPU-seconds each, on a quiet 6-core Ryzen); `MLPHourlyModel` with its defaults 44 CPU-minutes (3,816 networks,
0.7 CPU-seconds each, on a loaded EPYC); the top-4 × 4 ensemble above 114 (AT) to 333 (DE) CPU-minutes, its networks being
up to 1024-512 on 1,456 days. The same run gave the same numbers to the bit on both machines (AVX2 kernels).

## Installing torch

```bash
pip install 'epftoolbox2[torch]'
```

installs torch, from PyPI. On Linux, PyPI's torch is the CUDA build (several GB); for a machine without a GPU, install the CPU
wheel first and then the extra:

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install 'epftoolbox2[torch]'
```

and for a GPU, the wheel of your CUDA version (`cu126` here; a GPU that today's wheels have no kernels for, such as compute
capability 6.1, falls back to the CPU, see [Device](#device)):

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu126
```

In a checkout of this repository, `uv sync --extra torch` takes torch from PyTorch's CPU index, as `uv.lock` records it. The extra
covers Python 3.11 to 3.15, free-threaded 3.14t included. Nothing in the core imports torch: `import epftoolbox2` works without it,
and `epftoolbox2.nets` without it raises `MissingExtraError` naming the install line.

## The networks

```python
import torch
from epftoolbox2.nets import MLP

net = MLP(n_inputs=247, n_outputs=24, hidden=[256, 128], dropout=0.1, activation="relu")
out = net(torch.zeros(64, 247))  # (64, 24)
```

| Class | Parameters | What it is |
|---|---|---|
| `MLP` | `n_inputs`, `n_outputs`, `hidden=(256, 128)`, `dropout=0.0`, `activation="relu"` | For each hidden width a `Linear`, an `Activation` and, when `dropout` > 0, a `Dropout`; then a `Linear` to the outputs. With an output per period of the day it is the Lago-style DNN |
| `Activation` | `name="relu"` | An elementwise activation by name, as `torch.nn`'s module of that name computes it: `relu`, `gelu`, `tanh`, `sigmoid`, `softplus`, `elu`, `selu`, `silu`, `leaky_relu` |
| `Dropout` | `p=0.1` | Dropout whose mask is a hash of the member's key, the training step, the layer's number and the element: no draw from torch's generator. Identity in eval mode |
| `Linear` | `in_features`, `out_features` | `x @ weight + bias`, `weight` of shape (in, out), its initial values drawn from the member's key (uniform in ±1/√in, `torch.nn.Linear`'s distribution) |

`Dropout`, `Linear` and `Activation` exist for stacking. The trainer can train the members of a fit (seeds, learning rates) one
after another or together as one stack (`torch.func.vmap`) padded to a fixed size; in a stack, `torch.nn.Dropout` draws one mask
for the whole stack, so a member's mask would depend on its place in it, and the trainer refuses it there (and batch norm, which
updates running statistics in place). `Linear` makes the stacked products the same in any slot and gives each member weights
that depend on its key alone. `Activation` does the same for an activation on a CPU: over a whole stack, a vectorised kernel
computes the elements at the tensor's end, which belong to the last member, another way, and `sigmoid`, `silu`, `elu` or
`softplus` give that member other last bits. Outside the trainer a `Dropout` repeats its mask until its `step` buffer changes
(`layer.step.fill_(k)`).

### A network of your own

A network is any `torch.nn.Module` with `__init__(n_inputs, n_outputs, **params)` and `forward(x)`, `x` of shape (batch,
n_inputs) to (batch, n_outputs). It sees scaled inputs and returns outputs in the scaled target space; it never sees dates, rows
or targets. Use the layers of `epftoolbox2.nets` where you want dropout in a stack, and `nets.Activation` for an activation other
than `relu` (`torch.relu`, sums and products give every element the same bits however a kernel takes them):

```python
import torch
from epftoolbox2 import nets


class ResidualMLP(torch.nn.Module):
    def __init__(self, n_inputs, n_outputs, width=256, depth=3, dropout=0.1):
        super().__init__()
        self.inp = nets.Linear(n_inputs, width)
        self.blocks = torch.nn.ModuleList(nets.Linear(width, width) for _ in range(depth))
        self.drop = torch.nn.ModuleList(nets.Dropout(dropout) for _ in range(depth))
        self.out = nets.Linear(width, n_outputs)

    def forward(self, x):
        h = torch.relu(self.inp(x))
        for block, drop in zip(self.blocks, self.drop):
            h = h + drop(torch.relu(block(h)))
        return self.out(h)
```

Layers from `torch.nn` work too: in a stack their initial weights come from torch's generator seeded by the member, and in the
loop any layer works, `torch.nn.Dropout` and batch norm included.

## The trainer's rules

- **Seeds.** Every random choice of a member comes from its own key (a hash of the model's `random_state` and the fit it belongs
  to: period, horizon, refit date, seed number): its early-stopping days, the order of its rows in each epoch, its initial
  weights and its dropout masks. They don't depend on the model's name, on the other members or on the process.
- **Early stopping** holds out a random share of the member's own training days (`early_stopping=0.2`), never a day outside its
  training window and never the validation period; the best weights on them are restored. A member whose loss on them is never
  finite (it diverged from the start) has no trained weights to restore: it counts as failed and forecasts nothing, rather
  than forecasting from its untrained ones.
- **Fixed shapes.** The steps of an epoch come from the rows of a full training window (a member with fewer rows wraps around its
  own order), the early-stopping rows are padded to their count in a full window, and a stack is padded to a fixed size with
  dummy members. Then a member is bitwise the same alone, in a stack of 16 or 256, in any order and with other learning rates in
  the stack, for a network made of `epftoolbox2.nets` layers and operations exact in every element (sums, products,
  `torch.relu`). Unpadded stacks moved forecasts by up to 7.3 EUR/MWh in the research.
- **Loop or stack.** `stack="auto"` trains one member after another on a CPU (a pool of single-thread fits is the fast way there)
  and padded stacks on a GPU. The two do different arithmetic, so the choice is part of a model's configuration.
- **Threads change numbers.** A product's last bits depend on how many threads compute it, so the same loop on 1 and 8 threads gave
  forecasts up to 8.5 EUR/MWh apart. Each worker process pins torch's threads when it starts, its OpenMP threads and the MKL
  torch bundles alike (setting `OMP_NUM_THREADS` after the fork is too late, and a worker would keep its parent's count), and the
  thread count per fit is recorded in the manifest; a resume with another count is refused. Where the pool forks its workers
  (Linux and macOS) torch runs on one thread per worker, and more is refused: GNU OpenMP in a forked process hangs once its
  parent has run parallel torch work. Use more processes (`MAX_PROCESSES`) instead, the fast way on a CPU anyway. A stack on the
  CPU runs on one thread, so it is the same at any count.
- **TF32 off by default, scoped.** TF32 matrix products are faster on recent GPUs and change the numbers (by up to 0.07 EUR/MWh
  for a foundation model in the research). The library turns it off for each fit unless the model sets `tf32=True`, and puts back
  the flags (`torch.backends.cuda.matmul.allow_tf32`, `torch.backends.cudnn.allow_tf32`, `torch.set_float32_matmul_precision`) and
  the thread count when the fit ends, also after an error, so one model's settings never reach the next.

### Device

`device="auto"` uses the GPU when a 1×1 matrix product runs on it, and the CPU otherwise: a GPU torch has no kernels for fails
that product ("no kernel image is available") and the fit runs on the CPU. The check runs in a short-lived subprocess, so the
process that starts the worker pool never initialises CUDA and its forked workers can still use the GPU. torch's version, the
device type, dtype, `tf32`, the thread count, the stack and its size are recorded in the manifest and compared on resume, and on
a CPU the kernels torch runs (`torch.backends.cpu.get_cpu_capability()`, such as `AVX512` or `AVX2`: torch picks the best the
machine has, and AVX2 against the generic kernels moved a forecast by 1e-6), so a resume on another kind of CPU is refused too;
on a GPU its compute capability (`cuda_capability`, such as `9.0`). The device's model (`device_name`, the GPU's or the CPU's) is
recorded, and a resume on another only warns: bits are not known to hold across GPU models.

<Aside type="caution">
The library doesn't switch on torch's deterministic algorithms. A module of your own whose backward on CUDA uses atomic adds
(`scatter_add`, `index_add`, an embedding's backward, `index_put` with accumulation) gives other numbers from run to run on a GPU.
`pipeline.verify(...)` runs the issue day twice and reports such a model as `inconclusive` (nondeterministic); verify it on the
CPU (`verify(..., device="cpu")`), or keep to layers whose backward has no atomics (the `epftoolbox2.nets` layers have none).
</Aside>

The trainer is a port of the research's stacked trainer, and on the research's own inputs (the DE benchmark, LEAR features,
1456-day windows, 256-128 networks) it gives that trainer's forecasts to the bit on the CPU.
</Aside>

## Many networks at once: torch stacks

A loop of `add_model` calls (a search, plan section 3.12) trains its networks together. `ModelPipeline.run` puts the torch
models of a run whose fits are stacks on their device (`stack="vmap"`, or `"auto"` on a GPU) and that share a **stack key** in
one group, and trains their networks in stacks of `pad_to` members on one device: each network on its own rows, with its own
seeds, learning rate and dropout rate. It is speed only: every forecast, record and manifest is the one the model gives alone,
to the bit, whatever the other models of the loop, their order or how they are split over array tasks
(`models_per_task`), and after a resume.

```python
import random

from epftoolbox2.models import TorchModel
from epftoolbox2.nets import MLP
from epftoolbox2.pipelines import ModelPipeline
from epftoolbox2.presets import lear_predictors

lear_x = lear_predictors(["load_forecast"])
pipeline = ModelPipeline()
rng = random.Random(0)
for i in range(48):
    pipeline.add_model(TorchModel(module=MLP, output="day", predictors=lear_x, training_window=728, refit="7D",
                                  module_params={"hidden": rng.choice([[256, 128], [512, 256], [1024, 512]]),
                                                 "dropout": round(rng.uniform(0, 0.5), 2)},
                                  lr=round(10 ** rng.uniform(-4, -3.5), 6), seeds=4, device="cuda", pad_to=256,
                                  name=f"mlp_{i:02d}"))
```

Here the models of each width are one group, their 4 seeds of every weekly fit trained 256 at a time.

- **The key**: the module (its import path, or a notebook class's own token, so only models of the same class object of the
  session stack together) and its hash, `module_params` but `dropout` (the defaults filled in), `output`, `training_window`,
  `refit`, `loss`, `batch_size`, `max_epochs`, `patience`, `early_stopping`, `weight_decay`, the device, `tf32`, `pad_to` and
  the sizes of named blocks.
  Models that differ in anything else (`lr`, `dropout`, `seeds`, `random_state`, the predictors, the scaler, a per-row
  target) share stacks, each fit prepared and mapped back by its own model. Within a group a stack holds networks of one
  structure only (every layer's class and settings, every weight's shape): a dropout of 0 (no `Dropout` layer) or another
  number of inputs is another stack, and so is a module of your own that keeps a setting of its own as a plain attribute
  rather than in a buffer.
- **When it is bit for bit, and who runs alone.** A stack gives each network the numbers it gets alone when every operation of
  the module and the loss computes each slot's elements alike:
  - on a GPU, for any module the stack takes (its elementwise kernels compute every element alike);
  - on a CPU, only for `nets.MLP` (the presets and `TorchModel(module=MLP)`) with `loss="l1"` or `"mse"`: there a vectorised
    kernel takes a stacked tensor's tail by its scalar path, so a module's own `torch.sigmoid`, `silu`, `softplus`, `log1p`
    or power, or a loss of its own, can give the last slot other last bits (up to 4e-7 in a test). Any other model runs alone
    on a CPU.

  Also alone: a model whose key no other model of the run has, a loop (`stack="auto"` on a CPU: a loop's arithmetic isn't a
  stack's), a `forecast_only` run, and a subclass that changes how a fit is made or read. A module whose structure is drawn
  from torch's generator when it is built (a random projection or permutation kept as a plain attribute rather than a
  buffer, which vmap would run with the first slot's for every slot) is found by building it under two seeds, and its fits
  train alone in their job. A draw both seeds happen to agree on (a coin tossed at build) is found when a stack is built:
  each network's module is compared with the first's, and if any differs that stack's fits train alone, and the models'
  later fits too. `TORCH_STACKS=off`, an environment variable read when a run runs, runs every model on its own.
- **`TORCH_STACKS=check`** stacks as `on` does and also trains about one stacked fit in 50 alone (chosen by a hash of its
  seeds, so the same fits whatever the loop), comparing failures, best epochs and forecasts bit for bit. Each model's
  manifest records `stack_check` (fits checked, how many differed, how many raised when trained or predicted alone and so
  weren't compared, the largest difference in the scaled space), and a model with a difference or a fit not compared warns. A checked fit trains alone as its model would, in a stack of `pad_to` slots of its own, so on a
  GPU with a large `pad_to` each costs about a whole stack: it is a check to run on a sample of a study, not on every run.
- **`pad_to` on a GPU.** A step of a stack costs far less than its networks one by one: the trainer ran 67 networks per second
  (256-128, 50 epochs of 1,456-day windows) in stacks of 256 on an H100, 75 in stacks of 2,048. Alone, a fit's 4 seeds fill 4
  of its `pad_to` slots and the rest is padding; in a loop the stacks are full. Set `pad_to` for the loop (256 suits these
  networks), and keep it: it is compared when a run resumes.
- **On a CPU** a stack does one product per network, so stacking a loop buys little there: `stack="auto"` (a loop of
  single-thread fits in a pool of processes) is the fast way, and it runs each model alone.
- **Failures stay where they were.** A network that diverged makes its own fit's forecasts `fit_error`s, as alone, and moves no
  other network of its stack. A stack that raises (out of GPU memory, say) is trained again fit by fit, as each model alone,
  slower: each worker process warns once, with the error. A fit that raises stops the group as it stops a model's own run,
  with a `RuntimeError` naming the model; what came back is saved and a later run resumes, as after an interrupt.

How it runs: the group reads the data once, as an [engine group](/epftoolbox2/model-pipeline/engine/) does (chunks of at most
`ENGINE_MAX_MODELS` models and `ENGINE_MAX_COLUMNS` columns), and runs jobs of a few refit blocks of every model in
`MAX_PROCESSES` worker processes (one on a GPU). A job holds at least `TORCH_STACK_MEMBERS` networks (by default one stack, up
to four where every process still has a job) and at most 1,024 fits (or `pad_to`, if more); its fits are prepared as each
model's own run prepares them, then trained together, members of one learning rate in the same stacks, since a stack trains
until its last member stops. `ModelPipeline.run` refuses a `TORCH_STACKS` or `TORCH_STACK_MEMBERS` it can't read before any
model writes.

Measured (synthetic data of the research's shapes: 247 inputs, 24 outputs, 728-day windows, weekly refits, 4 seeds): the
48-configuration loop above over half a year, 4,992 networks, took 4.7 minutes on one H100, so two years about 19; a second
process on the same GPU gained nothing. Once warm, a stack trained as fast per network as the research's stacked trainer at a
fixed 50 epochs (0.93 to 1.02 of its speed in stacks of 256 from 256-128 to 1024-512, 1.11 in stacks of 1,024); preparing each
fit's rows (about 50 ms a fit, as alone) was a quarter of the loop's time, and the first stack of a process waits for CUDA. On
a CPU the same loop with `stack="vmap"` over two weeks (384 networks, 20 epochs, `pad_to=16`, 8 processes) took 3.4 minutes
stacked against 31 for its models one by one, each fit's 4 networks padded to 16. Every forecast was its model's own, to the
bit: on the CPU for the 48 configurations alone, in another order and in shards of 20; on the H100 for 12 of them alone and in
another order, for a loop of `MLPHourlyModel`-shaped networks (one output, 146 early-stopping rows a fit) alone and stacked,
and for the tests' loops with TF32 off and on.
