Every model scales each task's data before the fit and maps the prediction back afterwards. The model's `scaler` parameter chooses how. Besides plain standardisation there are two variance-stabilising transformations (VSTs), which damp price spikes and work with negative prices.

```python
from epftoolbox2.models import OLSModel, LassoCVModel

ols = OLSModel(predictors, name="OLS")                            # scaler="standard" (default)
ols_asinh = OLSModel(predictors, name="OLS asinh", scaler="asinh")
lasso_npit = LassoCVModel(predictors, name="Lasso N-PIT", scaler="npit")

# With parameters: transform only the target and the price lags
lasso_price_vst = LassoCVModel(
    predictors,
    name="Lasso asinh prices",
    scaler={"name": "asinh", "params": {"apply_to": ["price", "price_d-*"]}},
)
```

A scaler instance works too, e.g. `scaler=AsinhScaler(apply_to="target")` with `from epftoolbox2.scalers import AsinhScaler`. The model stores it as a `{"name", "params"}` dict so the pipeline can be saved to YAML. Only the scalers listed below are accepted.

## Available scalers

| `scaler` | Class | Transformation of a column `x` (parameters from the training rows) |
|---|---|---|
| `"standard"` | `StandardScaler` | `(x - mean) / sd` |
| `"asinh"` | `AsinhScaler` | `asinh((x - median) / (MAD / 0.6745))`, then standardised |
| `"npit"` | `NPITScaler` | `Φ⁻¹(F̂(x))` with `F̂` the empirical CDF of the training rows, then standardised |

- **`AsinhScaler`** is the "Invariant" scaler of epftoolbox's LEAR (Lago et al., 2021): median/MAD normalisation (the MAD divided by 0.6745 estimates the standard deviation of normal data), then the inverse hyperbolic sine. Near the median it is almost linear. For spikes it grows like a logarithm, and it is symmetric, so negative prices are fine. If the MAD is 0 (more than half of the training values are equal, e.g. a price floor) the sample standard deviation is used, and 1.0 if that is 0 too, or [only rounding noise](#constant-columns). The inverse is `median + scale · sinh(z)`.
- **`NPITScaler`** is the normal probability integral transform. The i-th smallest of n training values gets `F̂ = i / (n + 1)` (tied values share their mid-rank), so every value maps to a finite normal quantile. Between training values the map is linear. Values outside the training range are clamped to the extreme knots: a transformed predictor can't exceed the training range, and **a forecast can't go below the training window's lowest or above its highest price**.

## Parameters

`AsinhScaler` and `NPITScaler` take one parameter:

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `apply_to` | str or list | `"all"` | Which predictors get the VST besides the target: `"all"` (every non-binary predictor), `"target"` (none, predictors are standardised), or a list of glob patterns matched against the expanded predictor names, e.g. `["price", "price_d-*"]` |

`StandardScaler` takes no parameters.

## Which columns are transformed

- **The target** always gets the VST.
- **Predictors** follow `apply_to`. The default `"all"` matches epftoolbox's LEAR, which applies the Invariant scaler to every input except the day-of-week dummies. The VST papers transform the price series. `apply_to=["price", "price_d-*"]` does that and only standardises exogenous inputs such as load or weather. If no pattern matches any predictor, a warning says that only the target is transformed.
- **Binary 0/1 predictors** (dummies) are never changed, whatever `apply_to` says. The same rule as for `StandardScaler` decides what is binary: see [Binary columns](#binary-columns).
- Every column gets its own parameters (median/MAD or empirical CDF), estimated from the task's training rows.
- A predictor that is constant in the training rows is set to 0 instead of being divided by a standard deviation of about 1e-16. See [Constant columns](#constant-columns).
- After the VST every transformed column, and the target, is standardised, so models always receive centred data with unit variance. This is why `OLSModel`, which fits without an intercept, stays valid. epftoolbox's LEAR skips this step. An affine rescaling doesn't change a least-squares fit with an intercept, but it does change the relative scale of the inputs that a Lasso penalty sees, so LassoCV results won't match LEAR's exactly.

## Binary columns

A predictor whose values are all 0 or 1 is left as it is by every scaler. Which predictors those are is decided once per list,
period and horizon, and per window in a run with [validation](/epftoolbox2/model-pipeline/validation-and-test/), not per forecast:
from the training rows of the window's first day or, for a [predictor function](/epftoolbox2/model-pipeline/predictor-functions/)'s
list first used later, of the first day it is used. A column with no value in those rows, such as one that starts inside the test,
can't tell, so it is decided on the first later day whose rows have a value of it; a forecast of the list before that day has no
training row with that column and is skipped. Nothing after a forecast's issue day decides how it is scaled.

## Constant columns

A column whose standard deviation is zero can't be divided by it, so its scale is 1.0. The same goes for a column that is constant apart from rounding noise: one whose standard deviation is at or below 1e-12 of its largest absolute value is treated as constant. Floating-point arithmetic gives a standard deviation of about 1e-16, not 0, for such a column, for example 0.3 with rounding error, or `0.3` repeated 30 times, and dividing by it would turn the noise into a regressor: a test row that differs a little from the constant would reach the model as a value of 1e13 or more.

The rule is the same for every scaler and for the target, which is centred and divided by 1.0 in that case. For `AsinhScaler` and `NPITScaler` it applies to the column as it is before the transformation, which is then fitted as for an exactly constant column. A constant predictor has training values of exactly 0 (missing values stay missing), so the model gives it the coefficient 0 whatever its solver does with a column of noise of about 1e-15. Its test row is centred and divided by 1.0 as usual and is not set to 0. An all-zero column and a column with fewer than two values keep scale 1.0, as before. Any other column is scaled exactly as before. A column with a real spread, however small next to its level (a standard deviation of 1e-9 of its largest value, say), is scaled normally.

## No look-ahead

A fresh scaler is fitted for every (hour, horizon, run day) task on that task's training rows only. The newest training target is the price of the day before the forecast is issued, or, with `newest_target="published"`, the newest its rule says is known by the issue time, never on a row dated on the issue day. The test row is transformed with the training parameters and never changes them. Don't apply a VST to the whole data set in a `DataPipeline`: that would put information from the test period into the training data.

## Back-transformed forecasts are median-type

The model is fitted to the transformed target, and its prediction is mapped back with the inverse VST. The inverse is monotone but non-linear, so it maps a median to a median but not a mean to a mean (`E[sinh(Z)] ≠ sinh(E[Z])`). A model fitted to the transformed target therefore gives, after back-transformation, roughly the **conditional median** price, not the mean. That suits MAE, which the median minimises. RMSE is minimised by the mean, and with skewed, spiky prices the back-transformed forecast can be biased for it. No bias correction is applied.

<Aside type="caution">
  Result files are named after the model and resumed by (hour, horizon, day) only. Give each scaler variant its own `name`, otherwise a run with `save_dir` reuses forecasts made with the other scaler.
</Aside>

## YAML

```yaml
models:
- class: OLSModel
  params:
    predictors: [price_d-1, "load_forecast_d+{horizon}"]
    training_window: 365
    name: OLS asinh
    scaler: asinh
- class: LassoCVModel
  params:
    predictors: [price_d-1, "load_forecast_d+{horizon}"]
    name: Lasso N-PIT prices
    scaler:
      name: npit
      params:
        apply_to: [price, price_d-*]
```

A model without a `scaler` entry uses `standard`.

## Not implemented

The shifted and mirror logarithm, Box-Cox, the parametrised asinh of Uniejewski (2026) and averaging forecasts across transformations are not available yet.
