Every model scales each task's data before the fit and maps the prediction back afterwards. The model's `scaler` parameter chooses how. Besides plain standardisation there are four variance-stabilising transformations (VSTs), which damp price spikes and work with negative prices.

```python
from epftoolbox2.models import OLSModel, LassoCVModel, RidgeModel

ols = OLSModel(predictors, name="OLS")                            # scaler="standard" (default)
ols_asinh = OLSModel(predictors, name="OLS asinh", scaler="asinh")
lasso_npit = LassoCVModel(predictors, name="Lasso N-PIT", scaler="npit")
ridge_mlog = RidgeModel(predictors, name="Ridge mirror-log", scaler="mlog")
ridge_poly = RidgeModel(predictors, name="Ridge poly", scaler={"name": "poly", "params": {"lam": 0.25}})

# With parameters: transform only the target and the price lags
lasso_price_vst = LassoCVModel(
    predictors,
    name="Lasso asinh prices",
    scaler={"name": "asinh", "params": {"apply_to": ["price", "price_d-*"]}},
)
```

A scaler instance works too, e.g. `scaler=AsinhScaler(apply_to="target")` with `from epftoolbox2.scalers import AsinhScaler`. The model stores it as a `{"name", "params"}` dict so the pipeline can be saved to YAML. Only the scalers listed below are accepted.

## Available scalers

| `scaler` | Class | Transformation of a column `x` (parameters from the training rows) |
|---|---|---|
| `"standard"` | `StandardScaler` | `(x - mean) / sd` |
| `"asinh"` | `AsinhScaler` | `asinh((x - median) / (MAD / 0.6745))`, then standardised (not with `standardise=False`) |
| `"mlog"` | `MirrorLogScaler` | `sgn(u) · (log(|u| + 1/c) + log c)` with `u = (x - median) / (MAD / 0.6745)`, c = 1/3, then standardised |
| `"poly"` | `PolyScaler` | `sgn(u) · ((|u| + a)^λ - b)`, `a = (c/λ)^(1/(λ-1))`, `b = (c/λ)^(λ/(λ-1))`, the same `u`, λ = 0.125, c = 0.05, then standardised |
| `"npit"` | `NPITScaler` | `Φ⁻¹(F̂(x))` with `F̂` the empirical CDF of the training rows, then standardised |

- **`AsinhScaler`** is, with `standardise=False`, the "Invariant" scaler of epftoolbox's LEAR (Lago et al., 2021): median/MAD normalisation (the MAD divided by 0.6745 estimates the standard deviation of normal data), then the inverse hyperbolic sine. Near the median it is almost linear. For spikes it grows like a logarithm, and it is symmetric, so negative prices are fine. If the MAD is 0 (more than half of the training values are equal, e.g. a price floor) the sample standard deviation is used, and 1.0 if that is 0 too, or [only rounding noise](#constant-columns). The inverse is `median + scale · sinh(z)`.
- **`MirrorLogScaler`** and **`PolyScaler`** are the mirror-log and the polynomial transformation of Uniejewski, Weron & Ziel
  (2018), on the median/MAD normalisation of `AsinhScaler` (with its fallback for a MAD of 0). Both are odd, zero at the median with
  slope `c` there, and strictly increasing, with an inverse defined for every value: the mirror-log grows like a logarithm for
  spikes, `log(1 + c·|u|)`, the polynomial like `|u|^λ`, a Box-Cox generalisation (λ > 0, not 1). The defaults are the paper's
  (mirror-log c = 1/3; polynomial λ = 1/8, c = 1/20). They are computed in a form that keeps the last digits near the median
  (`log1p`, `expm1`), equal to the paper's formulas within 4e-15 and inverted within 1e-14. In the forecasting plan's research
  (LEAR on DE and AT, 2022–26) each beat the Invariant asinh in DE's 2022 crisis (−2.3 and −2.4 % MAE) and was slightly worse in
  2023–25 (not significantly in DE, significantly in AT); averaged with asinh and N-PIT they are part of the
  [recommended LEAR](/epftoolbox2/models/lear/#recommended-settings).
- **`NPITScaler`** is the normal probability integral transform. The i-th smallest of n training values gets `F̂ = i / (n + 1)` (tied values share their mid-rank), so every value maps to a finite normal quantile. Between training values the map is linear. Values outside the training range are clamped to the extreme knots: a transformed predictor can't exceed the training range, and **a forecast can't go below the training window's lowest or above its highest price**.

## Parameters

`AsinhScaler`, `MirrorLogScaler`, `PolyScaler` and `NPITScaler` take these two:

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `apply_to` | str or list | `"all"` | Which predictors get the VST besides the target: `"all"` (every non-binary predictor), `"target"` (none, predictors are standardised), or a list of glob patterns matched against the expanded predictor names, e.g. `["price", "price_d-*"]` |
| `standardise` | bool | `True` | Keyword-only. Standardise each column after the VST (mean 0, standard deviation 1 on the training rows). `False` leaves that out: a transformed column is the VST alone, and a non-binary predictor that `apply_to` doesn't select stays as it is |

`MirrorLogScaler` takes `c` and `PolyScaler` `lam` and `c` too, keyword-only:

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `c` (`MirrorLogScaler`) | float | `1/3` | The mirror-log's `c`, positive: its slope at the median, and `1/c` the shift inside the logarithm |
| `lam` (`PolyScaler`) | float | `0.125` | The power λ, positive and not 1 (below 1 compresses spikes) |
| `c` (`PolyScaler`) | float | `0.05` | The slope at the median, positive |

A parameter at its default is left out of the scaler's parameters, as `standardise=True` is, so `"mlog"` and
`{"name": "mlog", "params": {"c": 1/3}}` are one scaler in a manifest and in YAML.

`AsinhScaler(standardise=False)` is epftoolbox's Invariant scaler exactly, which [`LEARModel.lago()`](/epftoolbox2/models/lear/#lago-et-al-2021-exactly) uses:
`scaler={"name": "asinh", "params": {"standardise": False}}`. Its MAD is statsmodels' `mad` (epftoolbox's) to the last bit or one
unit in the last place: statsmodels divides each absolute deviation by 0.6745 before taking the median, this library after. A MAD of 0
divides by 0 in epftoolbox, and takes the fallback above here. A near-constant predictor still trains on exact zeros (see
[Constant columns](#constant-columns)). The default `True` is left out of the scaler's parameters, so a spec, a manifest or a YAML
file of the default is what it was before the option existed.

`StandardScaler` takes one, keyword-only:

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `scale_binary` | bool | `False` | Standardise the binary 0/1 predictors too, ignoring which columns are [binary](#binary-columns), as a study that standardises its whole design matrix does: `scaler={"name": "standard", "params": {"scale_binary": True}}` |

The default is left out of the scaler's parameters, so `StandardScaler()` and `{"name": "standard", "params": {"scale_binary": False}}`
are `"standard"`, in a manifest and in YAML.

## Which columns are transformed

- **The target** always gets the VST.
- **Predictors** follow `apply_to`. The default `"all"` matches epftoolbox's LEAR, which applies the Invariant scaler to every input except the day-of-week dummies. The VST papers transform the price series. `apply_to=["price", "price_d-*"]` does that and only standardises exogenous inputs such as load or weather. If no pattern matches any predictor, a warning says that only the target is transformed.
- **Binary 0/1 predictors** (dummies) are never changed, whatever `apply_to` says. The same rule as for `StandardScaler` decides what is binary: see [Binary columns](#binary-columns).
- Every column gets its own parameters (median/MAD, or the empirical CDF for N-PIT), estimated from the task's training rows.
- A predictor that is constant in the training rows is set to 0 instead of being divided by a standard deviation of about 1e-16. See [Constant columns](#constant-columns).
- After the VST every transformed column, and the target, is standardised, so models always receive centred data with unit variance. This is why `OLSModel`, which fits without an intercept, stays valid. epftoolbox's LEAR skips this step. An affine rescaling doesn't change a least-squares fit with an intercept, but it does change the relative scale of the inputs that a Lasso penalty sees, so LassoCV results won't match LEAR's exactly.

## Binary columns

A predictor whose values are all 0 or 1 is left as it is by every scaler, unless `StandardScaler(scale_binary=True)` is asked to
standardise it too. Which predictors those are is decided once per list,
period and horizon, and per window in a run with [validation](/epftoolbox2/model-pipeline/validation-and-test/), not per forecast:
from the training rows of the window's first day or, for a [predictor function](/epftoolbox2/model-pipeline/predictor-functions/)'s
list first used later, of the first day it is used. A column with no value in those rows, such as one that starts inside the test,
can't tell, so it is decided on the first later day whose rows have a value of it; a forecast of the list before that day has no
training row with that column and is skipped. Nothing after a forecast's issue day decides how it is scaled.

A model with [`refit`](/epftoolbox2/model-pipeline/time-and-calendars/#refitting-on-a-calendar) finds them on each fit's own training
rows (those of its period, horizon, refit day and list), not on the first test day, so a forecast doesn't depend on where the run starts.

## Constant columns

A column whose standard deviation is zero can't be divided by it, so its scale is 1.0. The same goes for a column that is constant apart from rounding noise: one whose standard deviation is at or below 1e-12 of its largest absolute value is treated as constant. Floating-point arithmetic gives a standard deviation of about 1e-16, not 0, for such a column, for example 0.3 with rounding error, or `0.3` repeated 30 times, and dividing by it would turn the noise into a regressor: a test row that differs a little from the constant would reach the model as a value of 1e13 or more.

The rule is the same for every scaler and for the target, which is centred and divided by 1.0 in that case. For the four VSTs it applies to the column as it is before the transformation, which is then fitted as for an exactly constant column. A constant predictor has training values of exactly 0 (missing values stay missing), so the model gives it the coefficient 0 whatever its solver does with a column of noise of about 1e-15. Its test row is centred and divided by 1.0 as usual and is not set to 0. An all-zero column and a column with fewer than two values keep scale 1.0, as before. Any other column is scaled exactly as before. A column with a real spread, however small next to its level (a standard deviation of 1e-9 of its largest value, say), is scaled normally.

## No look-ahead

A fresh scaler is fitted for every (hour, horizon, run day) task on that task's training rows only; with `refit`, for every fit (hour, horizon, refit day, list) on its training rows. The newest training target is the price of the day before the forecast is issued, or, with `newest_target="published"`, the newest its rule says is known by the issue time, never on a row dated on the issue day. The test row is transformed with the training parameters and never changes them. Don't apply a VST to the whole data set in a `DataPipeline`: that would put information from the test period into the training data.

## Back-transformed forecasts are median-type

The model is fitted to the transformed target, and its prediction is mapped back with the inverse VST. Every inverse here is monotone but non-linear, so it maps a median to a median but not a mean to a mean (`E[sinh(Z)] ≠ sinh(E[Z])`). A model fitted to the transformed target therefore gives, after back-transformation, roughly the **conditional median** price, not the mean. That suits MAE, which the median minimises. RMSE is minimised by the mean, and with skewed, spiky prices the back-transformed forecast can be biased for it. No bias correction is applied.

<Aside type="caution">
  Result files are named after the model and resumed by (hour, horizon, day) only. Give each scaler variant its own `name`, otherwise a run with `save_dir` reuses forecasts made with the other scaler.
</Aside>

## YAML

```yaml
models:
- class: OLSModel
  params:
    predictors: [price_d-1, "load_forecast_d+{horizon}"]
    training_window: 365
    name: OLS asinh
    scaler: asinh
- class: LassoCVModel
  params:
    predictors: [price_d-1, "load_forecast_d+{horizon}"]
    name: Lasso N-PIT prices
    scaler:
      name: npit
      params:
        apply_to: [price, price_d-*]
```

A model without a `scaler` entry uses `standard`.

## Averaging transformations

No single VST wins in every year. An average of models that differ only in their scaler is an
[`AverageEnsemble`](/epftoolbox2/model-pipeline/ensembles/) of them, as the [recommended LEAR](/epftoolbox2/models/lear/#recommended-settings)
does with Lago's Invariant asinh (`standardise=False`), mirror-log, polynomial and N-PIT: one model per scaler, each with its own `name`, averaged on the forecasts all of
them have. There is no list of scalers inside one model.

## Not implemented

The shifted logarithm, Box-Cox and the parametrised asinh of Uniejewski (2026) are not available yet.
