`Workflow` ties a `DataPipeline` YAML, a `ModelPipeline` YAML, and all run parameters together into a single experiment file.

## Quick Example

```python
from epftoolbox2.pipelines import Workflow

# Phase 1: save config (once, on your laptop)
Workflow(
    data_pipeline="data_pipeline.yaml",
    model_pipeline="model_pipeline.yaml",
    data_start="2023-05-01",
    data_end="2024-08-01",
    data_cache=True,
    model_test_start="2024-06-01",
    model_test_end="2024-07-01",
    model_target="price",
    model_horizon=6,
    max_processes=32,
    threads_per_process=1,
    cache_path="/tmp/scratch/$SLURM_JOB_ID/cache",
).save("experiment.yaml")

# Phase 2: run (cluster job)
report = Workflow.load("experiment.yaml").run()
print(report.summary())
```

## YAML Format

```yaml
environment:
  max_processes: 32
  threads_per_process: 1
  cache_path: /tmp/scratch/$SLURM_JOB_ID/cache   # $VAR expanded at runtime

data_pipeline:
  path: data_pipeline.yaml    # relative to this file's directory
  start: "2023-05-01"
  end: "2024-08-01"
  cache: true

model_pipeline:
  path: model_pipeline.yaml
  test_start: "2024-06-01"
  test_end: "2024-07-01"
  target: price
  horizon: 6
  freq: 1h
```

Dates may be quoted or not. YAML reads an unquoted `end: 2024-08-01` as a date and the workflow treats it like the
string `"2024-08-01"`, so the whole day is included.

**Forecast-only variant**: add `forecast_only: true` and use date keywords so the file runs daily without editing:

```yaml
data_pipeline:
  path: data_pipeline.yaml
  start: "now_d-735"       # ~2 years of history, relative to today
  end: "today_d+6"         # whole horizon-6 day (local day, given `timezone` in data_pipeline.yaml)
  cache: true

model_pipeline:
  path: model_pipeline.yaml
  target: price
  horizon: 6
  freq: 1h                 # set to 15min for 15-minute forecasting
  forecast_only: true      # test_start/test_end default to "today", skips evaluators and exporters
```

<Aside type="tip">
  All paths in the YAML are resolved relative to the workflow YAML's own directory. Move the whole experiment folder and nothing breaks.
</Aside>

## Constructor Parameters

| Parameter | Type | Default | Description |
|-----------|------|---------|-------------|
| `data_start` | str | Required | Data fetch start date |
| `data_end` | str | Required | Data fetch end date |
| `model_test_start` | str | `None` | Test period start; or `model_test` |
| `model_test_end` | str | `None` | Test period end; or `model_test` |
| `data_pipeline` | str \| Path | `None` | Path to `data_pipeline.yaml` |
| `model_pipeline` | str \| Path | `None` | Path to `model_pipeline.yaml` |
| `data_cache` | bool \| str | `False` | Data caching (True, False, or path) |
| `model_target` | str | `"price"` | Target column name |
| `model_horizon` | int | `7` | Max forecast horizon (days) |
| `model_freq` | str | `"1h"` | Forecasting frequency (e.g., `"15min"`) |
| `max_processes` | int | `None` | Worker process count (unset: usable CPUs `// threads_per_process`) |
| `threads_per_process` | int | `None` | Tasks each worker process runs at once, on threads (unset: 1) |
| `cache_path` | str | `None` | Cache directory (overrides `data_cache` if set) |
| `model_index` | int \| str | `None` | Run only this array task: `models[model_index]`, or its block with `models_per_task`. All models run if omitted. Requires `model_save_dir`. `$VAR` reads the variable |
| `models_per_task` | int | `None` | Models per array task: task `i` runs models `[i*k, (i+1)*k)` (YAML: `environment.models_per_task`). See [SLURM arrays](#slurm-arrays-one-model-or-a-block-per-task) |
| `model_forecast_only` | bool | `False` | Skip evaluators/exporters. `test_start`/`test_end` default to `"today"` if omitted |
| `model_save_dir` | str | `None` | Directory for one resumable JSONL per model (YAML: `model_pipeline.save_dir`), resolved from the YAML's directory |
| `model_allow_manifest_mismatch` | bool | `False` | Resume into `model_save_dir` even if its [manifest](/epftoolbox2/model-pipeline/caching/) disagrees with this run's configuration (overwrites it) (YAML: `model_pipeline.allow_manifest_mismatch`) |
| `model_require_manifest` | bool | `False` | Refuse to resume from a `model_save_dir` that has results but no manifest, instead of warning (YAML: `model_pipeline.require_manifest`) |
| `model_validation` | list \| str | `None` | Validation period `[start, end]` or `"previous_year"` (YAML: `model_pipeline.validation`). See [Validation and Test](/epftoolbox2/model-pipeline/validation-and-test/) |
| `model_test` | list | `None` | Test period `[start, end]`, the same as `model_test_start` and `model_test_end`; giving both raises (YAML: `model_pipeline.test`) |

## Environment Variables

`Workflow.run()` always sets these before spawning any worker processes:

| Variable | Value | Why |
|----------|-------|-----|
| `OMP_NUM_THREADS` | `1` | Pins OpenMP threads for libraries loaded later (the worker processes limit loaded BLAS and OpenMP libraries to one thread per task themselves) |
| `MKL_NUM_THREADS` | `1` | Pins Intel MKL threads |
| `OPENBLAS_NUM_THREADS` | `1` | Pins OpenBLAS threads |
| `BLAS_NUM_THREADS` | `1` | Generic BLAS thread pin |
| `PYTHON_GIL` | `0` | Enables free-threading on Python 3.13t+ |
| `MAX_PROCESSES` | from config | Applied if `max_processes` is set |
| `THREADS_PER_PROCESS` | from config | Applied if `threads_per_process` is set |

<Aside type="caution">
  `PYTHON_GIL=0` affects worker processes spawned by the workflow. For the main process on Python 3.13t+, set it before any imports or pass `-Xgil=0` to the interpreter.
</Aside>

## Inline Component Overrides

Pipeline sections can be specified directly in the workflow YAML, overriding the corresponding section from the referenced `path`. If no `path` is given, the pipeline is built entirely from inline sections. `model_pipeline` also takes `information_set` and `availability` this way ([Information Set](/epftoolbox2/model-pipeline/information-set/#three-levels)).

<Tabs>
  <TabItem label="Override transformers">
    ```yaml
    data_pipeline:
      path: data_pipeline.yaml
      start: "2023-05-01"
      end: "2024-08-01"
      cache: true
      transformers:                    # replaces transformers from data_pipeline.yaml
        - class: LagTransformer
          params:
            columns: [load_actual, price]
            lags: [-7, -6, -5, -4, -3, -2, -1, 0]
            freq: day
    ```
  </TabItem>
  <TabItem label="Override models">
    ```yaml
    model_pipeline:
      path: model_pipeline.yaml
      test_start: "2024-06-01"
      test_end: "2024-07-01"
      models:                          # replaces models from model_pipeline.yaml
        - class: OLSModel
          params:
            predictors: [load_actual, price_d-1]
            training_window: 180
            name: OLS_short
    ```
  </TabItem>
  <TabItem label="Inline only (no path)">
    ```yaml
    data_pipeline:
      start: "2023-05-01"
      end: "2024-08-01"
      cache: true
      sources:
        - class: EntsoeSource
          params:
            country_code: PL
            api_key: YOUR_KEY
            type: [load, price]
      transformers:
        - class: ResampleTransformer
          params: {freq: 1h}
      validators:
        - class: CoverageValidator
          params:
            columns: [load_actual, price]
            min_coverage: 1.0
    ```
  </TabItem>
</Tabs>

**Override semantics:** inline sections **replace** the entire corresponding section from the loaded file, not merge. Sources + validators from `path` are kept unless also overridden.

## Full Workflow Setup

<Steps>

1. **Build and save pipeline configs**

   ```python
   import os
   os.environ["PYTHON_GIL"] = "0"

   from epftoolbox2.pipelines import DataPipeline, ModelPipeline
   from epftoolbox2.data.sources import EntsoeSource, OpenMeteoSource, CalendarSource
   from epftoolbox2.data.transformers import TimezoneTransformer, ResampleTransformer, LagTransformer
   from epftoolbox2.data.validators import CoverageValidator
   from epftoolbox2.models import OLSModel, LassoCVModel
   from epftoolbox2.evaluators import MAEEvaluator
   from epftoolbox2.exporters import ExcelExporter, TerminalExporter

   predictors = [
       "is_monday_d+{horizon}", "is_tuesday_d+{horizon}",
       "is_wednesday_d+{horizon}", "is_thursday_d+{horizon}",
       "is_friday_d+{horizon}", "is_saturday_d+{horizon}",
       "is_sunday_d+{horizon}", "is_holiday_d+{horizon}",
       "daylight_hours_d+{horizon}",
       "load_actual_d-1", "load_actual_d-2",
       "price_d-1", "price_d-2",
       "warsaw_temperature_2m_d+{horizon}",
   ]

   (
       DataPipeline(timezone="Europe/Warsaw")
       .add_source(EntsoeSource(country_code="PL", api_key=os.environ["ENTSOE_API_KEY"], type=["load", "price"]))
       .add_source(OpenMeteoSource(latitude=52.2297, longitude=21.0122, prefix="warsaw"))
       .add_source(CalendarSource(country="PL", holidays="binary", daylight=True, weekday="onehot"))
       .add_transformer(TimezoneTransformer())
       .add_transformer(ResampleTransformer(freq="1h"))
       .add_transformer(LagTransformer(columns=["load_actual", "price"], lags=[1, 2, 7], freq="day"))
       .add_transformer(LagTransformer(
           lags=range(-7, 1),
           freq="day",
           columns=[
               "is_monday", "is_tuesday", "is_wednesday", "is_thursday", "is_friday",
               "is_saturday", "is_sunday", "is_holiday", "daylight_hours",
           ],
       ))
       .add_validator(CoverageValidator(columns=["load_actual", "price"], min_coverage=1.0))
       .save("data_pipeline.yaml")
   )

   (
       ModelPipeline()
       .add_model(OLSModel(predictors=predictors, training_window=365, name="OLS"))
       .add_model(LassoCVModel(predictors=predictors, training_window=365, cv=5, name="LassoCV"))
       .add_evaluator(MAEEvaluator())
       .add_exporter(TerminalExporter())
       .add_exporter(ExcelExporter("results.xlsx"))
       .save("model_pipeline.yaml")
   )
   ```

2. **Save workflow config**

   ```python
   from epftoolbox2.pipelines import Workflow

   Workflow(
       data_pipeline="data_pipeline.yaml",
       model_pipeline="model_pipeline.yaml",
       data_start="2023-05-01",
       data_end="2024-08-01",
       data_cache=True,
       model_test_start="2024-06-01",
       model_test_end="2024-07-01",
       model_target="price",
       model_horizon=6,
       max_processes=32,
       threads_per_process=1,
       cache_path="/tmp/cache",
   ).save("experiment.yaml")
   ```

3. **Run job**

   ```python
   import os
   os.environ["PYTHON_GIL"] = "0"

   from epftoolbox2.pipelines import Workflow

   if __name__ == "__main__":
       report = Workflow.load("experiment.yaml").run()
       print(report.summary())
   ```

</Steps>

## SLURM arrays: one model or a block per task

`model_index` selects an array task by its 0-based index. Alone it selects one model, `models[model_index]`, which suits a few models that each deserve a job. With `models_per_task: k`, task `i` runs the block of models `[i*k, (i+1)*k)` in the order of the pipeline's model list, one after another, and the last block may be short, which suits a grid of thousands of models. When `model_index` is omitted, all models run, and `models_per_task` has no effect, with a warning.

In this array mode each task writes its models' results to `model_pipeline.save_dir` (one JSONL per model, resumable if the task is restarted) and skips the [ensembles](/epftoolbox2/model-pipeline/ensembles/#results-on-disk-and-slurm-arrays), evaluators and exporters: they need every model. Once all tasks have finished, merge the results, compute the ensembles and run the evaluators and exporters once with `epf report experiment.yaml` (or `Workflow.load("experiment.yaml").report()`). What the tasks listed about inputs known after the issue time comes from their manifests into the report, once. A negative `model_index` or one past the last block raises, naming the valid range, and so does array mode without `save_dir`. A problem with an ensemble that shows before any fit, such as a `top` ensemble with no validation window, stops every task before it reads any data. With [`validation` and `test`](/epftoolbox2/model-pipeline/validation-and-test/#slurm-arrays-yaml-and-the-cli) each task runs its models over both windows, and a merge raises if the tasks ran on different windows.

**A worked example.** Five models, two per task:

```yaml
environment:
  max_processes: 8
  threads_per_process: 1
  model_index: $SLURM_ARRAY_TASK_ID   # 0-based, expanded at load() time
  models_per_task: 2                  # leave it out for one model per task

model_pipeline:
  path: model_pipeline.yaml
  save_dir: results                   # shared by all tasks; relative to this YAML
  test_start: "2024-01-01"
  test_end: "2024-12-31"
```

| Task | Runs |
|------|------|
| 0 | `models[0]`, `models[1]` |
| 1 | `models[2]`, `models[3]` |
| 2 | `models[4]` |

`epf array` prints the range for `sbatch`, so nobody has to divide by hand and round up. Its standard output holds the range and nothing else, and logs go to standard error:

```bash
epf array experiment.yaml             # 0-2
sbatch --array=$(epf array experiment.yaml) run_task.sh   # each task: epf run experiment.yaml
# after the array has finished (e.g. sbatch --dependency=afterok:<array job id>):
epf report experiment.yaml
```

In Python it is the number of tasks, whatever `model_index` is:

```python
from epftoolbox2.pipelines import Workflow

Workflow.load("experiment.yaml").array_size()  # 3: indices 0 to 2
```

The same file serves all three commands. `$SLURM_ARRAY_TASK_ID` need not be set for `epf array`, `epf report` or `epf validate`. Only `run()` needs an index, and raises if the variable isn't set and `epf run --model-index` doesn't give one.

**The block size is no part of a result.** It only says which task runs a model, and no record or manifest holds it. Results of an array at one `models_per_task` resume at another, and the merge is what one run gives, bit for bit. So if blocks prove too big for the time limit, lower `models_per_task` and submit again: what was stored is kept.

**The blocks follow the model list.** A list changed while an array runs moves them, so finish the array first. Nothing goes wrong silently: a model no task ran has no results file, and a changed model raises `ManifestMismatchError` when it resumes.

`report()` raises if a model has no results file, naming each model of a missing block. `report(allow_missing=True)` (`epf report --allow-missing`) reports the models that have one, and leaves out an ensemble with a missing member, with a warning. A task that stopped in the middle of a model leaves a shorter file, and `report()` warns with its counts. Check `report.forecast_counts()` before comparing models.
