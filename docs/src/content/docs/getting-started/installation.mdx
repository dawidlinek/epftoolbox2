## Parallel Model Training

Models run in a **process pool**: each worker process forecasts whole days, `THREADS_PER_PROCESS` of a day's tasks at a time. `MAX_PROCESSES` × `THREADS_PER_PROCESS` tasks run at once, one per core, and each task runs its BLAS and OpenMP code on one thread.

```
┌─ Process 1 ─────────────┐  ┌─ Process 2 ─────────────┐
│  1 task thread          │  │  1 task thread          │
│  processes days 0..N    │  │  processes days N..M    │
│  BLAS threads = 1       │  │  BLAS threads = 1       │
└─────────────────────────┘  └─────────────────────────┘
```

The defaults, one process per usable CPU and one task thread per process, are the fastest setting in most cases. Threads in one process share its GIL, so with the GIL on they are slower than as many processes, often slower than a single thread. The GIL is on in every standard build, and on a free-threaded build (3.13t+) too unless the interpreter starts with `PYTHON_GIL=0`, because importing pandas 2.x turns it back on. With the GIL off, threads are about as fast as processes and share one copy of the data, which saves memory where each process gets its own copy (Windows, below).

To keep the GIL off, set it when the interpreter starts: `PYTHON_GIL=0 python script.py` or `python -X gil=0 script.py`. Setting `os.environ["PYTHON_GIL"]` inside the script comes too late.

### Script Setup

Both variables are read when a model runs, so they can be set anywhere before that. Both are optional:

```python
import os

os.environ["MAX_PROCESSES"] = "4"        # worker processes (default: one per usable CPU)
os.environ["THREADS_PER_PROCESS"] = "1"  # tasks each process runs at once (default: 1)

from epftoolbox2.pipelines import DataPipeline, ModelPipeline
from epftoolbox2.models import OLSModel, LassoCVModel
```

### Environment Variables

| Variable | Default | Description |
|---|---|---|
| `MAX_PROCESSES` | usable CPUs `// THREADS_PER_PROCESS` | Number of worker processes, never more than the run days (nor 61 on Windows). Usable CPUs are those this process may run on, e.g. a SLURM or `taskset` allocation |
| `THREADS_PER_PROCESS` | `1` | Tasks each worker process runs at once, on threads |

You don't need `OMP_NUM_THREADS`, `MKL_NUM_THREADS` or `OPENBLAS_NUM_THREADS`: each worker process limits BLAS and OpenMP to one thread per task itself (with `threadpoolctl`), and your own process keeps its settings.

### Platform Notes

<Tabs>
  <TabItem label="Linux / Mac">
    Uses `fork`: worker processes inherit the parent's memory directly. No `if __name__ == '__main__':` guard needed in your scripts.
  </TabItem>
  <TabItem label="Windows">
    Uses `spawn`: worker processes start fresh Python interpreters. Scripts that call `model.run()` at top level **must** be wrapped:
    ```python
    if __name__ == '__main__':
        report = model.run(...)
    ```
  </TabItem>
</Tabs>

<Aside type="tip">
  On a shared machine, set `MAX_PROCESSES` below the CPU count to leave cores for others. With `spawn`, each worker process holds its own copy of the data: if memory runs short, use fewer processes.
</Aside>
