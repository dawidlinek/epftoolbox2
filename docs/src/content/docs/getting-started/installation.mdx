## Requirements

- Python 3.11+ (Python 3.14t recommended for parallel processing)
- pandas, numpy, scikit-learn
- requests (for API sources)
- openpyxl (for Excel export)
- rich (for terminal output)

### The `[fast]` extra

```bash
pip install 'epftoolbox2[fast]'
```

installs numba, which compiles the LARS and coordinate-descent kernels of [`LEARModel`](/epftoolbox2/models/lear/): about 10 times
faster for its default exact refit and 35 times for Lago's coordinate descent (`solver="cd"`) than the numpy kernels, which are always
there. `EPFTOOLBOX2_KERNELS` chooses: `auto` (the default) uses numba when it imports, `numpy` never, and `numba` raises
`MissingExtraError` without it. The two agree within 1e-9 with the same kinks, not to the bit (see [Kernels](/epftoolbox2/models/lear/#kernels)
for when), and a run's manifest records which ran. numba compiles on its first use (some 20 s, then cached on disk) in the process that starts the pool, before any worker
forks. The extra is for Python 3.11 to 3.14, free-threaded 3.14t included.

### The `[torch]` extra

```bash
pip install 'epftoolbox2[torch]'
```

installs torch, for the networks of `epftoolbox2.nets` and the neural-network families. On Linux PyPI's torch is the CUDA build;
for a machine without a GPU install the CPU wheel first (`pip install torch --index-url https://download.pytorch.org/whl/cpu`).
See [Neural Networks](/epftoolbox2/models/neural-networks/#installing-torch) for GPUs. The extra is for Python 3.11 to 3.15,
free-threaded 3.14t included.

### The tree extras

```bash
pip install 'epftoolbox2[lightgbm]'    # or [xgboost], [catboost]; [gbm] is LightGBM and XGBoost
```

install the packages of [`LightGBMModel`, `XGBoostModel` and `CatBoostModel`](/epftoolbox2/models/trees/), one extra each.
LightGBM and XGBoost are for Python 3.11 to 3.15, free-threaded 3.14t included (XGBoost's Linux wheel pulls NVIDIA's NCCL, about
300 MB; `pip install xgboost-cpu` instead is its CPU-only build, Python 3.12+, whose forecasts differ from the full
build's: one build per study). CatBoost needs a 3.11 to 3.14 build with the GIL:
it has no wheels for 3.15 or free-threaded builds, and on 3.14t pip tries to build it from source, which fails.

## Parallel Model Training

Models run in a **process pool**: each worker process forecasts whole days, `THREADS_PER_PROCESS` of a day's tasks at a time. `MAX_PROCESSES` × `THREADS_PER_PROCESS` tasks run at once, one per core, and each task runs its BLAS and OpenMP code on one thread.

```
┌─ Process 1 ─────────────┐  ┌─ Process 2 ─────────────┐
│  1 task thread          │  │  1 task thread          │
│  processes days 0..N    │  │  processes days N..M    │
│  BLAS threads = 1       │  │  BLAS threads = 1       │
└─────────────────────────┘  └─────────────────────────┘
```

The defaults, one process per usable CPU and one task thread per process, are the fastest setting in most cases. Threads in one process share its GIL, so with the GIL on they are slower than as many processes, often slower than a single thread. The GIL is on in every standard build, and on a free-threaded build (3.13t+) too unless the interpreter starts with `PYTHON_GIL=0`, because importing pandas 2.x turns it back on. With the GIL off, threads are about as fast as processes and share one copy of the data, which saves memory where each process gets its own copy (Windows, below).

To keep the GIL off, set it when the interpreter starts: `PYTHON_GIL=0 python script.py` or `python -X gil=0 script.py`. Setting `os.environ["PYTHON_GIL"]` inside the script comes too late.

### Script Setup

Both variables are read when a model runs, so they can be set anywhere before that. Both are optional:

```python
import os

os.environ["MAX_PROCESSES"] = "4"        # worker processes (default: one per usable CPU)
os.environ["THREADS_PER_PROCESS"] = "1"  # tasks each process runs at once (default: 1)

from epftoolbox2.pipelines import DataPipeline, ModelPipeline
from epftoolbox2.models import OLSModel, LassoCVModel
```

### Environment Variables

| Variable | Default | Description |
|---|---|---|
| `MAX_PROCESSES` | usable CPUs `// THREADS_PER_PROCESS` | Number of worker processes, never more than the run days (nor 61 on Windows). Usable CPUs are those this process may run on, e.g. a SLURM or `taskset` allocation |
| `THREADS_PER_PROCESS` | `1` | Tasks each worker process runs at once, on threads |
| `EPFTOOLBOX2_KERNELS` | `auto` | `LEARModel`'s kernels: `auto` (numba when the [`[fast]` extra](#the-fast-extra) imports), `numpy` or `numba` |

You don't need `OMP_NUM_THREADS`, `MKL_NUM_THREADS` or `OPENBLAS_NUM_THREADS`: each worker process limits BLAS and OpenMP to one thread per task itself (with `threadpoolctl`). While a run's worker pools exist (from the first model to the last in `ModelPipeline.run`, `verify` and so `Workflow`; one pool in a model's own `run`), your own process's OpenBLAS runs on one thread too: a worker forked from it inherits that count, and setting it there would start one idle OpenBLAS thread per CPU (on Windows, where workers are spawned and load their own libraries, these three variables, `BLIS_NUM_THREADS` and `VECLIB_MAXIMUM_THREADS` are also set to `1` for that time). It gets its count back when the models are done, before ensembles, evaluators and exporters, which restarts its OpenBLAS threads once. Other BLAS and OpenMP libraries in your process, and the variables on Linux and macOS, keep their settings.

### Platform Notes

<Tabs>
  <TabItem label="Linux / Mac">
    Uses `fork`: worker processes inherit the parent's memory directly. No `if __name__ == '__main__':` guard needed in your scripts.
  </TabItem>
  <TabItem label="Windows">
    Uses `spawn`: worker processes start fresh Python interpreters. Scripts that call `model.run()` at top level **must** be wrapped:
    ```python
    if __name__ == '__main__':
        report = model.run(...)
    ```
  </TabItem>
</Tabs>

<Aside type="tip">
  On a shared machine, set `MAX_PROCESSES` below the CPU count to leave cores for others. With `spawn`, each worker process holds its own copy of the data: if memory runs short, use fewer processes.
</Aside>
