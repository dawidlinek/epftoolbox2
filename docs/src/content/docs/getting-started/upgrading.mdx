# Upgrading

This release fixes several methodology issues in the data layer (look-ahead, DST misalignment, silently
dropped rows). Fixing them changes numbers computed on the same dates and config. This page lists what
changed, why, and what you need to do before trusting new results.

<Aside type="caution">
  Don't compare old and new numbers directly, and don't resume an old results directory into this version —
  see [Results directories](#results-directories-recompute-dont-resume) below.
</Aside>

## Why results change

- **ENTSO-E parsing.** A chunk that mixed hourly and 15-minute periods used to keep only one resolution,
  silently dropping the other (this also produced gaps around the 2025-10-01 15-minute go-live). Values
  ENTSO-E omits under curve type A03 because they repeat the previous point are now forward-filled instead
  of left missing. DE_LU/AT day-ahead prices no longer mix the main SDAC auction with the separate EXAA
  auction. Pumped-storage generation and consumption are no longer merged into one series.
- **Open-Meteo cutoff.** `OpenMeteoSource` used to serve whichever forecast run Open-Meteo's API returns for a
  `previous_dayK`/`previous_runs` bucket, which can be a run published *after* the forecast's own issue time —
  look-ahead. It now selects, per row and lead time, only runs initialised at or before a cutoff (`D` at
  `run`:00 UTC, `run` defaulting to `"00"`). Every `*_d+i` weather value can change. See
  [Open-Meteo redesign](#open-meteo-redesign-one-class-apirun-instead-of-issue_timepublication_delay_hvintage)
  below for the full parameter mapping (this folds in and supersedes the original issue-time-vintage change).
- **Calendar-day lags.** `LagTransformer` and the target-shifting in `ModelPipeline` used to shift by a
  fixed 24-hour offset; DST days have 23 or 25 hours, so a day lag landed on the wrong wall-clock hour
  around a spring/autumn switch. Lags now shift by local calendar days. Only the days near each DST switch
  are affected, but every `_d-k`/`_d+k` column in the training window can shift.
- **Resampling.** `ResampleTransformer` no longer interpolates or back-fills real gaps in the source; it
  only fills slots created by *upsampling* (e.g. an hourly value stepped over its four quarter-hours), from
  that slot's own period. The old behaviour could smooth a real outage into a plausible-looking value.
- **The cache.** Per-source caching now writes atomically and locks around fetch+write (concurrent SLURM
  array tasks used to be able to read a half-written file), records coverage from the data actually
  returned rather than the whole requested range, and never caches the part of a range that isn't settled
  yet (today's still-provisional weather, tomorrow's not-yet-published price). A multi-column source's
  outer join used to let a column that stopped early (e.g. `load_actual` during a TSO outage) hide behind
  one that kept going (`price`), so the outage's gap was recorded as covered and never refetched; the
  recorded range is now additionally capped at one step past the last value of any column still being
  published (its last value newer than 14 days before now). The cache key format changed to match
  (`CACHE_FORMAT_VERSION` 2 → 3 → 4): old cache entries are never read by the new code, so old and new
  values can't get mixed silently.

## `.cache/sources/` should be cleared

The format-version bump above means old cache entries are already ignored — reading them again won't return
stale data. Clearing `.cache/sources/` isn't required for correctness, but old entries are dead weight (they
will never be reused), so delete them to reclaim disk space and avoid confusion when inspecting the cache
directory.

## Results directories: recompute, don't resume

A `save_dir` from before this version has no manifest. On resume, epftoolbox2 now writes a
[manifest](/epftoolbox2/model-pipeline/caching/#the-manifest) — model params, the predictors' ordered
layout, a content hash of the data up to `test_end`, its time zone, target, horizon and freq — and compares
it to the current run before adding to an existing results file. A directory with results but no manifest
is accepted with a warning by default (`require_manifest=False`), and a manifest is written from then on;
pass `--require-manifest` (`require_manifest=True`) to refuse instead.

That check only catches *configuration* drift (a different predictor list, a different target, …). It
cannot tell that the same configuration now produces different numbers because a bug fix above changed a
column's values — old rows already in the file are kept as they are and reported as if they were computed
by this version. **Recompute results made before this version from scratch** (a new `save_dir`, or delete
the old one) rather than resuming them; don't rely on the manifest to catch this class of change for you.

## Required and renamed parameters

- **`OpenMeteoSource`: `timezone` is now required (directly or inherited).** It used
  to default to `"Europe/Warsaw"`, which silently mis-timed the cutoff (and therefore leaked or
  over-restricted data) for any market outside that zone. Pass the market's zone explicitly, or set it once with
  `DataPipeline(timezone=...)` and leave it unset here (see the next bullet) — fetching without either raises.
- **The market zone can now be set once, on `DataPipeline(timezone=...)`.** `TimezoneTransformer.target_tz`,
  `CalendarSource`/`OpenMeteoSource`'s own zone all default
  to `None` and then inherit it, instead of each needing the same zone written out again. An explicitly set,
  different zone still raises. This is a drop-in simplification: existing configs that already spell the zone
  out everywhere keep working unchanged.
  ```python
  # before: the same zone written four times
  DataPipeline(
      sources=[OpenMeteoSource(lat, lon, timezone="Europe/Warsaw"), CalendarSource(country="PL", timezone="Europe/Warsaw")],
      transformers=[TimezoneTransformer(target_tz="Europe/Warsaw")],
      timezone="Europe/Warsaw",
  )
  # after: written once
  DataPipeline(
      sources=[OpenMeteoSource(lat, lon), CalendarSource(country="PL")],
      transformers=[TimezoneTransformer()],
      timezone="Europe/Warsaw",
  )
  ```
- **`ResampleTransformer`: `method`/`columns` → `agg`/`fill`.** The old two parameters are still accepted
  (with a `FutureWarning`) and mapped onto the new ones, but under the new, leak-free resampling semantics
  above — not a like-for-like translation of the old behaviour. Prefer `agg="mean", fill="ffill"` (or a
  `{column: ...}` dict for per-column control) going forward.
- **`ImputeTransformer`: `limit` now defaults to `None`.** It used to default to `"1D"`, silently leaving a
  gap longer than one day as NaN. The default now fills every gap the chosen method can reach, however long;
  pass `limit=` explicitly (e.g. `"1D"` for the old behaviour) if you want long outages left unfilled instead
  of masked. `{column}_imputed` still flags every cell the transformer actually filled, so a longer fill
  doesn't hide itself — check that column, not just the absence of NaN, if a long-filled stretch matters to you.
- **`CalendarSource`: `school_subdivisions`/`school_weights` are gone.** `school_holidays` now takes `False`
  (default), `True` (same as before: a single nationwide `is_school_holiday` flag), `"national"` (spelled out),
  or `"all"` — a new mode that replaces per-subdivision flags and a weighted share with one
  `school_holiday_share` column: the unweighted fraction of the country's top-level regions (e.g. Poland's 16
  voivodeships) on school holiday that day. If you relied on per-subdivision columns
  (`is_school_holiday_{code}`) or a population-weighted share, there is no direct replacement; `"all"` gives an
  unweighted regional share instead. See [School holidays](/epftoolbox2/data-sources/calendar/#school-holidays).
- **`CalendarSource`: `regimes=True` now adds a much larger, differently-sourced set of columns.** The
  6-entry `DEFAULT_REGIMES` (market coupling and MTU go-lives) is replaced by a 31-entry catalog covering
  bidding-zone and coupling go-lives, harmonised SDAC price limits, named policy interventions (nuclear
  phase-outs, price caps, capacity markets) and open-ended shocks, each carrying `ex_ante`, `description` and
  `source`. `regimes=True` still means "the on-by-default subset for this country", but that subset is bigger
  and its dates come from more entries — an existing pipeline using `regimes=True` gets new `regime_*` columns
  on its next run, changing predictor counts (and therefore fitted models) even though no code changed. Pass
  `regimes=[...]` with the old names if you need the previous, smaller set reproduced exactly; the catalog is
  otherwise unchanged for entries it already had (dates and default-on status are the same). See [Regime
  dummies](/epftoolbox2/data-sources/calendar/#regime-dummies).

## New components

`EpftoolboxBenchmarkSource` (the Lago et al. 2021 datasets); `DSTNormalizeTransformer`, `DailyProfileTransformer`,
`DailyStatsTransformer`, `LambdaTransformer`, `ImputeTransformer`;
`CoverageValidator`, `DSTStructureValidator`, `PlausibilityValidator`;
variance-stabilising scalers (`asinh`, N-PIT) alongside the default standardiser;
and `epftoolbox2.presets` (ready-made LEAR/expert-model predictor lists). `OpenMeteoSource` also takes several
`locations`, combined into per-location columns, one or more aggregated series per variable (`agg`), or both —
see [Data Sources > OpenMeteoSource > Several locations](/epftoolbox2/data-sources/openmeteo/#several-locations).

## Open-Meteo redesign: one class, `api`/`run` instead of `issue_time`/`publication_delay_h`/`vintage`

`OpenMeteoSource` and the former `OpenMeteoSingleRunsSource` are now **one class**. Which API it uses is now a
parameter, `api="previous_runs"` (default, the old `OpenMeteoSource`'s long lead-time-bucket archive) or
`api="single_runs"` (the old `OpenMeteoSingleRunsSource`'s one-exact-run-per-day archive), and the leak-free
cutoff is now anchored to a UTC run hour, `run` (default `"00"`), instead of a local `issue_time` plus a
`publication_delay_h`: a value on local day D's rows may come only from a model run initialised at or before
`D` at `run`:00 UTC. The old `vintage="valid_time"` look-ahead mapping, and the `derived`/`hdd_base_c`/
`cdd_base_c` computed columns, are removed entirely — nothing replaces them.

| Old | New |
|---|---|
| `OpenMeteoSource(...)` | `OpenMeteoSource(api="previous_runs", ...)` (or omit `api`, it's the default) |
| `OpenMeteoSingleRunsSource(...)` | `OpenMeteoSource(api="single_runs", ...)` |
| `issue_time="10:00"` / `publication_delay_h=10` | `run="00"` (a UTC hour). See the table in [Data Sources > OpenMeteoSource > Choosing `run`](/epftoolbox2/data-sources/openmeteo/#choosing-run) for typical delays per model family, now built into `epftoolbox2.information_set.source_rules` instead of a source parameter. |
| `vintage="issue_time"` (the leak-free default) | nothing to pass — this is now the only behaviour |
| `vintage="valid_time"` (look-ahead) | removed entirely, no replacement |
| `run_interval_h=6` (old `OpenMeteoSingleRunsSource`) | removed; `run` names one exact UTC hour instead of a cycle |
| `derived=["hdd", "cdd", "wind_speed_100m_cubed"]`, `hdd_base_c`, `cdd_base_c` | removed entirely; compute these yourself from the fetched columns if you need them |

```diff
- OpenMeteoSource(latitude=52.23, longitude=21.01, timezone="Europe/Warsaw", issue_time="11:30", publication_delay_h=4)
- OpenMeteoSingleRunsSource(latitude=52.23, longitude=21.01, timezone="Europe/Warsaw", issue_time="11:30", run_interval_h=6)
+ OpenMeteoSource(latitude=52.23, longitude=21.01, timezone="Europe/Warsaw", run="06")
+ OpenMeteoSource(latitude=52.23, longitude=21.01, timezone="Europe/Warsaw", api="single_runs", run="06")
```

A spring-forward target wall-clock hour that doesn't exist (e.g. 2024-03-31 02:00 in `Europe/Warsaw`) now comes
back `NaN` instead of silently shifting to the next hour under that row's name.

## Removed components

- **`ResidualLoadTransformer` and `SpikeFlagTransformer` are gone.** Both were thin wrappers around
  arithmetic that `LambdaTransformer` now expresses directly and more flexibly. Rebuild a residual load
  column with a same-row expression:
  ```python
  # before
  ResidualLoadTransformer(load="load_forecast", renewables=["generation_wind_onshore_forecast"])
  # after
  LambdaTransformer(columns={"residual_load_forecast": "load_forecast - generation_wind_onshore_forecast"})
  ```
  A rolling spike flag needs a `func` (there is no drop-in one-liner): write the median/MAD band as a
  callable, following the example on the [LambdaTransformer](/epftoolbox2/transformers/lambda-transformer/)
  page, or keep a copy of the old `SpikeFlagTransformer` source if you rely on it as-is.
- **`FreshnessValidator` and `LagConsistencyValidator` are gone**, with no replacement. Both were narrow
  checks (one column against the frame's own last row or `today`; day-lag columns against their base
  column) that a few lines over the frame you already have can express directly if you still need them.
- **`NullCheckValidator` is gone; `CoverageValidator` replaces it.** `max_null_frac=f` becomes
  `min_coverage=1 - f` (`allow_nulls=True` becomes `min_coverage=0.0`); `columns` carries over unchanged.
  `CoverageValidator` additionally counts timestamps **missing from the index entirely**, not only null
  values on the rows present, so a column with the same null share can now report lower coverage — the
  errors and warnings it raises are not a strict subset of what `NullCheckValidator` raised.
  ```python
  # before
  NullCheckValidator(columns=["load_actual", "price"], max_null_frac=0.05)
  # after
  CoverageValidator(columns=["load_actual", "price"], min_coverage=0.95)
  ```
- **`CalendarSource`: `fourier_weekly`/`fourier_annual` are gone**, with their `week_sin_k`/`week_cos_k` and
  `year_sin_k`/`year_cos_k` columns. There is no drop-in replacement; if you still want Fourier terms, add
  them with a `LambdaTransformer(func=...)` that computes the phase from the local wall clock (weekday and
  time of day, or day of year and time of day) the same way `CalendarSource`'s other features do — see
  [LambdaTransformer](/epftoolbox2/transformers/lambda-transformer/).

## Also renamed or removed before release

A few names existed only on the development line between the previous release and this one, and never
shipped: `PseSource` (a source for the Polish TSO's own API; the package targets European markets in
general, not one country's TSO), `SettlementPriceSource` (a fixed-schema CSV reader, redundant once
`CsvSource` covers reading your own files), `SchoolHolidaysSource` (folded into `CalendarSource`'s
`school_holidays`, see above), `OpenMeteoWeightedSource` (superseded by `OpenMeteoSource`'s
`locations`/`agg`), and `CalendarSource`'s `subdiv` parameter (renamed to `region`). None of them need a
migration step — they are named here only so the history stays easy to search.

## The new information-set check

`epftoolbox2.information_set` can check, before any model is fit, that every predictor (and the newest
training target) is actually known at the moment a forecast is issued — same-day `load_actual` is the
canonical example of a predictor that isn't. It's opt-in: pass `issue_time` (and optionally
`issue_timezone`) to `ModelPipeline`/`Workflow`, or nothing to skip the check entirely, so existing pipelines
are unaffected until you turn it on. See [Information Set](/epftoolbox2/model-pipeline/information-set/) for
the built-in availability rules, custom rules, and `leakage_probe`, an empirical check that perturbs
not-yet-known values and asserts a model's forecasts don't move.
