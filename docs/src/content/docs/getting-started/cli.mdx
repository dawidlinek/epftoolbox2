After installing epftoolbox2, an `epf` command is available on your PATH.

```bash
pip install epftoolbox2
epf --help
```

## Interactive Mode

Running `epf` with no arguments launches a wizard-style interactive terminal where you can build and run pipelines without writing any YAML.

```bash
epf
```

You'll see a menu with arrow-key navigation:

```
  Run experiment from YAML
  Run data pipeline from YAML → CSV
  Run model pipeline from YAML
  ──────────────────────────────────
  Build & run data pipeline interactively
  Build & run model pipeline interactively
  ──────────────────────────────────
  Exit
```

**Build & run data pipeline interactively** walks you through:
1. Adding sources (EntsoeSource, OpenMeteoSource, CsvSource, CalendarSource, EpftoolboxBenchmarkSource, PseSource) with prompted config
2. Adding transformers (optional)
3. Adding validators (optional)
4. Setting date range and caching
5. Choosing an output CSV path
6. Saving a reusable `data_pipeline.yaml`
7. Running immediately

**Build & run model pipeline interactively** walks you through:
1. Loading an input CSV (from a previous data run, with a prompt for the time zone if the file doesn't name it)
2. Adding models: available columns are shown as a checkbox list for predictor selection
3. Adding evaluators and exporters
4. Setting the test period, target column, horizon and resolution (`1h`, `15min` or `1D`)
5. Saving a reusable `model_pipeline.yaml`
6. Running immediately

<Aside type="tip">
  Both wizards offer to save a YAML at the end. Run that YAML later with `epf run` or `epf data` / `epf model` without going through the wizard again.
</Aside>

## `epf run`: Full workflow

Run a complete experiment from a [Workflow YAML](/epftoolbox2/workflow/overview/).

```bash
epf run experiment.yaml
```

**Options:**

| Flag | Description |
|------|-------------|
| `--model-index N` | Run only array task `N`: `models[N]`, or its block with `environment.models_per_task` (array mode: needs `model_pipeline.save_dir`, see [`epf report`](#epf-report-merge-array-results)) |
| `--processes N` | Override `max_processes` |
| `--threads N` | Override `threads_per_process` |
| `--dry-run` | Build both pipelines without executing, validates config |

**Examples:**

```bash
# Basic run
epf run experiment.yaml

epf run experiment.yaml --model-index 2

# Validate config without running
epf run experiment.yaml --dry-run
```

## `epf report`: Merge array results

After a SLURM array in which each task ran one model or a [block of them](/epftoolbox2/workflow/overview/#slurm-arrays-one-model-or-a-block-per-task) (`--model-index`), merge every model's JSONL from `model_pipeline.save_dir`, compute the [ensembles](/epftoolbox2/model-pipeline/ensembles/) from them and run the evaluators and exporters once. Prints planned vs produced forecasts per model, and what the ensembles chose.

```bash
epf report experiment.yaml
epf report experiment.yaml --allow-missing   # report the models that have results
```

Without `--allow-missing` it fails if any model has no results file, naming each of them. With it, an ensemble with a missing member is left out with a warning.

## `epf array`: The range of a SLURM array

Print the range of array tasks that cover every model of a workflow, as `sbatch --array=` takes it: `0-` the last index, from the number of models and `environment.models_per_task`. Standard output holds the range and nothing else; logs and a count of the tasks go to standard error. Exits with code 1 if the YAML can't be used. `$SLURM_ARRAY_TASK_ID` need not be set.

```bash
epf array experiment.yaml             # 5 models, models_per_task: 2 prints 0-2
sbatch --array=$(epf array experiment.yaml) run_task.sh
```

## `epf data`: Data pipeline only

Run a DataPipeline YAML and save the result as a CSV.

```bash
epf data data_pipeline.yaml --start 2022-01-01 --end 2024-01-01 --output data.csv
```

The CSV keeps the local time zone: the index header names it (e.g. `datetime[Europe/Warsaw]`), and `epf model` and the interactive mode read the data back in that zone, so days and hours match an in-process run.

**Required flags:**

| Flag | Description |
|------|-------------|
| `--start DATE` | Fetch start date (`YYYY-MM-DD`) |
| `--end DATE` | Fetch end date (`YYYY-MM-DD`) |
| `--output FILE` | Output CSV path |

**Optional flags:**

| Flag | Description |
|------|-------------|
| `--cache PATH` | Cache directory or CSV file for source data |

**Example:**

```bash
epf data data_pipeline.yaml \
    --start 2020-01-01 \
    --end 2024-01-01 \
    --output data.csv \
    --cache .cache/
```

## `epf model`: Model pipeline only

Run a ModelPipeline YAML on an existing CSV dataset (e.g. produced by `epf data`). The model's days and hours are local, so the file must say which time zone it is in: files from `epf data` do. For other files with UTC offsets in the timestamps, pass `--tz`.

```bash
epf model model_pipeline.yaml \
    --data data.csv \
    --test-start 2023-01-01 \
    --test-end 2024-01-01
```

**Required flags:**

| Flag | Description |
|------|-------------|
| `--data FILE` | Input CSV file |
| `--test-start DATE` | Test period start. Required with `--test-end`, unless `--validation` is given |
| `--test-end DATE` | Test period end |

**Optional flags:**

| Flag | Description |
|------|-------------|
| `--validation START END` | Validation period, or `--validation previous_year` for each 12 months of the test period served by the 12 months before them. Without a test period only these days are forecast. See [Validation and Test](/epftoolbox2/model-pipeline/validation-and-test/) |
| `--target COL` | Target column name (default: `price`) |
| `--horizon N` | Forecast horizon in days: every horizon from 1 to N (default: `7`) |
| `--horizons LIST` | Only these horizons, in place of `--horizon`: `3-9`, `1,3,7` or `1-3,7`. See [Some horizons only](/epftoolbox2/model-pipeline/time-and-calendars/#some-horizons-only) |
| `--issue-days DAYS` | Issue forecasts on these weekdays only: weekday names joined by commas, in any case, e.g. `friday` or `monday,thursday` (default: every day). Training is untouched. See [Some weekdays only](/epftoolbox2/model-pipeline/time-and-calendars/#some-weekdays-only) |
| `--freq {1h,15min,1D}` | Data resolution: one model per hour, per quarter-hour, or per day on a file with one row per date at one time of day (default: `1h`). Must match the data. See [Daily frames](/epftoolbox2/model-pipeline/time-and-calendars/#daily-frames) |
| `--tz ZONE` | Local time zone of the data (e.g. `Europe/Warsaw`). Overrides the zone named in the file |
| `--issue-time HH:MM` | Compare every predictor with this issue time before fitting ([information set](/epftoolbox2/model-pipeline/information-set/)). Overrides the YAML's `information_set`, or adds one if it has none |
| `--issue-timezone ZONE` | Zone of `--issue-time` (default: the YAML's, else `Europe/Brussels`). Without `--issue-time`, the YAML's issue time is kept, or `11:45` if the YAML has no `information_set` |
| `--availability {none,warn,raise}` | What a predictor known after the issue time does: `warn` lists it and goes on (the default with an issue time), `raise` refuses it before fitting, `none` checks nothing. Overrides the YAML's. `warn` and `raise` need an issue time |
| `--save-dir DIR` | Save per-model prediction JSONL files to this directory |
| `--forecast-only` | Skip evaluators and exporters |
| `--allow-manifest-mismatch` | Resume even if `--save-dir`'s [manifest](/epftoolbox2/model-pipeline/caching/) disagrees with this run's configuration (overwrites it) |
| `--require-manifest` | Refuse to resume from a `--save-dir` that has results but no manifest, instead of warning |

## `epf verify`: Check for leaks

Check on sampled issue days that no forecast depends on anything unknown when it is issued: see [Verifying a Pipeline](/epftoolbox2/model-pipeline/verification/). It prints one row per model and what is wrong.

```bash
epf verify model_pipeline.yaml \
    --data data.csv \
    --test-start 2024-01-01 \
    --test-end 2024-12-31
```

Exits with code 0 only if every model is `ok`, and with code 1 on a `leak`, an `inconclusive` model, or an error. The YAML needs an `information_set`, or pass `--issue-time`.

**Required flags:**

| Flag | Description |
|------|-------------|
| `--data FILE` | Input CSV file, already holding the columns the models use |
| `--test-start DATE` | First issue day to sample from |
| `--test-end DATE` | Last issue day to sample from |

**Optional flags:**

| Flag | Description |
|------|-------------|
| `--target COL` | Target column name (default: `price`) |
| `--horizon N` | Forecast horizon in days: every horizon from 1 to N (default: `1`, while `epf model` defaults to `7`: pass the horizon you run) |
| `--horizons LIST` | Only these horizons, in place of `--horizon`: `3-9`, `1,3,7` or `1-3,7`, the list you run |
| `--issue-days DAYS` | Sample issue days on these weekdays only, as `epf model` takes them: the weekdays you run (default: every day) |
| `--freq {1h,15min,1D}` | Data resolution: one model per hour, per quarter-hour, or per day on a file with one row per date at one time of day (default: `1h`). Must match the data. See [Daily frames](/epftoolbox2/model-pipeline/time-and-calendars/#daily-frames) |
| `--tz ZONE` | Local time zone of the data (e.g. `Europe/Warsaw`). Overrides the zone named in the file |
| `--issue-time HH:MM` | Issue time to verify against. Overrides the YAML's `information_set`, or adds one if it has none |
| `--issue-timezone ZONE` | Zone of `--issue-time` (default: the YAML's, else `Europe/Brussels`). Without `--issue-time`, the YAML's issue time is kept, or `11:45` if the YAML has no `information_set` |
| `--days N` | Issue days per model (default: `5`) |
| `--seed N` | Picks the days and the noise (default: `0`) |
| `--models NAME [NAME ...]` | Names of the models to verify (default: all) |
| `--no-positive-control` | Skip the check that perturbing what is known moves the forecasts; a pass then only says nothing moved |

## `epf validate`: Validate any pipeline YAML

Load and parse a YAML file, instantiate all components, and report errors. Without running anything.

```bash
epf validate data_pipeline.yaml
epf validate model_pipeline.yaml
epf validate experiment.yaml
```

The file type is auto-detected from its top-level keys. Exits with code 1 if validation fails.

## `epf init`: Scaffold template files

Create `experiment.yaml`, `data_pipeline.yaml`, and `model_pipeline.yaml` with placeholder values in the current directory.

```bash
epf init
epf init --force   # overwrite existing files
```
